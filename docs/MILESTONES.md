## 第三阶段：会话生命周期

### 目标

前两阶段解决了音频与结果能否流通。本阶段解决一次会话如何可靠结束：正常结束时保留尾部结果；客户端断开、Worker 报错、输入超时或服务停止时，通知相关操作退出并完成清理；单个会话的异常不影响其他会话。

### 已完成工作与设计取舍

1. **集中判定会话结果并执行收尾。** 上传和下载分别汇报退出原因，由 `session.run` 统一决定如何关闭连接、取消 RPC，并等待内部 goroutine 退出。这样关闭规则集中在一处，代价是需要明确维护事件含义和判定顺序。
2. **区分输入结束与识别完成。** 收到合法 `end` 后只半关闭 gRPC 请求方向，继续接收尾部结果；Worker 的响应流正常结束且已经收到合法 `end`，才满足正常完成条件。`is_final` 只表示片段定稿，Worker 提前结束不能被当作整场成功。
3. **限制输入等待。** 增加等待完整 `start` 的超时，以及音频输入阶段等待下一条完整消息的超时。默认分别为 10 秒和 30 秒，支持配置；合法 `end` 后不再使用输入空闲超时，以免误伤尾部结果处理。
4. **跟踪尚未完成清理的会话数量。** `sessionTracker` 负责接入计数、停止接入和全部退出通知；会话清理后才减少计数。目前没有按 ID 保存会话对象的注册表，因为当前需求是统一停止与等待，不需要逐会话查询或定向取消。
5. **协调服务退出。** 停止接纳新会话，取消已有会话，再执行 HTTP 关闭和会话清理等待；等待预算为 15 秒，清理失败向调用方返回错误。该策略会结束正在进行的问诊连接，不是等待所有问诊自然结束；无缝恢复留到第六阶段。
6. **用可控故障验证资源释放。** 测试覆盖正常尾部结果、客户端直接断开、Worker 报错、超时、服务停止和重复会话清理，检查 Worker、handler、会话计数及底层连接，而不只检查客户端是否收到错误。

代码入口：[session](../internal/gateway/session.go)、[上传与输入超时](../internal/gateway/upload.go)、[下载](../internal/gateway/download.go)、[tracker](../internal/gateway/tracker.go)、[服务退出](../cmd/gateway/main.go)。

### 当前限制与后续归属

- 输入空闲超时只约束读取完整消息的等待，不覆盖阻塞中的 gRPC `Send`、Worker 处理或结果写回；处理等待与慢客户端问题进入第四阶段。
- 目前没有应用层音频队列，但依赖库及操作系统仍有缓冲；已有单消息大小限制不等于总内存或系统容量有界。
- `sessionTracker` 没有最大会话数限制；停止接入开关不等于容量准入控制。
- `Wait` 超时只代表调用方停止等待，不会强制释放会话。WebSocket 关闭还受库的握手行为影响，15 秒是清理等待预算，不是任何故障下的硬性释放保证。
- 第三阶段测试不覆盖长期真实音频、静默网络故障、慢 Worker、发送阻塞和过载，不能据此宣称已达到某个高并发容量。
- 当前支持异常退出与隔离；断线后继续同一问诊、音频重放和结果去重属于第六阶段。

已完成停读诊断：`StallAfterChunks` 已实现并通过行为测试。[改造前停读实验](experiments/stalled-worker.md)中，服务取消与客户端断开各运行三次，均复现 Gateway Send 和客户端 Write 持续等待。客户端断开后三次均在约两秒观察期末仍保留会话，需要实验兜底取消。这是后续发送期限保护的对照基线。

当前进度：单次 Worker Send 期限已经接入配置、上传、RPC 取消原因与独立失败收尾，参见[方案比较](worklog/designs/2026-09-21-worker-send-timeout.md)。配置开发默认值为 2 秒，协调者不会因 download 先退出而丢失发送超时原因。

改造后结果：[发送期限实验](experiments/worker-send-timeout.md)。客户端保持连接和断开两组各三次，均无需外部取消，在阻塞 Send 开始后约 2.005–2.010 秒完成会话清理；客户端断开场景兜底取消由 3/3 降为 0/3。原因是发送超时，不是即时断开检测；该范围也不是所有故障下的清理保证。全量 race 回归通过，并验证发送期限 100ms 不影响延迟 500ms 的正常尾部结果。

当前小步已完成：Mock 一次暂停后恢复的实现与行为测试通过，取消状态和永久停读优先级已修正。[可恢复抖动基线](experiments/worker-pause-recovery.md)比较无暂停、500ms 暂停和 3 秒暂停，各三次，9/9 正常完成。3 秒暂停组的最大结果等待为 2.807–2.810 秒，最大相邻 partial 间隔为 3.255–3.256 秒，而单次 Send 最大耗时仅 0.131–1.311ms，尾部等待仍为 52.0–52.5ms。这是抖动基线，说明发送成功和最终完成不足以代表中途实时性，不是新增的优化收益。完整三组 race 实验与全量 race 回归通过。

上述抖动基线提出的处理落后问题已由下文的积压预算覆盖部分范围；应用及依赖缓冲、单会话总资源边界仍需区分，会话准入上限不等于已测稳定容量。

以下为第四阶段推进顺序的原始路线，已完成项以本节上方的验证记录为准：

1. **复现等待问题。** 让 Mock Worker 可控地变慢或卡住，观察上传、下载分别卡在哪里，先建立可重复的验证场景。

4. **增加会话准入。** 配置并发会话上限，超出时明确拒绝；清理完成后再归还名额。该上限先用于资源保护，稳定容量需要第五阶段实验确定。
5. **验收慢速、抖动与过载。** 检查缓冲、等待、内存与会话数是否受控，并继续运行第三阶段测试，确保尾部结果和清理行为没有退化。

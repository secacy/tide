# Tide Milestones

## 当前进度与阶段口径

**第三阶段「会话生命周期管理」的基础范围已完成；当前处于第四阶段「背压与实时性控制」，尚未完成。**

旧文档只列出一个「M1 - Streaming MVP」，将端到端链路合并描述，没有覆盖后续阶段。本文按当前能力重新整理路线，统一用 M1–M7 对应第一至第七阶段；这是进度梳理，不追溯声称早期已有这些详细验收约定。旧 Streaming MVP 对应下面 M1 与 M2 的合并成果。

## M1 — 流式协议与 Mock Worker

**目标与范围：** 定义音频和识别结果契约，建立可独立于真实模型运行的 gRPC 双向流后端。

**验收与状态：已完成基础范围。**

- [x] 约定 PCM 格式，定义流式音频请求和 partial/final 结果。
- [x] Mock Worker 在输入过程中返回 partial，请求半关闭后返回 final。
- [x] 各 RPC 独立处理音频，取消可中止模拟等待。

**依据：** [流式协议](../proto/tide/asr/v1/asr.proto)、[Mock Worker](../internal/mockasr/worker.go)。没有对应的已落盘 ADR / Experiment，不补造历史记录；旧文档中的 ADR-001 引用无对应文件，故移除。

## M2 — WebSocket 端到端链路

**目标与范围：** 跑通 Client → Gateway → Mock Worker，以及反向结果通路。

**验收与状态：已完成基础范围。**

- [x] 客户端按音频时间轴发送 Start、二进制音频、End，并同步读取结果。
- [x] 音频未发送结束即可收到 partial；正常 End 能收到尾部结果。
- [x] 多会话使用独立 RPC，不串音频与结果。

**依据：** [客户端](../internal/wsclient/client.go)、[Gateway](../internal/gateway/gateway.go)、[协议](../internal/wsprotocol/protocol.go)。[EXP-003](experiments/EXP-003-streaming-load.md) 后续补充了多会话结果归属、顺序和完整性检查，不作为早期实验记录。

## M3 — 会话生命周期管理

**目标与范围：** 明确会话、连接、RPC 和执行流的所有权，实现并发安全的登记、接入限制、取消与服务关闭。

**验收与状态：已完成基础范围。**

- [x] 注册表逐个保存会话；升级前登记，准备、运行和清理阶段均占用名额，原子检查 `MaxSessions`。
- [x] 正常完成、升级失败、协议错误、已被读取发现的客户端断开和 Worker 错误进入相应收尾路径。
- [x] 先取消和关闭以解除等待，再等待执行流退出，最后注销并归还名额。
- [x] `StopAccepting` 停止接入；`Wait` 等待全部注销；`Abort` 请求强制终止，重复及并发调用受控。
- [x] 服务关闭先自然排空，预算耗尽后强制清理；已接管的 WebSocket 连接由会话路径管理。
- [x] 使用关联 `session_id` 的 slog 日志；测试覆盖并发登记、取消、升级竞争和关闭编排。

**边界：** 当前一个 WebSocket 会话对应一次 RPC，尚无独立的 `RecognitionAttempt` 生命周期。M3 的完成不包含静默断网发现、自动重连、断点续传或实例故障后的会话恢复。Start/建流没有专用期限；同步 Close/Abort 不能被等待预算抢占，因此没有无条件的退出时间保证。

**依据：** [当前架构](architecture.md)、[注册表测试](../internal/gateway/registry_test.go)、[Gateway 测试](../internal/gateway/gateway_test.go)、[Abort 回归测试](../internal/gateway/abort_regression_test.go)、[关闭测试](../cmd/gateway/shutdown_test.go)。M4 的 [EXP-001](experiments/EXP-001-send-stall-disconnect.md) / [EXP-002](experiments/EXP-002-slow-websocket-write.md) 进一步验证并加固了阻塞 I/O 下的退出能力。

## M4 — 背压与实时性控制

**目标与范围：** 短暂抖动下继续转发，持续处理不足时限制资源和等待，并明确失败语义。关注单会话流式链路，Worker 池容量与分配策略留给 M5。

**验收与状态：进行中。**

- [x] 上行拆分为 Reader → 有界音频 FIFO → Sender，读取不等待 Send 或队列空位。
- [x] 同时限制队列字节数和块数；满队列明确过载失败，取消 RPC，并尝试通知 WebSocket 1013。
- [x] End 后按序排空，再半关闭请求；结合发送完成与 Worker EOF 判断正常结束。
- [x] 下行保留 Recv → Write，单条结果写入有独立期限；验证慢写退出行为。
- [x] 保存 Send 停滞、慢 Write 的基线与改动后对照；完成持续音频、多会话、抖动和慢 Worker 的初步负载实验。
- [x] 确认工程初值：正常转录可见延迟 P95 目标 1 秒，最早未确认处理音频等待 3 秒触发失败，End 后完成预算 5 秒；失败尾部不保证自动补全。真实出字目标与 Mock 回显指标分开验证。
- [x] EXP-004 对比局部期限与处理进度监测，验证短暂抖动、模拟静音、批量进度、单块停滞和 End 后无 EOF 的行为。
- [x] ADR-003 确认处理进度监测与独立 End 期限；已实现原生 Worker 进度协议、有限记录表、协调者计时和明确的超时关闭原因。
- [x] 正式实现重跑 EXP-004 七场景各两次，验证持续停滞、静音、批量确认和 End 后不返回 EOF；补充协议边界与并发进度测试。
- [ ] 补充真实 TCP 慢读及更广的断开/取消竞争场景，验证期限触发后的取消和资源释放目标。

**当前证据：** 历史 EXP-003 最终采用 16 轮、179 个会话：155 个正常完成，24 个按预期过载退出，清理后登记数均为零。但慢 Worker 下，已返回结果最大延迟约 5.64 秒；**队列可容纳 2 秒音频，不等于端到端延迟上限为 2 秒**。原有队列与写入参数保持不变。

EXP-004 的 42 次候选实验说明局部期限未覆盖已离开队列且 Send 已返回的音频停滞。方案确认并实现后，又完成 14 次生产对照：8 次正常完成、6 次期限退出，约 3 秒未确认等待或 5 秒 End 等待触发，全部清理后登记数归零。更早取消仍有未完成尾部，真实出字 P95 目标尚未验证。进度确认是新的必需 Worker 语义，Gateway 与 Worker 需要配套升级。

**关联：** [ADR-002](adr/ADR-002-streaming-io-backpressure.md)、[ADR-003](adr/ADR-003-processing-progress-deadline.md)、[EXP-001](experiments/EXP-001-send-stall-disconnect.md)、[EXP-002](experiments/EXP-002-slow-websocket-write.md)、[EXP-003](experiments/EXP-003-streaming-load.md)、[EXP-004](experiments/EXP-004-processing-progress-deadline.md)。

## M5 — 容量评估与 Worker 调度

**目标与范围：** 在共享下游处理能力受限时，确定稳定容量、接入规则和多 Worker 会话分配方式。

**状态：未开始。** `MaxSessions` 是当前静态接入上限，不是测得的稳定容量；EXP-003 中各流独立模拟处理，32 会话通过不证明共享模型能承载 32 会话，也不代表已实现 Worker 调度。

**计划验收：**

- 构建共享处理能力受限的可控 Worker，逐步增加负载，观察正常、临界和过载区间。
- 依据延迟、失败率、队列、CPU、内存和清理表现，报告给定环境下的稳定容量与瓶颈。
- 对比单 Worker 基线与候选多 Worker 分配策略，验证名额预留、释放、容量耗尽拒绝和故障 Worker 停止接入的行为。
- 给出可复现实验与适用边界，再决定调度算法和容量配置，不预先要求特定中间件。

**关联：** [EXP-003](experiments/EXP-003-streaming-load.md) 提供负载工具及有限基线；本阶段尚无已确认 ADR / Experiment。

## M6 — 弱网与故障恢复

**目标与范围：** 区分断开、静默失联和实例故障，定义检测、终止及恢复转录的语义。

**状态：未开始。** 当前取消并释放旧会话是恢复的前提，尚不具备恢复协议。

**计划验收：**

- 明确失联检测与恢复时间目标，验证静默断网、半开连接、Worker 退出和 Gateway 退出。
- 先决定重新开始识别还是恢复既有对话，明确允许丢失、重复和重放的边界及客户端可见行为。
- 若一个业务 Session 需要跨连接或跨 RPC 保持身份，再设计独立 `RecognitionAttempt`、音频序号和确认进度等机制。
- 根据所选语义检验恢复时间、音频缺口、结果重复和旧尝试清理；不默认承诺无损恢复或恰好一次。

**关联：** [当前架构](architecture.md) 记录取消与清理基础；本阶段尚无已确认 ADR / Experiment。

## M7 — 真实 ASR 与临床时长验证

**目标与范围：** 接入真实流式模型，在目标部署环境验证完整 ASR 链路。AIGC 病历生成不属于本路线的实现范围。

**状态：未开始。** 一分钟 Mock 负载不能替代数十分钟问诊验证。

**计划验收：**

- 验证真实模型的音频格式、partial/final、半关闭、错误和取消契约；有差异时重新评估接口。
- 定义真实音频采集到结果可见的延迟口径，分别观察中间结果与最终结果，避免直接套用 Mock 逐块回显指标。
- 按确认的临床会话时长、并发和故障负载运行，报告端到端延迟、稳定容量、资源趋势及恢复行为。
- 保存硬件、模型、参数、版本和原始数据，形成部署建议及已知限制；真实模型推翻早期假设时回到对应阶段修正。

**关联：** 尚无本阶段 ADR / Experiment。

## 跨阶段要求与下一步

当前已有结构化日志、回归测试和实验用指标采集；尚未形成在线服务的完整指标体系。随 M4–M7 的验证需求补充活跃会话、拒绝与退出原因、排队与处理延迟、资源及恢复指标，并控制采集开销。实验 hook 不等于生产监控。

**下一任务仍属于 M4：** 用真实 TCP 慢读与断开/取消场景验证已实现的写入、处理进度和 End 期限之间的交互及资源释放。若暴露需要改变设计或语义的重要问题，先记录实验、讨论方案，再决定是否新增或替代 ADR。暂不开始 Worker 调度或恢复协议。

涉及重要设计或语义选择时遵循 [文档工作流](README.md)：对话讨论及必要基线实验 → 确认选择 → 最终 ADR → 实现与验证。普通实现、一般 bug 修复和本次进度整理不单独创建 ADR。

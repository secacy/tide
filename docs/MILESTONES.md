## 当前进度

项目定位：面向长时临床对话的实时语音流式处理系统。当前聚焦 Go ASR 网关，AIGC 病历生成不在本轮实现范围内。

## 第三阶段：会话生命周期

### 目标

前两阶段解决了音频与结果能否流通。本阶段解决一次会话如何可靠结束：正常结束时保留尾部结果；客户端断开、Worker 报错、输入超时或服务停止时，通知相关操作退出并完成清理；单个会话的异常不影响其他会话。

### 已完成工作与设计取舍

1. **集中判定会话结果并执行收尾。** 上传和下载分别汇报退出原因，由 `session.run` 统一决定如何关闭连接、取消 RPC，并等待内部 goroutine 退出。这样关闭规则集中在一处，代价是需要明确维护事件含义和判定顺序。
2. **区分输入结束与识别完成。** 收到合法 `end` 后只半关闭 gRPC 请求方向，继续接收尾部结果；Worker 的响应流正常结束且已经收到合法 `end`，才满足正常完成条件。`is_final` 只表示片段定稿，Worker 提前结束不能被当作整场成功。
3. **限制输入等待。** 增加等待完整 `start` 的超时，以及音频输入阶段等待下一条完整消息的超时。默认分别为 10 秒和 30 秒，支持配置；合法 `end` 后不再使用输入空闲超时，以免误伤尾部结果处理。
4. **跟踪尚未完成清理的会话数量。** `sessionTracker` 负责接入计数、停止接入和全部退出通知；会话清理后才减少计数。目前没有按 ID 保存会话对象的注册表，因为当前需求是统一停止与等待，不需要逐会话查询或定向取消。
5. **协调服务退出。** 停止接纳新会话，取消已有会话，再执行 HTTP 关闭和会话清理等待；等待预算为 15 秒，清理失败向调用方返回错误。该策略会结束正在进行的问诊连接，不是等待所有问诊自然结束；无缝恢复留到第六阶段。
6. **用可控故障验证资源释放。** 测试覆盖正常尾部结果、客户端直接断开、Worker 报错、超时、服务停止和重复会话清理，检查 Worker、handler、会话计数及底层连接，而不只检查客户端是否收到错误。

代码入口：[session](../internal/gateway/session.go)、[上传与输入超时](../internal/gateway/upload.go)、[下载](../internal/gateway/download.go)、[tracker](../internal/gateway/tracker.go)、[服务退出](../cmd/gateway/main.go)。

已记录的资源清理实验：每次预热 6 个会话，再运行 20 轮；每轮同时建立 6 个会话，分别以正常结束、客户端断开、Worker 报错三种方式退出，各 2 个。重复 5 次，共 **600 个正式会话、30 个预热会话**。

- 每轮活跃会话数和服务端未关闭连接数均回到 0。
- 每个会话均观察到 Worker 与 handler 退出。
- 每次运行预热后的 goroutine 数和最终值均为 12；这是当时的观测值，不是固定运行指标。
- 上述重复测试使用 `-race`，没有报告数据竞争。
- 跨测试夹具的明显堆增长，经 profile 和等待后 GC 观察，主要来自 `bufconn` 缓冲区的延迟回收。

详细条件、数据与限制见 [资源清理实验记录](experiments/session-lifecycle-cleanup.md)。以上为已有实验结果，本次文档维护没有重新执行测试。

### 当前限制与后续归属

- 输入空闲超时只约束读取完整消息的等待，不覆盖阻塞中的 gRPC `Send`、Worker 处理或结果写回；处理等待与慢客户端问题进入第四阶段。
- 目前没有应用层音频队列，但依赖库及操作系统仍有缓冲；已有单消息大小限制不等于总内存或系统容量有界。
- `sessionTracker` 没有最大会话数限制；停止接入开关不等于容量准入控制。
- `Wait` 超时只代表调用方停止等待，不会强制释放会话。WebSocket 关闭还受库的握手行为影响，15 秒是清理等待预算，不是任何故障下的硬性释放保证。
- 第三阶段测试不覆盖长期真实音频、静默网络故障、慢 Worker、发送阻塞和过载，不能据此宣称已达到某个高并发容量。
- 当前支持异常退出与隔离；断线后继续同一问诊、音频重放和结果去重属于第六阶段。

## 第四阶段：进行中

状态：**进行中，已完成慢 Worker/停读/抖动/慢客户端实验、发送/尾部/写回期限及单实例准入；缓冲、实时性和资源边界的剩余范围仍待梳理验收。**

已完成小步：在现有结果发送延迟之外，为每个有效音频块增加可取消的处理延迟，并验证 partial 耗尽后仍持续生效。固定音频块大小进行基线实验，后续再加入卡住、抖动等场景；本步不代表已完成背压控制。

实验记录：[持续慢 Worker 的基线实验](experiments/slow-worker-baseline.md)。单会话、10 秒 PCM、100ms/块，正常与持续降速各重复 3 次：两组发送耗时均约 9.9 秒，End 后等待分别为 51.6–51.9ms 与 10.194–10.203 秒；6 次均完整处理音频并正常关闭。已保存逐块原始数据和源码参照，这是问题基线，不是优化收益或容量证明。

验证：Mock 行为测试、全量回归与一轮完整实验的 race 检查通过。下一小步针对更长输入或 Worker 停止读取，定位发送阻塞、取消及积压行为。

已完成停读诊断：`StallAfterChunks` 已实现并通过行为测试。[改造前停读实验](experiments/stalled-worker.md)中，服务取消与客户端断开各运行三次，均复现 Gateway Send 和客户端 Write 持续等待。客户端断开后三次均在约两秒观察期末仍保留会话，需要实验兜底取消。这是后续发送期限保护的对照基线。

当前进度：单次 Worker Send 期限已经接入配置、上传、RPC 取消原因与独立失败收尾，参见[方案比较](worklog/designs/2026-09-21-worker-send-timeout.md)。配置开发默认值为 2 秒，协调者不会因 download 先退出而丢失发送超时原因。

改造后结果：[发送期限实验](experiments/worker-send-timeout.md)。客户端保持连接和断开两组各三次，均无需外部取消，在阻塞 Send 开始后约 2.005–2.010 秒完成会话清理；客户端断开场景兜底取消由 3/3 降为 0/3。原因是发送超时，不是即时断开检测；该范围也不是所有故障下的清理保证。全量 race 回归通过，并验证发送期限 100ms 不影响延迟 500ms 的正常尾部结果。

当前小步已完成：Mock 一次暂停后恢复的实现与行为测试通过，取消状态和永久停读优先级已修正。[可恢复抖动基线](experiments/worker-pause-recovery.md)比较无暂停、500ms 暂停和 3 秒暂停，各三次，9/9 正常完成。3 秒暂停组的最大结果等待为 2.807–2.810 秒，最大相邻 partial 间隔为 3.255–3.256 秒，而单次 Send 最大耗时仅 0.131–1.311ms，尾部等待仍为 52.0–52.5ms。这是抖动基线，说明发送成功和最终完成不足以代表中途实时性，不是新增的优化收益。完整三组 race 实验与全量 race 回归通过。

当前仍未解决输入过程中发送成功后的识别落后、应用层缓冲和单会话总资源边界；会话准入提供了配置上限，但稳定容量尚未测定。

当前小步已完成：单实例会话准入已接入，见[设计取舍](worklog/designs/2026-09-22-session-admission.md)和[量化验收](experiments/session-admission.md)。MaxSessions 默认为开发保护值 64；在上限设为 4 的五轮验收中，100 次突发尝试共接纳 20、容量拒绝 80、其他错误 0，每轮保持 4 个会话名额。全部接纳会话正常完成，清理后 active 均为 0；另外 5 次重新接入也正常完成。已验证等待 start 和尾部结果占位、拒绝不误扣名额、升级失败归还，以及定向和全量 race 回归。

原建议的缓冲边界先行顺序已根据暂停实验调整，先完成可独立验证的准入保护。后续仍需明确缓冲及等待边界；上述结果不证明默认 64 个会话是稳定容量，也不代表内存、识别延迟或多实例共享 Worker 已受控。

当前小步已完成：[尾部期限保护](experiments/tail-timeout.md)已接入配置、结果判定和清理。相较[改造前停滞基线](experiments/tail-stall-baseline.md)，三次实验的外部兜底由 3/3 降为 0/3；测试预算 200ms 时，相对观察到 Worker EOF 的 handler 清理完成时间为 201.45–202.65ms，名额归零后重新接入 3/3 成功。默认配置仍为开发策略 15 秒。已验证 end 前运行超过预算不误超时、预算内尾部完整返回；定向与全量 race 检查通过。该预算不等于所有网络条件下的资源释放硬期限。

当前小步已完成：[结果写回期限](experiments/result-write-timeout.md)已接入配置、download、协调者和直接清理。相较[慢客户端基线](experiments/slow-reader-baseline.md)，三次真实 TCP 实验外部兜底由 3/3 降为 0/3，200ms 测试预算下，从已观测阻塞的底层 Write 到 handler 返回为 201.18–201.41ms，名额归零后重新接入 3/3 成功。默认配置仍为开发策略 2 秒；不同计时起点不直接比较倍数。完整 run 的错误类型、读取失败先到的分类、正常尾部及全量 race 回归均通过。

当前小步：Worker 独立处理进度协议、Gateway 下载分流、Mock 逐块汇报和会话内计量接入已完成，见[方案与取舍](worklog/designs/2026-09-22-worker-progress.md)。确认先于 Send 返回、非法确认退出、发送失败不回滚、溢出时发送前终止及内部错误清理均有测试，全量 race 回归通过。运行链路已保存接收/处理量并可计算未确认量；尚无积压上限或改善数据，下一步先记录当前版本的积压基线，保留直接转发。

目标：当音频进入速度持续超过 Worker 的处理速度时，控制系统允许积压多少、等待多久、接纳多少会话，并向客户端明确报告无法继续处理的情况。

建议按以下顺序推进，每一步先说明原因、方案与取舍，再由开发者实现业务代码、补充相应测试：

1. **复现等待问题。** 让 Mock Worker 可控地变慢或卡住，观察上传、下载分别卡在哪里，先建立可重复的验证场景。
2. **确定缓冲边界。** 对比直接转发与有界队列的行为，再决定是否拆开客户端读取与 Worker 发送；明确缓冲按字节或音频时长如何计量，以及满载时的处理规则。
3. **确定等待边界。** 明确发送、处理、尾部结果和客户端写回分别需要什么期限，避免用一个超时混淆不同原因。
4. **增加会话准入。** 配置并发会话上限，超出时明确拒绝；清理完成后再归还名额。该上限先用于资源保护，稳定容量需要第五阶段实验确定。
5. **验收慢速、抖动与过载。** 检查缓冲、等待、内存与会话数是否受控，并继续运行第三阶段测试，确保尾部结果和清理行为没有退化。

具体阈值与策略尚未确定，不预先填写性能目标或声称收益。第四阶段完成前，应记录实验条件、预期边界、实际数据与剩余问题。

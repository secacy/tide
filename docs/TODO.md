- 重要性：关系到一次问诊能否保留完整记录；具体排期、与第七阶段真实 ASR 接入的先后关系尚未确定。本次只记录待办，不启动设计评审或开发。

### 已明确的业务方向

完整问诊内容的保留优先于持续实时输出；后端暂时跟不上时，可以接受转录延后完成。需要评估如何让实时识别失败时，原始记录仍可保留并最终完成处理。

“约五分钟”是当前提出的可接受等待，不是已验证的服务承诺。后续要明确计时起点、是否包含上传补齐、排队、转录与病历生成，以及适用的问诊时长和并发范围。业务能够接受等待，不代表现有系统已经能在该时间内完成。

### 当前能力与缺口

- 当前积压保护超限会终止受影响的实时会话，并清理资源。它提供资源保护，但可能中断本次转录；相关依据见[积压预算对照](experiments/backlog-comparison.md)。
- 当前有限音频重放用于同实例短暂断网恢复，已确认内容可以释放；它不是完整录音存储，接纳确认也不是持久保存确认。见[第六阶段总结](worklog/2026-10-14-stage-six-summary.md)。
- 尚无覆盖完整问诊的可靠录音保存、延后转录任务和最终结果替换机制；业务客户端也没有与实验工具等价的精确缺口诊断能力。
- 问诊输入最终结束时，有限积压可能被处理完，因此不应把“处理持续落后”直接等同于“只能终止”。但连续新会话仍可能使全系统积压增长，需要同时评估总处理能力和等待资源。

### 需要回答的问题

- [ ] **完整性的范围是什么？** 区分音频采集完整、上传/保存完整、转录处理完成，以及识别准确性；明确网络中断、客户端退出、Gateway/Worker 异常等故障分别承诺到什么程度。音频保存完整不等于识别内容准确无遗漏。
- [ ] **音频在哪里、从何时开始保留？** 比较客户端、服务端或两端配合；明确断网暂存、补传、连续范围校验、保存成功确认和删除条件。若依赖完整录音兜底，仅在超限后才开始保存可能缺少此前已释放内容。
- [ ] **实时处理变慢时如何选择？** 是否短时等待、暂停放行、结束实时流或转为延后处理；触发与恢复条件是什么，如何避免反复切换；录音与识别任务的生命周期是否需要分开。
- [ ] **延后处理什么范围？** 全量重跑、续接原流或只处理缺失部分，分别需要哪些模型能力与输入上下文；如何处理分段变化、说话人信息、实时预览与最终文本之间的差异。
- [ ] **容量与等待怎样约束？** 同时考虑录音存储、上传、任务排队、识别及病历生成；新问诊持续进入时如何准入，存储满或处理长时间不可用时如何明确告知状态，不能无限等待。
- [ ] **何时允许使用最终结果？** 如何区分录音中、已保存、转录中、部分失败和最终完成；病历生成如何获知输入是否完整，未知缺口如何表达。AIGC 仍不属于当前 Go ASR 实现范围，本项先明确交接要求。
- [ ] **保存与清理的边界是什么？** 根据实际部署和业务确定访问范围、保留时长、删除及异常清理责任，不预设无限保存。

### 候选路线，均未选定

| 路线 | 可能价值 | 需要验证的代价或前提 |
| --- | --- | --- |
| 有限缓冲、限时等待，沿用原识别流 | 减少重复计算，可能吸收短时抖动或等待有限输入结束 | 原流仍须存活；输入持续产生时需要存储，后端未必有追赶余量；不单独解决实例状态丢失 |
| 完整音频可靠保存，必要时全量延后转录 | 有机会在实时流失败后重新处理，减少跨流拼接要求 | 增加上传/存储与后台任务管理，可能重复计算，最终文本也可能与实时预览不同 |
| 保存音频与可续处理位置，只补算部分内容 | 可能降低重复计算和最终等待 | 需真实模型上下文或检查点支持，处理进度本身未必可作为恢复点；分段与结果一致性更复杂 |

这些路线可能组合使用；客户端或服务端存储、具体中间件、队列和状态结构均未决定。“完整录音全量重跑”只是候选，不能在项目介绍中写成已选方案或已有能力。

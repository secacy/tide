# Tide 开发协作方式

日期：2026-10-06。依据开发者对工作流调整的确认；适用于后续项目推进，具体任务中的明确授权优先。

## 分工

开发者负责核心业务与并发逻辑，参与并质疑设计选择。助手负责设计讨论、代码评审、测试、负载与指标工具、实验分析、注释及文档维护，并按已有授权提交本步 Git 变更。

评审发现核心问题时，先解释触发场景、原因与修改建议，由开发者修改；明确委托助手实现或修复的内容按委托执行。助手不以测试通过代替设计评审，也需要检查先前指导是否合理。

## 按能力组织、小步实现

每轮实现前说明三件事：当前能力目标、已完成与剩余部分、后面两三步会到哪里。阶段确定范围，可验收能力组织一组改动，小步用于降低单次实现和排错难度。

重要并发、协议和资源所有权设计需要讲清具体问题、备选方案、取舍、必要约束与验证方式。基础实现按需要简短说明。先给必须满足的约束，保留合理实现自由；接口骨架按需要提供，并解释状态、字段、参数及退出信号的含义。

开发者提交“写好了”后，助手读取实际代码，先判断实现与设计，再补有意义的测试。核心需要修改则指导修正；验证完成后记录结果、限制和下一步。定期以组合或端到端验证确认已实现部件形成了目标能力，不能持续增加部件而不检查整条路径。

## 证据与进度

设计前明确要证明的行为；实验前固定负载、条件、指标和判据。正确性测试证明已覆盖场景的行为；性能实验给出特定条件下的完成率、延迟和资源表现；端到端验收证明业务能力。

测试数量是覆盖规模，测试包耗时是验证耗时，二者不能包装为业务收益或恢复性能。记录首次失败及修正原因，不丢弃不利结果；模拟时间、可控替身与真实网络证据明确说明范围。

Milestones 记录当前进度、完成依据与证据缺口；worklog 保存设计、实现及验收；ADR 保存重要决策；experiments 保存实验条件和证据；personal 保存个人复盘。文档随实际完成程度更新，设计提出、部件通过和业务能力接通分别记录。

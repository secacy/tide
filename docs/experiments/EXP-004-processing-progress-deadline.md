# EXP-004: 局部等待期限与处理进度监测

Date: 2026-09-11
Commit: 2cb261b055010072ce5f00f56e9bc4cb2e35f0c5
Related: [EXP-003](EXP-003-streaming-load.md), [ADR-002](../adr/ADR-002-streaming-io-backpressure.md)（现有生产策略）

## Question

已接纳音频尚未确认处理的时间达到 3 秒时，仅限制队列等待和 Send 停滞能否及时退出？处理进度监测能否覆盖这两个局部指标之外的积压，同时容忍短暂抖动、静音和批量进度确认？音频全部处理完之后，是否仍需要独立的 End 完成期限？

本轮是候选方案实验，不是新 ADR 的实施结果。生产协议、默认参数和退出语义保持不变。

## Hypothesis

- 应用队列和 Send 都可能没有长时间等待，而 Worker 仍未处理已接纳的音频；局部期限无法覆盖全部处理停滞。
- 基于 Worker 明确返回的连续处理进度，独立计时器可以在没有新输入或结果的情况下发现未完成音频过期。
- 静音也确认处理进度，不用文字输出间隔判断处理停滞；确认间隔小于预算时可以容忍批量确认。
- 处理进度达到输入末尾不代表 RPC 已完成，End 后不返回 EOF 需要独立期限。

## Setup

已确认的工程初值：正常语音转录可见延迟目标 P95 ≤ 1 秒；最早未确认处理音频等待达到 3 秒触发失败；Gateway 收到 End 后完成预算 5 秒。允许 500 ms 短暂处理停顿后追赶。失败不静默丢弃后继续报告成功，不保证未完成尾部可自动补全。这些是项目实验起点，不是临床标准或已验证的生产承诺。

| 策略 | 保留的边界 | 实验新增判定 |
| --- | --- | --- |
| baseline | 当前 64,000 字节 / 128 块队列、2 秒结果写入期限 | 仅观测，不主动按音频年龄或 End 时间退出 |
| local | 同上 | 队列中最早音频等待 ≥ 3 秒，或单次 Send 持续 ≥ 3 秒；End 后 ≥ 5 秒 |
| progress | 同上 | 最早未确认处理音频等待 ≥ 3 秒；End 后 ≥ 5 秒 |

Client：单会话，每 20 ms 发送 640 字节合成 PCM，按绝对时间节奏发送，迟到时补发；同时读取结果。音频中编码序号与客户端发送前的单调时间戳。没有真实音频采集或模型推理。

| 场景 | 输入与 Worker 行为 | 每策略重复次数 |
| --- | --- | ---: |
| normal | 300 块，约 6 秒；每块处理 5 ms | 2 |
| jitter | 同上，第 51 块处理停顿 500 ms，之后恢复 5 ms | 2 |
| slow | 最多 600 块，约 12 秒；每块处理 50 ms | 2 |
| silence | 300 块，每块处理 5 ms，只返回处理进度，末尾返回 final | 2 |
| batched_progress | 300 块，每块处理 5 ms；每 50 块确认一次连续进度，结果仍逐块返回 | 2 |
| stalled_one | 只发送 1 块，不发 End；Worker 收到后不处理，观察 6 秒 | 2 |
| end_hang | 50 块，约 1 秒；正常处理并确认全部音频，收到半关闭后不返回 final/EOF；从启动观察 8 秒 | 2 |

silence 是“持续处理但没有文字输出”的协议行为模拟，不验证真实静音检测。stalled_one 故意不发 End，避免 End 期限掩盖音频处理停滞。end_hang 的基线在 End 后实际观察约 7 秒。

Environment：Go 1.26.5，darwin/arm64，机器报告 12 个逻辑 CPU。具体 CPU 型号、物理内存和真实 CPU/GPU 处理能力未测量。WebSocket 与 gRPC 均为真实协议，经 64 KiB bufconn 内存传输；gRPC 流窗口固定 64 KiB、连接窗口 1 MiB。各场景顺序运行，正式采样关闭 race detector。

实验实现：

- Go overlay 在临时编译副本中观测入队、出队、End 和会话生命周期；每会话独立 watchdog 每 10 ms 检查一次，退出时等待 watchdog 结束。
- Worker 处理完音频后，通过真实 gRPC 发送累计确认。实验用保留的 SegmentId 加 Text 编码进度，由客户端适配器消费；不是已设计或发布的生产协议。
- 确认值代表“此前所有音频已处理”的连续前缀，可重复但不能倒退或超出已接纳范围。Worker 收到音频时不确认处理完成。
- 三组都有相同的进度消息和观测开销，仅退出策略不同。Worker 的共享原子计数仅作事后核对，watchdog 不读取它作为进度。
- 候选超时调用 Session cancellation，复用现有收尾路径；本原型由该路径发送 1001。它不代表生产的过载/超时关闭码已经确定。队列满沿用 1013。
- 实验记录有限输入的完整到达时间数组，最多 600 项；这不是未来生产进度追踪器的内存设计。本轮不测容量或内存性能。

## Metrics

- `oldest_unacknowledged_peak_ms`：每次检查时，从最早未确认音频成功入队到当前的时间峰值。包含应用队列、传输及 Worker 处理和确认返回等待；不包含客户端采集到 Gateway 入队前的时间。
- `queue_age_peak_ms` 与 `send_max_ms`：局部队列等待的采样峰值、实际 Send 调用最大耗时。
- `first_age_breach_ms`：第一次观测到未确认音频等待 ≥ 3 秒的时刻；`trigger_ms` 是策略触发取消的时刻，两者都相对客户端开始发送。
- `trigger_to_cleanup_ms`：策略触发到 Gateway handler 与 Worker handler 均退出；`end_to_cleanup_ms` 包含尾部处理和清理，不是单独的客户端最终结果延迟。
- 音频发送、接纳、出队、实际处理、收到确认、返回结果和未确认尾部数量；最终注册表数量。
- `result_latency`：发送前到客户端收到对应回显结果的时间，复用 EXP-003 的 1 ms 向上取整直方图；只覆盖已返回结果，静音没有 partial 样本。它不证明真实转录 P95 目标已满足。
- `observation_end`：观测窗结束后，实验主动取消，属于截断样本；不能作为策略自行退出的证据。

3 秒和 5 秒是触发判定阈值；10 ms 检查周期和运行时调度会带来少量超出。清理时间另外报告，不宣称所有网络条件下都能在阈值内完成资源释放。采样峰值可能漏掉两次检查间的瞬时变化。

## Results

正式样本共 42 次（7 场景 × 3 策略 × 2 次），24 次正常完成，12 次由被测策略自行结束，6 次由实验观察窗截断。全部 Gateway 和 Worker handler 最终退出，注册表归零；所有时间连续性与音频计数校验通过，本轮没有排除或补跑正式样本。

| 场景 | baseline | local | progress |
| --- | --- | --- | --- |
| normal | 2/2 正常完成 | 2/2 正常完成 | 2/2 正常完成 |
| jitter | 2/2 正常完成 | 2/2 正常完成 | 2/2 正常完成 |
| silence | 2/2 正常完成，无 partial | 2/2 正常完成，无 partial | 2/2 正常完成，无 partial |
| batched_progress | 2/2 正常完成 | 2/2 正常完成 | 2/2 正常完成 |
| slow | 9.723–9.724 秒队列满退出 | 9.721 秒左右队列满退出 | 4.951–4.971 秒因未确认音频过期退出 |
| stalled_one | 6 秒观察窗内未自行退出 | 6 秒观察窗内未自行退出 | 3.011–3.012 秒退出 |
| end_hang | End 后约 7.02 秒仍未自行退出 | End 后 5.010 秒左右退出 | End 后 5.010 秒左右退出 |

表中退出时间包含本次清理；slow/stalled_one 相对客户端开始发送，end_hang 相对 Gateway 收到 End。观察窗截断不是策略成功。候选期限退出与观察窗截断都复用 1001，原始数据通过 outcome 明确区分；队列满为 1013。

baseline/local 约在第 4.95–4.97 秒就观察到未确认音频等待达到 3 秒，但直到队列满才退出。局部队列等待约 2 秒、最长 Send 约 1.32 秒，都未达到各自的 3 秒期限。progress 在第一次观测到超限的检查中触发取消，当时队列峰值仅 640 字节；它检测到的是已经离开应用队列的积压。

stalled_one 更直接地暴露局部期限盲区：三组 Send 均在 0.04 ms 内返回，队列没有持续等待；baseline/local 观察 6 秒仍无自发取消，progress 在未确认音频等待约 3009.6 ms 时触发。Worker 接收过这块音频，但处理计数仍为零。

end_hang 中三组都确认了全部 50 块音频，未确认尾部为零；因此处理进度期限本身没有超时条件。local/progress 由独立的 End 期限退出。所有候选期限退出的触发至清理耗时为 0.668–1.973 ms，仅代表本次内存传输和配合清理的 Worker。

normal 三组回显延迟 P95 均为 8 ms；jitter 为 283–290 ms，短暂停顿后完成全部音频；batched_progress 的未确认音频等待峰值约 0.980–0.990 秒，未误触发。silence 无 partial 样本，不能把没有延迟样本写成“0 ms 出字延迟”。

先行的 21 个组合 race 检查、常规全量 race 和 vet 均通过。另在本文版本提供 [watchdog 正向控制测试](../../internal/gateway/deadline_experiment_validation_test.go)，构造已过期的队列、Send、音频进度和 End 状态，确认各分支确实能取消；连续 10 次 race 检查通过。这些回溯时间状态的检查不计入正式样本，也不作为延迟测量。

## Conclusion

四项假设在本轮条件下得到支持：

- local 在当前阈值下没有达到未确认音频等待 3 秒即触发失败的目标。调整局部阈值可能改变 slow 的退出时间，但无法覆盖 stalled_one 中“队列为空且 Send 已返回”的状态。
- progress 在持续慢处理和单块停滞中发现超期，且不依赖新音频到达；500 ms 抖动、模拟静音和约 1 秒批量确认均正常完成。
- 进度全部确认后仍可能不返回 EOF，需要单独限制 End 后的完成等待。
- 更早取消缩短了失败会话继续积累音频的时间，仍留下未确认尾部。失败样本中未返回的结果不进入延迟直方图，不能仅凭更低的 P95 宣称服务体验已改善。

本轮支持优先评估“处理进度监测＋独立 End 期限”，尚未形成新的生产设计决策。现有队列上限与结果写入期限仍分别承担内存边界和慢写保护，不能被进度期限替代。

证据边界：每组只有两次、单会话、内存传输、可控 Worker；不证明真实网络、高并发或真实模型下的表现。处理确认耗时包括确认返回，批量周期过长或下行堵塞可能导致保守退出；真实 Worker 必须提供有语义保证的连续处理进度，不能把接收确认或最近一次文本输出冒充它。生产追踪结构、协议兼容、进度合法性、期限触发与正常结束竞争、错误通知和慢客户端清理还需要正式设计与验证。正常转录可见延迟 P95 ≤ 1 秒仍是待真实模型验证的目标。

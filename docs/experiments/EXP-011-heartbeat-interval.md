# EXP-011: 心跳间隔的检测收益与多会话开销

Date: 2026-09-13
Commit: `317398f66285b058fcf0cb1a80d7fabf9ad15158`
Related: [EXP-010](EXP-010-silent-disconnect.md)、[M6](../MILESTONES.md)

## Question / Hypothesis

EXP-010 验证了两秒探测周期、三秒单次预算能够覆盖所测静默失联，但没有证明需要如此频繁探测。本轮比较两秒与五秒周期，保持三秒预算不变：减少探测能节约多少开销，发现故障会推迟多少？是否已有足够事实支持固定生产默认值？

预期五秒周期减少控制流量和周期工作，但不减少当前实现中每个连接持有的心跳 goroutine。静默失联需要等到下一次探测，较长周期会延后恢复触发；端到端恢复尚无协议实现，所以本轮只测检测，并将音频积压及追赶作为明确假设下的解析估算。

## Setup

### 检测对照

复用 EXP-010 的生产 Gateway、gRPC/bufconn Worker 和 loopback TCP 双向转发器。每组先完成 Start、一块音频的处理确认与回显、双方一次正常 Ping；故障前不再有未确认音频，避免三秒处理期限混淆心跳检测。客户端和 Gateway 均持续 Read，候选仍是测试侧独立 watchdog，生产协议与配置不变。

分别比较周期 2,000 / 5,000 ms，单次 Ping 写入与等待 Pong 的预算都为 3,000 ms。六场景各两种周期，各两轮：

- 双向阻断，分别在探测开始后约 200 ms 与 1,200 ms 注入；两候选使用相同绝对故障相位。
- 只阻断上行或下行，均约 200 ms 注入；未阻断方向仍可传输。
- 双向暂停 500 ms；各在本候选首次周期 Ping 前 200 ms 开始，确保两种周期的探测都真正命中暂停窗口。因此暂停组的绝对注入时刻不同，分别约 1.8 / 4.8 秒。
- 音频确认后的正常空闲；不能把无新音频或文字判为失联。

故障组在注入后观察九秒；正常空闲组观察十一秒，暂停组恢复转发后再观察十一秒，保证五秒周期的健康对照至少有两次成功探测。观察快照先于 End/兜底 Abort，未检测不填零，保留失败与误判。转发暂停保留字节顺序，不等同于真实丢包、重传或半开 socket 的精确模型。

### 开销对照

通过直接 loopback TCP 接入生产 Gateway，维持 64 或 256 个 Session 与实际 gRPC/bufconn 空闲 RPC。三组分别不启用周期心跳、双端每两秒探测、双端每五秒探测，各两轮。它们都先完成同样的连接建立、Start 和一次双端 Ping；**不发送音频**，这些并发数不是 ASR 稳定容量。

每组准备好全部会话并执行一次 GC 后，统一开放探测启动屏障，测量二十一秒。观察窗刻意不结束在 2/5 秒的共同 tick 上，正常结束仍采用停止后续探测、等待在途探测完成、再发 End 的方式。连接建立和关闭握手不计入开销窗口。

测量包含整个测试进程中的客户端、Gateway、Mock、共享 gRPC 及观测器：

- `getrusage` 的用户与系统 CPU 时间差，除以实际观察时长得到平均占用核数；不是 Gateway 单独的 CPU。
- Gateway WS 底层连接实际 Read/Write 的字节差，包括控制帧及客户端掩码，不包括 TCP/IP 头、重传或 TLS 开销。
- 成功 Ping 数、提前退出和探测失败、观察结束时登记/预留/活动 RPC 数。
- 启动心跳前与观察结束的 goroutine 数、堆、总分配字节差和 GC 次数。没有堆峰值采样，也不把进程堆除以连接数当作生产单会话上界。

各端尽量同时启动探测，形成可复现的周期突发；不模拟随机分散的部署相位。两轮采用固定运行顺序，无心跳→两秒→五秒，样本少，保留范围，不报告统计显著性。所有正式组顺序运行，关闭 race，避免检测与开销负载互相争用。环境为 Go 1.26.5、macOS 26.6.2 arm64、十二逻辑 CPU，详见元数据。

## Metrics / Acceptance

检测结果单独报告双方自己的心跳失败时刻、协调者失败判定、RPC cancellation 和清理。两秒候选按五秒、五秒候选按八秒检测目标评估，这些是实验目标，不是任意环境的硬上界。健康和暂停样本报告是否提前退出。

开销组保留实际完成数、探测失败、提前退出及窗口结束的占用，不能用清理后成功重新建流覆盖失败。所有组最后检查登记、预留和活动 RPC 归零，等待各自 I/O 执行流退出。

汇总校验原始数据 SHA-256、源码与记录提交、仅观察协调者结果的 overlay、重复次数和观察窗口。沿用子测试墙钟跨度与 Go elapsed 相差超过一秒则拒绝性能汇总的规则。race 和更小连接数/窗口的工具检查不作为正式样本；不以 Go 测试通过代替检测或开销验收。

## Results

开销组共十二个正式样本，全部会话在观察窗口结束时仍保持接入，正常 End 后完成并释放；合计 1,920 个空闲会话，无提前退出或探测失败。下面为两轮范围，KB/MB 按十进制表示：

| 会话数 | 周期 | 测试进程平均 CPU（核） | WS 控制流量（KB/s） | 总分配速率（MB/s） | 增加的心跳 goroutine |
| --- | --- | ---: | ---: | ---: | ---: |
| 64 | 不启用 | 0.00002–0.00003 | 0 | 低于 0.0001 | 0 |
| 64 | 2 秒 | 0.0039–0.0045 | 0.634 | 0.240–0.245 | 128 |
| 64 | 5 秒 | 0.0023–0.0027 | 0.244 | 0.099–0.102 | 128 |
| 256 | 不启用 | 0.00002–0.00004 | 0 | 低于 0.0001 | 0 |
| 256 | 2 秒 | 0.0214–0.0232 | 2.536 | 0.967–0.980 | 512 |
| 256 | 5 秒 | 0.0069–0.0101 | 0.975 | 0.398–0.399 | 512 |

每端每会话在二十一秒窗口内，两秒组完成十次周期 Ping，五秒组四次，因此五秒组的成功探测数减少 60%。字节数减少约 61.5%，不是严格 60%：两秒组末尾的 Ping 序号已达到两位数，控制帧 payload 略大。实际头部开销还取决于客户端掩码；此处不包含 TCP/IP 和 TLS。

256 会话下，两轮对应的 CPU 节省约 0.011–0.016 核。两秒组平均使用约一个 CPU 核的 2.1%–2.3%，因此节省真实存在，但本轮没有显示两秒心跳已形成容量瓶颈。更改间隔没有减少持有的 goroutine 数；表中的两个端点都在测试进程中，Gateway 自身每会话只有一个心跳执行流。

总分配速率描述分配周转，不是常驻内存。256 会话两秒组各触发一次 GC，五秒组没有 GC；结束采样的 HeapAlloc 反而是五秒组更高（约 28.9–29.0 MB，对照两秒组约 22.1–24.9 MB）。这不能解释成五秒频率造成泄漏，也不能只取某时刻的堆推断内存优化。固定顺序、小样本和整个进程的观测边界同样限制 CPU 差值的推广。

检测组共二十四个正式样本。下表为双方自身的心跳失败时刻，范围合并双方及两轮，按毫秒取近似值；它不是 RTT 百分位。

| 场景 | 2 秒间隔 | 5 秒间隔 |
| --- | ---: | ---: |
| 双向阻断，200 ms 相位 | 约 4,801–4,802 ms | 约 7,800 ms |
| 双向阻断，1,200 ms 相位 | 约 3,801–3,802 ms | 约 6,800–6,801 ms |
| 单向上行阻断 | 约 4,800–4,801 ms | 约 7,800–7,801 ms |
| 单向下行阻断 | 约 4,801 ms | 约 7,801 ms |
| 暂停 500 ms | 两次均继续正常运行 | 两次均继续正常运行 |
| 已确认音频后的健康空闲 | 两次均正常保持连接 | 两次均正常保持连接 |

十六个故障样本均在各自五秒/八秒目标内由双方探测到，并在兜底前取消 RPC、退出 Worker、归还名额。八个健康/暂停样本没有提前退出，End 后正常完成；暂停组的两种候选都实际经过了被阻断的方向。相同绝对故障相位下，五秒间隔比两秒间隔晚约三秒发现故障。

两批合计三十六个正式样本，通过源码、overlay、原始数据、记账、清理和时间连续性校验，无样本排除。完整原始日志保留。五秒候选的双向故障与暂停 race、小规模八会话三档开销 race、常规带实验标签的全量 race 与 vet 已通过；旧 EXP-010 的历史汇总可原样重新生成。小规模和 race 检查不混入正式结果。

## Recovery Interpretation: 测得检测，不冒充恢复

本轮故障实验没有持续采集音频、建立替代 RPC、重放或合并文字。汇总中的音频量和追赶时间只是以下模型：旧链路失效后持续产生 32,000 B/s PCM；在发现故障时即可建立可用替代连接、立即获得名额，没有更早的积压；假设全部故障期间音频需要补齐，处理速度恒为实时输入速度的 `v` 倍。

若检测用了 `D` 秒，则检测期间新产生的音频体积为 `32,000 × D` 字节。在继续接收实时输入的同时，净追赶速度为 `v−1`，理想追赶时间为 `D / (v−1)` 秒。它是检测之后的时间；`v≤1` 时模型不能追上。汇总列出的 1.2/1.5/2 倍都不是实测 ASR 速度。

以 200 ms 相位的约 4.8 / 7.8 秒检测为例：

| 解析估算，非实测恢复 | 2 秒间隔 | 5 秒间隔 |
| --- | ---: | ---: |
| 检测等待期间产生的 PCM | 约 153.6 KB | 约 249.6 KB |
| 假设处理速度 1.2 倍，检测后追赶 | 约 24 秒 | 约 39 秒 |
| 假设处理速度 1.5 倍，检测后追赶 | 约 9.6 秒 | 约 15.6 秒 |
| 假设处理速度 2 倍，检测后追赶 | 约 4.8 秒 | 约 7.8 秒 |

增加的三秒检测等待对应约 96 KB 新音频。缓存能够容纳这部分数据，并不意味着它能在十秒恢复预算内被补齐；例如 1.5 倍速度的理想情景中，两秒档勉强落在十秒内，五秒档超过十秒。反过来，即使选择两秒档，实际重连、退避和重放上下文也可能使恢复超时。不能把这张表当成某个真实 Worker 的恢复能力。

这可以说明推迟检测如何增加待补音频，却不能证明真实恢复改善了多少。实际还需考虑录音及发送行为、网络何时恢复、重连与退避、容量拒绝、未最终确认的结果、上下文重放和音频丢失边界。三秒处理期限从 Gateway 接纳音频开始，不覆盖尚在客户端缓存中的历史等待，也不能代替整个恢复预算。

## Conclusion / Boundaries

两秒不是唯一可行周期。五秒周期在本轮所测故障中满足八秒检测目标，并减少控制帧、CPU 和分配周转；两秒周期则在相同故障相位下早约三秒发现失联。当前证据既不支持“心跳开销为零”，也没有显示两秒心跳已经成为本机 256 空闲会话的容量瓶颈。

若继续要求五秒检测，应保留两秒档；若业务接受八秒检测，五秒档是有实测依据的节约候选。最终取舍需要结合恢复预算和可用追赶能力，不能仅按探测次数减少百分比或几次零误判样本决定。当前倾向保留两秒作为优先验证较快恢复的实验初值，同时让间隔可配置、保留五秒对照；这不是已确认的生产默认值。

本轮只覆盖空闲控制链路、小样本短时故障、同进程客户端与 Gateway。没有测量持续音频/大量结果写入时的控制帧竞争、生产 Gateway 独立 CPU、随机相位、大规模心跳突发、WAN/TLS/真实丢包或端到端补齐。生产接入还需解决 EXP-010 已记录的探测启停与正常关闭竞争，不能直接搬用实验 watchdog。

生产心跳方案与参数尚未确认，本实验不写最终 ADR、不实现恢复协议。下一步在对话中确认检测目标与可配置周期的取舍，再记录最终决策、实现并验证；十五秒缓存和十秒恢复预算仍需后续真实重放实验。

# EXP-013: 有限恢复的结果边界、缓存与接入约束

Date: 2026-09-13
Commit: `b8f727c1e077ee28c72bf0ec6bd6186ac419e14a`
Related: [M6](../MILESTONES.md), [处理进度语义](../adr/ADR-003-processing-progress-deadline.md), [预留生命周期](../adr/ADR-005-worker-reservation-lifecycle.md), [心跳](../adr/ADR-008-websocket-heartbeat-lifecycle.md)

## Question / Hypothesis

客户端存活、旧识别尝试结束后，按处理进度释放音频是否会丢掉尚未应用的结果？按客户端已应用的安全断点重放，配合尝试隔离和重复事件处理，能否避免这组反例？缓存不再推进、旧会话尚未清理时，恢复是否会显式失败？

预期处理进度不等于恢复断点。候选依赖 Worker 提供不可变结果、连续音频覆盖范围及独立重启能力；这些能力在本实验中由 Mock 明确提供，不是根据真实语音推断出来的。本轮验证候选条件与失败边界，不确认最终协议、不修改生产恢复逻辑。

## Setup / Evidence Boundary

- 协议试验：真实 gRPC/bufconn 连接，测试专用 Worker 与单线程客户端状态模型。每块 3,200 B 合成 PCM 带全局编号，代表 100 ms 音频；实际发送不按实时节奏等待。每个 RPC 的 `audio_seq` 从 1 开始；Worker 核对编号、字节完整性及顺序。
- Mock 每五块返回一个包含结果、覆盖范围及可重启声明的事件；静音可以返回空文字的覆盖事件。它能够独立处理每个编号块，因而不需要恢复隐藏状态。该契约不代表真实 ASR 能每 500 ms 提供安全断点，也不说明重启后的识别质量。
- 处理进度和结果分别经 gRPC 返回。故障在结果解码后、应用到客户端状态前丢弃事件；迟到/重复结果由测试重新投递。旧 RPC 显式取消，等 Worker 退出后才建新 RPC。这是应用交付边界故障，未模拟 TCP 丢包、WebSocket 重连或实例进程退出。
- 候选把完整事件校验、保存结果、推进断点视为一个客户端应用事务。仅比较单个逻辑会话；未实现磁盘持久化、并发录音、UI、跨会话隔离、上下文重放或跨边界文字裁剪。
- 内部试验信封编码在 protobuf 的 Text 字段中，只在测试 Worker 与测试客户端之间使用。生产 Gateway 不理解此信封，它不是已选定的线协议。
- 接入试验单独使用生产 Gateway/WorkerPool、WebSocket/bufconn 和真实 gRPC Mock。旧受控 Recv 收到取消后，仍等测试释放信号才返回，验证旧清理占用。重试共用一次 500 ms Context；这是缩短的正确性预算，不验证候选十秒恢复预算。新接入成功后发送短音频并验证 final/1000。
- 环境为 Go 1.26.5、darwin/arm64、12 逻辑 CPU，正式样本开启 race。精确环境、命令与全部相关源码哈希见元数据。

## Results

十三种场景/策略组合各运行三轮，共三十九个样本。驱动和清理校验全部通过，二十四个样本满足其转录/恢复成功条件，十五个保留为预期的语义失败；无排除。源码与记录 Commit、原始数据哈希、场景计数及结果断言均通过校验。Go test 通过表示反例被按预期观察到，不表示所有候选恢复成功。

| 场景 | 对照 | 安全断点候选 / 约束结果 |
| --- | --- | --- |
| 已处理至 10，结果只应用至 5，丢弃 6–10 的结果 | 按处理水位释放后从 11 重放；三轮各缺失 5 块对应结果 | 保留 6–10，从 6 重放到 15；三轮无缺失/重复 |
| 结果已经应用至 10 后故障 | 两种策略均从 11 开始 | 两种策略各三轮均无缺失/重复；不能把上一场景简化为“所有重连都要重放已提交前缀” |
| 新尝试完成后交付旧尝试 6–10 的结果 | 不区分来源直接追加，每轮重复 5 块结果 | 每轮忽略一个旧尝试事件，无缺失/重复 |
| 新尝试结果重复交付 | 直接追加，每轮重复 10 块结果 | 每轮忽略两个已覆盖事件，无缺失/重复 |
| 全程无安全断点，也没有断网 | 不设置静默淘汰对照 | 第 151 块触发显式缓存不足；保留 150 块、峰值 480,000 B，断点仍为 0 |
| 20 秒编号静音，每五块提供安全覆盖事件 | 不需要生成虚构文字 | 三轮均覆盖至 200，缓存最终为空，峰值 16,000 B |
| 缺少重启能力、缺少结果、前缀有洞的事件 | — | 每轮拒绝三种事件，结果、断点和已有音频均未被修改 |
| 旧 RPC 已取消但 Recv 清理未结束 | 新尝试被 HTTP 503 拒绝，不额外建 RPC | 释放旧执行流后才可接入；三轮新尝试均正常完成 |
| 旧清理持续超过整个恢复预算 | 每轮十次 503，重试不刷新 500 ms 总预算 | 明确预算耗尽，不建立替代 RPC；之后由测试解除旧清理阻塞 |

所有协议试验的活动 Worker RPC 最终归零；接入组最终登记与预留归零。旧清理的解除是注入动作，不计为自动恢复。在缓存不足时，`unresolved_from=1` 表示还没有对应已提交结果的前缀，不表示前十五秒 PCM 已经全部丢失；实验仍保留它们，第 151 块未能进入缓存。此处显式结束试验，尚未选择实际产品在缓存耗尽后继续录音、标记缺口或重启的策略。

全量带 `tide_disconnect tide_load tide_tcp tide_recovery` 标签的 race 与 vet 检查另行通过；开发编译修正与 smoke 检查不作为正式样本，也不混入上述三十九次统计。

## Conclusion / Next Decision

反例支持将处理水位和客户端安全断点分开：处理确认不足以授权释放恢复音频；客户端已经应用的不可变结果不应因重连被盲目重复追加。尝试身份与重复事件处理分别约束旧尝试迟到和同一尝试重复交付，二者不能互相替代。

安全断点候选解决了所测交付反例，但它有实际前提：Worker 必须提供可信的结果覆盖范围与重启能力，且断点推进频率需要与有限缓存相容。全程无断点的正常连接也会耗尽缓存；不能只在断网时考虑这个边界。静音覆盖声明同样必须来自 Worker 契约，不能由客户端根据没有文字自行推断。

M5 的容量保护继续生效：旧会话尚未清理时，新尝试可以被拒绝；恢复预算必须包含这种失败及重试。试验没有证明新连接必定能在十秒内接入，更未测量追赶速度。

下一步需在对话中确认：是否将安全断点能力列为可恢复 Worker 的必要接口条件，以及没有断点/预算耗尽时如何标记未完成范围并继续业务。确认后再记录最终恢复 ADR。真实模型的分段、上下文依赖、边界词质量，以及连续录音与有限时间内追赶，仍须后续独立验证。

# EXP-004-11：未确认音频预算关闭/启用对照

日期：2026-09-25。阶段：第四阶段，积压预算已接入并通过功能验收。

## 问题与实验前假设

[原基线 EXP-004-10](progress-backlog-baseline.md) 表明：持续降速时，单次 Send 尚未超时，网关仍可能积压数秒音频，并在客户端结束输入后继续等待约 10 秒。新增预算要解决的是“是否还允许继续投入未确认音频”，不会提高 Worker 的处理速度。

实验前假设：32000 字节预算足以容纳本实验的正常波动和一次 500ms 暂停；持续降速则因超过预算明确结束，清理后可重新接入。前两者需正常完成，后者的业务结果是失败，只有原因、拦截和清理符合约定时才算实验验证通过。

## 设计与取舍

采用当前同一份源码、同批关闭与启用预算的对照，历史基线只作参照。直接与旧测量比较更省时间，但会混入版本和环境差异。每轮依次运行正常关闭/启用、暂停关闭/启用、降速关闭/启用，共三轮、18 个主会话。顺序固定，未随机化，因此不能完全排除时间顺序或机器后台负载的影响。

保留应用原来的直接转发和期限，预算分别为 0（关闭）、32000 字节（当前 PCM 格式下 1 秒音频）。不增加队列、不改变模型速度，也不通过放宽已有期限来促成预期结果。1 秒音频量并非 1 秒实际等待时间；该预算是实验候选值，不是生产 SLA。

测量使用测试接入壳暴露 session 计量器并执行生产 `session.run`，和此前基线的方式一致；主测量没有直接调用 `Gateway.ServeHTTP`。每个主会话之后，通过同一个 Gateway 的真实 `ServeHTTP` 完成一个短会话，验证名额可复用。该短会话独立于主测量，不计入 100 块负载或主会话时间。

## 条件与指标口径

- 一个会话、一个 Mock Worker，Client/Gateway/Worker 同进程，WebSocket 与 gRPC 均使用本机 TCP。合成音频用于验证顺序和字节数，不代表临床识别质量。
- 主会话计划发送 100 块，每块 3200 字节，每 100ms 一块，16kHz/单声道/16-bit PCM，共 10 秒音频。第 0 块计划在起点发送，第 99 块在 9.9 秒发送，之后写 end。收到服务端关闭即停止继续上传，因此失败会话可能只发送部分输入。
- 正常处理 50ms/块；暂停场景同样 50ms/块，在第 20 块及对应文本后暂停一次 500ms；降速为 200ms/块。ResponseDelay=0，每 500ms 音频一条 partial，完整输入产生 20 条 partial 和一条 final。
- Gateway：MaxSessions=1，消息上限 1MiB，start 10s、input idle 30s、Send 2s、tail 15s、result write 2s。45s 是单用例实验兜底，不作为业务能力。
- 正式运行不带 race；此前单独完成全量 race 回归、快速完成/失败夹具探针和六个完整场景的 race 验证。

| 指标 | 含义与限制 |
| --- | --- |
| 客户端写出量 | WebSocket Write 成功返回的完整块字节数，不代表网关已读取 |
| 网关读取量 | 会话 addReceived 已记录的字节数，包含触发超限但未发送的块 |
| 网关放行量 | gRPC Send 成功返回的字节数，不代表 Worker 已经读取或处理 |
| Worker 接收量 | Mock 调用 Recv 实际收到、通过内容与顺序校验的字节数 |
| Worker 进度发送量 | Mock 完成模拟处理并成功发送的累计确认，未保证网关收到 |
| 网关确认量 | download 已接收并登记的累计处理量 |
| 未确认量观测峰值 | 每 5ms 尝试采样 received−processed 的最大值；可能漏峰，实际采样间隔另存 |
| 触发判断的未确认量 | 从保留的超限错误中提取当次比较值；有精确数量，没有判断时刻的精确时间戳 |
| 尾部等待 | 客户端开始写 end 至收到 final；超限失败没有这个指标，不填 0 |
| 退出时刻 | 相对客户端 start Write 返回后的统一起点，分别记录客户端关闭、run 返回、handler 返回、Worker 方法返回 |
| 清理与复用 | handler 返回后检查名额为 0；应用未取消，再次建立短会话并正常完成 |

采样调用的起止时间包括调度和锁等待，不是纯锁耗时。音频未确认量也不是物理队列长度、整个链路全部缓冲或进程内存。

## 实测结果

18 个主会话全部通过预先约定的行为校验，其中 **15 次业务正常完成、3 次业务超限失败**。每次 handler 返回后活跃会话为 0，未通过取消应用帮助退出；随后额外的 18 个短会话均正常完成并清理。正常完成的每个主会话均收到完整 100 块、20 条 partial 和一条 final；超限会话均只返回一条 partial，没有整场 final。

以下范围为同一配置三次测量的最小值至最大值，不是百分位数或统计显著性结论。

| 场景 | 预算 | 业务结果 | 未确认量观测峰值 | 客户端 end 至 final |
| --- | --- | --- | ---: | ---: |
| 正常 50ms/块 | 关闭 | 3/3 完成 | 3200 字节 / 0.1s 音频 | 51.03–53.92ms |
| 正常 50ms/块 | 32000 字节 | 3/3 完成 | 3200 字节 / 0.1s 音频 | 50.80–51.43ms |
| 暂停 500ms | 关闭 | 3/3 完成 | 16000 字节 / 0.5s 音频 | 50.77–51.84ms |
| 暂停 500ms | 32000 字节 | 3/3 完成 | 16000 字节 / 0.5s 音频 | 50.71–51.07ms |
| 持续降速 200ms/块 | 关闭 | 3/3 完成 | 137600 字节 / 4.3s 音频 | 10.141–10.152s |
| 持续降速 200ms/块 | 32000 字节 | 3/3 积压超限失败 | 35200 字节 / 1.1s 音频 | 无 end、无 final，不适用 |

正常与短暂停顿的六次启用保护测量均未中断，尾部仍在约 51ms 的量级。本组数据未显示明显尾部退化，但仅三次重复，不能据此宣称零开销或推理提速。暂停期间中间结果仍可能落后：暂停启用组三次运行的最大 partial 等待为 303.09–305.42ms，因此尾部约 51ms 不表示全程所有文本都只等待约 51ms。

持续降速关闭保护时，每次最大 Send 为 1.203–1.204s，仍未触发 2s 发送期限；尾部等待也低于 15s 期限。启用后，三次均保留 `audio backlog exceeded (35200 > 32000)`，客户端收到 1011 / `audio backlog exceeded`，Worker 因 RPC 取消退出。对应 handler 在输入起点后 **1.8013–1.8023s** 返回并释放名额。这个时间是整段输入开始至清理完成，不是“检测到超限后清理用了 1.8 秒”；实验没有在判断点采集时间戳，不给出精确的检测至清理时延。

### 为什么是 1.1 秒，而不是恰好 1 秒

预算限制的是是否继续放行音频。上传先完整读取一块并记账，再判断是否超过预算，所以触发失败的最后一块仍在 received 中，但不会被发送。

三次超限的数量均一致：

| 观测点 | 音频量 | 当前格式下的音频时长 |
| --- | ---: | ---: |
| 客户端成功写出、网关已读取 | 19 块 / 60800 字节 | 1.9s |
| 网关 Send 成功返回 | 18 块 / 57600 字节 | 1.8s |
| Worker 实际读取 | 9 块 / 28800 字节 | 0.9s |
| Worker 成功发出、网关已登记的处理确认 | 8 块 / 25600 字节 | 0.8s |
| 网关未确认量（60800 − 25600） | 35200 字节 | 1.1s |
| 已读取但未放行的最后一块 | 3200 字节 | 0.1s |

判断时的 35200 字节来自原始错误中保存的比较值；采样观测峰值也恰好是 35200 字节。严格边界仍由读取/计量/判断/发送顺序与边界测试支撑，而非依赖采样捕获每个瞬间。改变单块大小，会改变允许出现的这一个块的超出量。

关闭会话不会把未处理音频自动补成完整转录；最终账目仍有 35200 字节未确认，是失败时保留的事实，不是应该回滚的计数。已经由 gRPC Send 接受、但未被 Worker 处理的音频同样没有完整识别结果。

### 验证与测量限制

- 全量 race 回归通过，包含两个快速夹具探针（完成、首块即超限）；六个完整场景另一次 race 验证通过。正式 18 次测量不带 race，Go 测试运行共 187.483s，这个数仅为实验执行时间。
- 原始日志与两份 CSV 核对：18 行主会话数据、37023 条计量采样，成功/失败原因和计数一致。测量源码在运行前后 SHA-256 一致；后处理脚本曾修正 CSV 表头以保留失败行独有的错误字段，原始数据与测量代码未改变，manifest 记录了该脚本变更。
- 5ms 目标周期的实际最大样本间隔为 **11.95ms**；snapshot 前后时间差最大 **1.24ms**，包含调度开销。周期采样可能漏峰。
- 当前 Go 为 1.26.5、macOS 26.6.2；Python 观察到 12 个逻辑 CPU。硬件型号和内存沿用历史 manifest 的 M2 Pro / 32GiB 记录，本次 sandbox 未允许 sysctl 硬件读取，未把历史信息描述为本次实测。
- 仅单会话、本机 TCP、固定块大小、可控 Mock、有限时长；没有测量总内存、稳定并发容量、弱网恢复、真实 ASR 质量或生产环境延迟。

## Result 与反思

可据此写入第四阶段 Result：在相同代码与输入条件下完成三场景、两配置、各三次的 18 次对照。启用 1 秒音频预算后，正常和 500ms 暂停场景 6/6 完整转录；持续降速场景由关闭保护时 4.3 秒音频的积压观测峰值，转为 3/3 在 1.1 秒未确认音频处明确超限失败，触发块均未继续发送。全部 18 次清理后名额归零，额外 18 次正常会话复用成功。

这项改进补上了“Send 仍能成功，但处理已经落后”的控制缺口。代价是超限会话不能完成原定 10 秒音频的转录；因此它属于积压保护，不能把更早失败换算为识别提速、完整转录延迟下降或系统吞吐提升。

下一步应先收拢第四阶段已验证的控制范围与仍未证明的范围，特别是本地已读音频预算与全链路缓冲/内存的区别。是否需要有界应用队列，要根据具体等待与内存证据决定；当前实验不提供必须加队列的依据。多 Worker 调度与稳定容量仍属于第五阶段。

# EXP-005-09：双 Worker 19 并发细测

状态：方案和判据于测量前固定，正式数据待执行。

## 目标与选点依据

[EXP-005-08](dual-worker-sweep.md) 已测得双 Worker 18 并发三批达标、20 并发三批未达标。因此按上一轮事先声明的规则，测试中间的 19 并发，而不将 18 直接写成容量上限。

问题是：19 是否在三次重复中满足相同的全部完成、尾部延迟和发送排期标准？如果未达标，具体是完成率、尾部还是发送节奏，以及各实例等待与批次清理表现如何？

## 方案与权衡

- 只细测 19、每场 20 秒、三批：以较小成本缩小已测范围，本轮采用；短时结果仍需延长观察。
- 将 18/19/20 一起重测：可增加同轮对照，但前一轮已经完整测量了 18/20，成本从约两分钟升到六分钟。本轮保存来源并校验同一 Go 实现、配置和环境，时间顺序变化仍是限制。
- 直接测试 19 两分钟：可以更早观察累积影响，但尚不知道 19 是否适合作为重复达标候选。先筛查，再为较高达标点设计长时实验。

19 是奇数；在同质会话、轮询每场只选择一次的条件下，选择规则预期两实例承担 10/9 场。当前负载工具没有逐 Worker 会话分配计数，不能把这一预期写成实测均衡或精确分配量。它提示我们总体多一个会话可能使其中一个实例更接近单 Worker 10 场的负载水平，实际影响仍由结果判断。

## 固定计划

| 项目 | 条件 |
| --- | --- |
| Worker / Gateway | 两个同配置 Worker，各一个处理名额、逐块 10ms；round robin；pending audio=32000 字节；其他参数沿用 EXP-005-08 |
| 输入 | 每场 20 秒静音 PCM，32000 字节/秒、3200 字节/块、实时排期；共 640000 字节、200 块 |
| 正式批次 | 19 并发，固定三批，共 57 次正式尝试；不按结果追加重测 |
| 预热 | 两场各两秒，不进入正式结果 |
| 期限 | 每场 35 秒；负载进程额外收尾 10 秒 |
| 采样 | Gateway 100ms、两个 Worker 各 20ms；完成查询后再等间隔；查询期限 1 秒；正式 40 秒、预热 10 秒 |
| 业务判据 | 全部完成且无批次错误；成功会话 nearest-rank 尾部 p95 ≤ 250ms；所有尝试有排期样本，最大发送落后 ≤ 100ms |
| 证据判据 | 各来源负载前后空闲、窗口内无查询失败、最大覆盖间隔 ≤ 500ms；身份、配置、计数、哈希和正常收尾一致 |

沿用此前工程筛查标准。采样通过与负载达标分别报告，失败保留在完成率分母中；尾部只含成功会话，必须同时展示失败量。各 Worker 峰值异步，分别记录；等待计数不作为等待耗时或音频积压量。

## 来源与实现

入口 [run_dual_worker_boundary.py](scripts/run_dual_worker_boundary.py) 先读取已完成的 16/18/20 原始证据，在临时副本重新分析，核对清单和分组哈希，再确认三档达标次数为 3/3/0。记录来源路径、提交、源文件和产物哈希以及原分组，历史文件不重写。

通过共享编排执行三批；在构建与网络请求前核对当前 Go/Proto/模块文件哈希与来源一致，发现变更则保留失败清单并停止。复用现有多实例采样、回收和分析，不修改 Go 业务代码。分析时再次检查选点规则及源文件一致。

新增 [六个测试方法](scripts/test_dual_worker_boundary.py)，涵盖固定档位、两 Worker、缺批/改档、选点依据不一致、来源和原始文件篡改、源代码变更前置拒绝、历史复算兼容；共 58 个分析测试通过。

预计约两分钟。使用 `caffeinate -i` 临时防止自动空闲休眠；覆盖检查决定证据是否有效。无效或中断尝试单独保留，完整复测使用新目录，不拼接好批次。

## 结果解读与后续规则

- 三批均达标：19 成为最高已测重复达标点，下一步优先延长 19 的观察。
- 三批均未达标：维持 18 为最高已测重复达标点，下一步优先延长 18。
- 部分批次达标：报告 19 的波动；维持 18 为重复达标候选，不将 19 纳入稳定参考点。
- 采集不合格：不据此判断性能边界，保留尝试并安排完整复测。

选择较高重复达标点做两分钟观察时，还可加入 16 作为较低负载对照；具体批次数和判据在下一轮开始前固定。短时三次达标或两分钟筛查都不替代长时稳定性和真实 ASR 测量。

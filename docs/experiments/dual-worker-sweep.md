# EXP-005-08：双 Worker 逐级加压

状态：已完成。方案、判据与工具在测量前提交为 `69309cc`；正式九批全部保留，采集校验通过。

## 为什么继续加压

EXP-005-07 中，双 Worker 的 8/9/10 场各三批均达标，只证明这些单 Worker 参考点得到改善。要评估扩容后的负载边界，需要继续提高并发，观察未完成、尾部延迟和发送排期的变化，并用各 Worker 等待状态辅助定位。

本轮以 16/18/20 场作短时初筛，分别对应单 Worker 参考点 8/9/10 的两倍。这是候选档位的选择依据，不是假定容量翻倍。当前 Mock 用受控等待模拟处理，同主机多一个进程与多一个名额，不等于多一台机器或真实 ASR 推理资源翻倍。

## 方案与权衡

- 逐个测试所有场数：边界更细，但重复测量成本更高。
- 先用三个档位包围变化区间：每档三批，能较快发现达标、波动和明显未达标。本轮采用，随后按结果细化。
- 直接进行长时测试：更贴近长问诊，但未确定运行点时可能花大量时间观察明显过载。先用 20 秒筛查，延长观察留下一步。
- 同时改变缓冲或调度策略：难以解释变化来源。本轮保持既有 round robin、每实例处理配置和阈值。

本轮只包含固定九批，不自动追加“直到通过”的重测。采集失效或中断时保留尝试，完整复测使用新目录。业务未达标属于结果，不作为丢弃证据的理由。

## 需要回答的问题

1. 16/18/20 哪些档位连续三批满足当前判据？哪些出现部分达标或三批均未达标？
2. 首先观察到的恶化是完整完成率、成功尾部延迟还是发送排期？逐项记录，不用成功尾部掩盖提前失败。
3. 每个 Worker 的处理占用和等待如何变化？失败后 Gateway 活动会话是否下降，所有实例是否回到空闲？
4. 与上轮双 Worker 8/9/10 相比，提高负载后的变化是否与各实例争用一致？

没有逐块音频处理确认、排队耗时、总内存或 CPU 采样，现有观测只能给出有限证据，不把等待计数叫作队列时延。各 Worker 查询异步，分别报告峰值；不相加当作系统同时峰值，也不根据快照推断精确会话分配比例。

## 下一步的选择规则

先报告各档三批的全部结果，再决定下一轮计划：

- 16/18 三批达标而 20 三批未达标：优先细测 19 场。
- 16 三批达标而 18 三批未达标：优先细测 17 场。
- 某档仅部分轮次达标：单独报告波动，不将其当成稳定达标点。
- 全部达标：只说明最高已测档位 20 达标，需要测试更高档位。
- 全部未达标：向 10–16 之间回查，不宣称 16 是边界。
- 出现非单调结果：保留结果和环境信息，不按容量必然单调的假设重排或删掉批次。

细化后再选择可重复达标的较高运行点延长至两分钟。两分钟也仅是长时稳定性筛查，不能视为生产容量保证。

五秒分段中，20 并发三批在前十秒均采到 20 个活动会话；10–15 秒出现下降，15–20 秒的大多数有效样本为 16 个活动会话，结束附近仍有收尾状态变化。此时各实例等待与原先失败四场后的活动量变化相符；不能将后半程的成功延迟描述成持续承载 20 场的表现。

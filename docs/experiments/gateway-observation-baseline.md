# EXP-005-03：Gateway 活动会话采样基线

Date: 2026-10-01
Status: 已完成九批联合观测基线；未测稳定容量。
Source: 1c67120；本轮未修改 Go 业务代码。
Related: [发送排期基线 EXP-005-02](loadgen-schedule-baseline.md)、[并发负载设计](../worklog/2026-09-28-concurrent-load.md)

## 问题与取舍

客户端计划发起 N 场会话，不等于 Gateway 在任意时刻都有 N 个活动会话。本轮使用已验收的独立采样命令，记录每批负载之前、期间、之后的 Gateway 快照，验证实际观测到的活动量和收尾后的零活动状态，并量化采样覆盖。

选择每批独立固定 10 秒的采样窗口：文件与批次一一对应，按期自然结束符合采样命令的退出契约；代价是每批需要等待观察窗口结束。整轮共用一个长采样进程可以减少启动与等待，但需要划分批次并处理共享窗口中的故障；负载结束后发送 SIGTERM 则会按当前契约退出 1，不能当正常完成处理。本轮采用独立窗口，并等待落盘的有效零活动样本后才启动负载。

这是一轮观测能力基线，不是性能优化 A/B。沿用此前 Worker/Gateway/客户端的负载条件，但新增一个采样进程及批间等待，不能将与旧结果的差异直接归因为优化或采样开销。

## 执行前固定的条件与判据

- 同机四个独立进程：单 Mock Worker、Gateway、loadgen 和 gateway-sampler；正式二进制不启用 race。
- Worker 共享处理名额 1，逐块处理 10ms、文本响应等待 5ms；Gateway 最大会话数 64、未确认音频预算 32000 字节，其余保持上一轮条件。
- 一场 2 秒预热单独保存；正式 1/2/4 场依次执行，重复三轮，共九批、21 场。每场 5 秒静音 PCM、160000 字节、50 块，实时发送，单场超时 20 秒。
- 每批采样完成后等待 100ms 再查询，单次查询期限 1s，整体运行预算 10s。采样就绪等待最多 2s，要求已写出的有效样本为 active=0、max=64、stopping=false；不以进程启动或空文件存在代替就绪。
- 客户端继续采用此前的完整完成、字节/块/结果数、首条结果早于 end、排期样本数及摘要复算检查。
- 采样进程须正常退出 0，样本清单与 JSONL 的序号、分类、计数及配置一致；保留全部失败行和失败批次。
- 每批必须有完全在负载进程启动前结束的有效零活动查询，以及负载进程返回后才开始的有效零活动查询；负载窗口内完整查询的观测峰值应等于计划数 N。峰值未观测到表示此轮检查未满足，不能据此断言真实峰值较低。
- 在上述负载窗口两侧最近的有效样本之间，相邻有效查询完成时间的最大间隔不超过 500ms；负载窗口内没有重叠的失败查询。500ms 是本轮观测覆盖检查条件，不是业务延迟 SLA。采样预算末端、负载已结束后的失败查询仍原样保存，不凭此否定已覆盖的负载窗口。
- 所有成功状态应满足 max=64、stopping=false、active 不超过本批计划数；观察不到的状态记为未知，不补零。
- 仅管理脚本启动的进程；8080 已占用则中止，不接管或停止其他服务。保存源码/脚本/二进制/环境、命令、退出码与全部原始文件哈希。

## 时间与指标口径

负载窗口采用实验脚本启动 loadgen 前和等待其返回后记录的 UTC 时间，覆盖客户端实际执行。快照实际读取时刻位于每条样本的 started_at/finished_at 之间，本轮不虚构精确的服务端取样时间。

观测峰值只统计查询区间完全处于负载窗口内的有效样本。采样覆盖最大间隔用相邻成功查询的 finished_at 计算；这不是固定频率保证，失败查询不会被当成零活动状态。跨进程对齐采用同机墙钟，检测到逆序则拒绝分析；原始查询 duration_ns 仍使用 Go 记录值，不从序列化时间反推。

“首个负载退出后零活动样本延迟”是查询 finished_at 减负载进程返回的时间，包含等待下一次查询及查询耗时；它只说明何时再次观测到零，不等于连接清理精确耗时，不证明整个采样间隙持续为零。

## 本轮结论与下一步

之前只有“客户端启动了 N 场”的输入计划，本轮增加了独立服务端证据：九批均观察到 N 个已接纳且尚未完成清理的会话，并在负载退出后再次观察到零。逐行样本、采样质量、前后窗口和进程退出结果可以相互核对，给后续压力上升时区分“负载没有到达”和“到达后处理变慢”提供了基线。

该结果没有证明 N=4 是容量上限，也未覆盖数十分钟问诊、持续到达负载、多 Worker 容量扩展、等待队列或内存变化。离散样本峰值不是连续最大值，活动会话数也不是 Worker 同时处理数。下一步补 Worker 处理名额的占用/等待观测，再制定逐级加压及容量判据。

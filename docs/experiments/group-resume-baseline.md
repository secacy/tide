# EXP-006-02：共享 Gateway 的群体重连基线

Date: 2026-10-11
Status: 正式五组各三批测量与独立复核完成；15 批证据合格，业务结果保留 94 完成 / 26 失败。
Baseline: 设计核对 `9d9efac`；正式执行时记录包含工具的提交、工作树差异、源码与产物哈希。
Related: [恢复能力与方案选择](../worklog/2026-10-11-group-resume-design.md)、[单会话恢复实验](client-resume-baseline.md)、[Milestones](../MILESTONES.md)

## Goal / Questions

在原 Gateway、原 Worker RPC 均存活时，观察八场问诊同时断线后的有限恢复。先测当前确定性退避，不在本实验中改变重试算法。

1. 逻辑会话已满时，能否各自接回原 RPC，保持音频完整、隔离及结果应用不重复？
2. 减少握手名额后，出现多少拒绝，恢复尝试是否聚集？
3. 入口短时满额并快速拒绝时，先耗尽次数还是时间预算？
4. 多久恢复新采集音频的结果？成功/失败后，原场何时自然清理？

范围是本机、八场共享入口，不用于给出生产容量或真实弱网恢复 SLO。

## Hypothesis

- 无故障组应完整完成；立即可用的恢复入口有机会使全部原场完成，是否发生拒绝需观测。
- 两个握手名额被占用 500ms 后释放，客户端可能在下一轮重试中接回。
- 占用 2s 时，五次默认尝试可能在释放前用完，即使恢复窗口为 5s。
- 确定性退避可能保留请求聚集，也可能被 I/O 和调度分散。jitter 的优势尚未验证。

## Setup

### 共享链路与输入

- 每批一个 Gateway、一个位置 Worker、一个故障代理，八个独立 V2Client Run，共享 Gateway 的 gate、tracker、registry 和 Worker 连接。
- Worker 支持八条并发流，各流每块处理 10ms，不设置跨流共享计算名额；本轮隔离入口竞争，不沿用第五阶段算力瓶颈结论。
- 每场 PCM 16kHz/单声道/16bit，60 块 × 3200 字节 = 192000 字节，固定 100ms 采集节奏。输入由实验编号和位置确定，八场内容不同，逐字核对。
- 用输入中的实验标记关联客户端和 Worker RPC，并验证整场内容。不能假设建流顺序等于客户端启动顺序；不修改生产协议。
- 每块处理后报告进度、携带实验编号/音频终点的结果，EOF 后一条尾部结果；完整场应应用 61 个连续序号。实验标记不是真实 ASR 文本约定。

### 固定预算

- 客户端：Realtime=true，MaxReplayBytes=320000、MaxReplayChunks=128、ReadLimit=65536；HandshakeTimeout=10s、WriteTimeout=5s、ApplyTimeout=5s、CompletionTimeout=30s。
- 恢复始终启用：MaxAttempts=5、Window=5s、InitialBackoff=100ms、MaxBackoff=1s。首次恢复立即尝试，后续确定性退避；各场独立计算预算。
- Gateway：MaxSessions=8、MaxMessageBytes=1048576、WorkerSendTimeout=2s、ResultWriteTimeout=2s、StartTimeout=10s、MaxPendingAudioBytes=0。
- v2：MaxHandshakes 按下表，EntryTimeout=10s、InputProgressTimeout=30s、ResumeWindow=10s、ResultRetentionTimeout=10s、WorkerStatusTimeout=2s；音频/结果字节预算各 1048576，块数/结果数各 256。
- 批次从第一个 Run 启动起最多观察 15s，其中全员 ready 最多等待 10s；所有 Run 返回后另观察自然清理最多 15s。最终兜底取消单独记账。
- 资源采样间隔 10ms，保留实际间隔和错误；尝试到达使用逐事件时间。保存 Go/OS/CPU/GOMAXPROCS、race 状态、起止和睡眠/采样异常。

## Procedure / 故障注入

1. 逐个建立八场，每场 ready 转发且首次 Read 被观察到后再启动下一场；源立即正常提供数据，不在首次 Read 内人为等待。现有采集器在 Read 前确定时间轴，阻塞源再集中放行会造成追赶式采集。记录八场首读时刻，跨度超过 50ms 标记同步输入不合格并保留；启动失败保留在计划分母，不注入不完整群体故障。各场时间轴有少量差异，故障通过下一步的音频位置屏障同步。
2. 代理读到各初始连接第 20 块 `[60800,64000)` 时暂扣，每连接最多持有一块作为屏障；前 19 块照常转发。全员到达后统一操作。A 组经过相同屏障，再放行并正常继续。
3. D/E 切断前用两条测试连接完成真实 Gateway WebSocket 升级，暂不发送首条消息。确认 activeHandshakes=2 且只有八场原 RPC；占位不创建逻辑会话，记录获得名额时刻。
4. B–E 在共同故障触发时刻 T0 并发关闭八条原连接的前后端，不转发暂扣块。记录每条关闭调用和完成时刻；源继续固定时间轴。切断完成跨度超过 50ms 标记同步注入不合格，保留该批而不计合格同步样本。
5. 恢复请求立即转发同一个 Gateway，不像 EXP-006-01 等开放再转发。D/E 到 T0+配置时长后关闭占位连接，记录实际关闭和名额归还；计划值不能代替释放事实。
6. 保留真实拒绝：若前端已升级而后端 Dial 收到 Gateway HTTP 错误，将同一稳定错误码传入前端 v2 error，同时记录原始 HTTP 状态和转发结果。不能将 handshake_limit 全部变成不明断线，也不能伪造拒绝。协议外错误单独分类。
7. 全部业务返回后观察原场和代理任务退出，最后才清理夹具。初始建立失败、超时、业务失败及兜底清理都输出报告。

注入是统一断开加入口占位，不是 TCP 丢包或网络黑洞。屏障暂扣一块会改变部分场的传输节奏，报告实际等待跨度，不称为自然网络故障。只在代理前等待不会占 Gateway 名额；并发数超过名额也不保证拒绝，因为本机握手可能很快。

## Acceptance / 判据

- 工具：核对计划数和原始事件，共享同一 Gate；D/E 确实占满两个名额、实际观察到 handshake_limit、释放事实明确；错误/缺失/超时反例可被发现，失败不丢失。
- 正确性：不串音频/结果、不创建替代 RPC、不将不完整场标为 completed；源关闭一次，自然清理单独检查。不能用平均完成率抵消这些问题。
- 行为：A 应全部完成；B/C/D 预期有机会全完成，失败保留并解释；E 预期观察次数先耗尽。与假设不符先分析，不为符合假设调参。
- 性能：建立当前方案基线，不预设改善百分比或生产时延线。E 业务失败不自动等于工具失败；工具合格与恢复率分别结论。
- 未在独立期限内自然收尾，记录未完成和兜底动作，不以强制取消后的零计数判为自然清理成功。

### 两个已观察到的问题

**快速拒绝会让次数早于窗口耗尽。** E 的实际占位为 2000.66–2001.30ms，但全部 24 场在 T0 后 1513.11–1516.42ms 返回失败，早于 5s 窗口和入口释放。原始 50ms 桶中每轮五波都各有八个请求，落在约 0 / 100 / 300 / 700 / 1500ms；共 120 次真实 HTTP 503 handshake_limit，窗口并未用满。这与当前首次立即、随后 100/200/400/800ms 的等待一致，属于次数预算与快速失败的组合。

**释放后仍存在入口竞争。** D 实际释放时刻为 T0+500.70–500.74ms。三轮的前三波各 24 次请求全部被拒绝；释放后还拒绝 2 / 3 / 6 次，共 11 次。约 700ms 的八场同桶请求分别接回 6 / 5 / 4 场；约 1500ms 的剩余 2 / 3 / 4 场再试，其中第三轮只有两场接回。该轮实验编号 6、8 在约 709ms 和 1512ms 两次可用期仍收到真实拒绝，最终在 1513.85/1513.92ms 用完第五次尝试。D 总完成率为 91.67%，没有用另一轮成功样本替换这两场失败。

这些事件支持进一步比较预算和请求分散策略，但没有证明 jitter 必然提高完成率。50ms 同桶不表示请求精确同时；MaxHandshakes=2 也不是每桶最多接纳两场，名额可在桶内归还复用。

### 失败缺口、清理与数据质量

26 个失败场均只处理前 `[0,60800)` 字节、应用 19 条结果；各场已采集 `[0,112000)`，其中 `[60800,112000)` 共 51200 字节没有恢复到 Worker，后续 `[112000,192000)` 共 80000 字节尚未采集。已采集未处理和未采集分开列出，不能都称为网络丢包。成功恢复场代理各观察到 3200 字节重复音频负载，占每场输入 1.67%；不是 TCP 总重传量。

15 批均在独立期限内自然归零，未停止服务兜底。A/B/C 和前两轮 D 从整批 Run 返回到整批空闲为 0.12–10.46ms；第三轮 D 为 5908.87ms，E 为 8489.26–8492.14ms。按失败场自身 Run 返回计，26 条原失败 RPC 又保留约 8484.30–8489.60ms 才退出，与服务端独立 10s 保留窗口一致；客户端失败不意味着远端名额立即释放。逐场 CSV 的 remote_idle_after_return_ms 使用**整批**空闲时刻，不能当作某个已完成场的精确释放时间。

304 个源码/工具/条件文件测量前后摘要一致，构建、运行、两次独立分析均退出 0。另在新目录解压完整归档，使用快照分析器再核对；reports、summary、sessions CSV 和请求桶 CSV 四类输出逐字节相同。120 场无未知项，15 批无工具或同步判据失败，未复测替换业务样本。

### Think / 后续选择

本轮已经建立事实基线，未测“优化收益”。与 EXP-006-01 的差异是故障期间请求立即被拒绝，而不是一次握手等待开放；单场 2s 中断能完成与本轮 2s 占位全失败不矛盾，不能直接比较为性能退化百分比。

下一步先设计**只改变尝试次数**的预算对照，保持 5s 窗口、确定性退避、共享入口和故障条件不变，观察能否等到开放，以及请求成本、恢复等待和失败后保留代价。增加次数会增加流量，不能直接当作最终方案。随后独立比较 jitter，明确首次是否等待、随机范围、平均等待和种子；不要同时改次数、窗口和 jitter 后无法归因。完整随机退避通常会缩短平均等待，仅靠分散当前五次请求不一定解决 E 的提前用完问题。

本轮仅三批八场、固定顺序、轻负载 Mock 和受控入口占位；真实弱网、长时反复故障、真实 ASR 及生产恢复 SLO 未在此验证。第六阶段继续推进。

# EXP-005-01：有限批次完整链路基线

Date: 2026-09-29
Status: 已完成小规模基线；未测稳定容量。
Source: f5377dd；业务代码不变，新增实验脚本与记录。
Related: [并发负载设计](../designs/2026-09-28-concurrent-load.md)

## 问题与实验前假设

负载命令已经通过受控 WebSocket 对端的验收，本轮连接实际独立进程 Gateway 与 Mock Worker，检查它是否按计划发送音频、在上传期间接收结果，并保存可复算的完整报告。不是新旧方案对照，也不寻找最大稳定容量。

采用单 Worker 固定配置，计划会话数为 1、2、4，各重复三批；每场 5 秒静音 PCM，160000 字节、50 块，每块 3200 字节，Realtime=true，单场超时 20 秒。预期尾部文本为“今天天气不错”。先运行一场 2 秒输入作预热并单独保存，不计入正式统计。

Worker 共享处理名额 1，每块处理延迟 10ms，每条文本响应延迟 5ms；partial 每 500ms 音频触发，现有命令只配置四条 partial，最后再返回一条 final。Gateway 的未确认音频预算显式为 32000 字节，其他默认保护参数及环境记录在 manifest。客户端、Gateway、Worker 同机独立进程，正式二进制不启用 race。

假设：本轮低负载下各场完整完成；第一条结果早于 end 写入，发送跨度接近 4.9 秒（第一块立即发送）；计划数增加时共享处理名额可能增加尾部等待。它是待观测假设，不把名额除以延迟推导的理想吞吐当作实测容量。

## 方案取舍与预定判据

- 真实命令进程验证运行路径；使用同一 Gateway/Worker 完成全部批次，保持服务配置固定。
- 执行顺序为 1、2、4，重复三轮，避免某组全部集中在最早或最晚；不是随机顺序，也没有隔离其他本机负载。
- 比较多 Worker 会同时改变资源量，本轮先固定一个 Worker；故障与过载实验留后续。
- 必须保留所有尝试，预热失败不启动正式测量。正式测量失败也保留原始报告及错误，不只抽取成功结果。
- 正确性判据：进程正常返回；21 场正式会话均完整完成；每场写入 160000 字节/50 块、零写入失败、4 partial + 1 final；第一条结果在 end 前；完成率、音频总量和 nearest-rank 尾部摘要能从原始记录复核。
- 不预设业务 SLA。记录每场发送跨度、最大音频 Write 耗时和尾部延迟，报告观测范围。各组仅 3/6/12 个样本，nearest-rank p95 都会等于该组最大值，不作稳定分布结论。

## 测量含义与缺口

发送跨度为客户端最后成功音频 Write 返回时间减首次成功音频 Write 开始时间；它可以发现整体发送被拖长，不能显示中间每块的排期落后或追赶。

尾部延迟沿用 end Write 开始到最后结果接收的定义，包含最后一块尚未完成的处理及响应等待；它不是逐音频块端到端延迟，也不是整场耗时。

当前进程没有对外暴露活跃会话、Worker 排队/占用、处理字节及内存/goroutine 采样。客户端成功写入不能当作服务端收到或处理的独立计数；最终文本匹配也不是音频内容识别质量证明。本轮只核对已有客户端事实、启动日志、健康检查及进程返回。下一步根据结果补齐缺失观测。

## 复现

确认本机 8080 未被占用。脚本只管理自己创建的进程，不复用或停止其他服务；Worker 自动分配本机端口。

```sh
python3 docs/experiments/scripts/run_loadgen_baseline.py \
  --output /tmp/tide-loadgen-baseline-new
```

输出目录必须不存在。记录代码提交、源文件/二进制/脚本哈希、系统与 Go 信息、命令、全部批次原始 JSON、进程日志与复算结果。Gateway 测后 SIGTERM 正常退出，Mock 测后 SIGTERM 停止；不把整个进程退出视为逐会话资源归零的证据。

## 实测结果

九批共 **21/21 场完整完成，成功写出 3360000 字节、1050 块，收到 84 条 partial 与 21 条 final；21/21 场第一条结果早于 end 写入，写入失败为 0**。所有正式命令退出 0，报告中的完成率、输入总量和尾部分位数复核通过。发送跨度约 4.9 秒符合当前首块立即发送的节奏，不将 5 秒音频误要求为正好 5 秒发送耗时。

正式测量结束后 Gateway 收到 SIGTERM 并退出 0，Mock 在会话结束后被 SIGTERM 停止（退出状态 -15）。这仅记录进程收尾，不能证明每批内部 active/goroutine 已归零。

### 首次预热的计量纠正

首次尝试的预热本身退出 0、会话完整完成，但助手的复核脚本错误地要求“JSON 两个 UTC 时间戳相减”与记录的 TailLatency 逐纳秒一致。前者为 23737000ns，后者为 23736291ns，相差 709ns，导致脚本中止；当时未开始正式九批测量，脚本异常清理停止自有进程。

本地 Go `go doc time` 的 Monotonic Clocks 说明确认：time.Now 的值带单调时钟，Sub 优先使用它；UTC/MarshalJSON 不保留单调读数。因此不能从序列化墙钟戳精确重建单调时长。修正仅发生在实验复核脚本，业务代码、负载条件和正确性目标不变：尾部摘要仍从保存的整数耗时样本精确复算，墙钟差值改作独立诊断值，不再与单调时长作逐纳秒等值断言。

修正后用新目录重新预热并执行正式九批。21 个正式样本的“墙钟尾部差值减记录尾部耗时”为 -625～750ns。两次预热均不计入正式统计。首次原始报告、错误清单与当时脚本全部保留，不能把这个复核脚本错误记作系统会话失败。

## 结论与下一步

本轮证明负载命令能通过实际 Gateway/Mock 进程按给定小批次运行，并保存足够复核输入量、结果数量与尾部统计的记录。它是后续实验的起点，没有改造前后的性能收益比较。

固定 Worker 资源时，4 场组尾部等待上界高于 1 场组。共享名额等待是合理解释之一，但本轮没有排队、实际处理时长和服务端积压记录，不能把差值全部归因于调度。单次客户端 Write 很快也不能证明 Worker 已经完成处理。

下一步优先补逐块发送排期落后：总跨度接近目标，仍可能掩盖中途停顿后追赶。随后补服务端活跃会话、Worker 排队/占用及资源采样，再固定容量实验的负载时长、稳定区间与通过标准。当前不报告每实例稳定并发数，也不把 21 个短会话扩展为长时临床负载结论。

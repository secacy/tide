# EXP-005-02：发送排期观测基线

Date: 2026-09-29
Status: 已完成同条件复测；未测稳定容量。
Source: ec4fc6d；本轮不修改业务代码。
Related: [原基线 EXP-005-01](loadgen-baseline.md)、[并发负载设计](../designs/2026-09-28-concurrent-load.md)

## 问题与方案选择

客户端整体发送跨度接近目标，仍可能在中途落后后追赶。容量实验需要区分服务端处理变慢与客户端未能按原计划制造负载。JSON v2 已保存每场排期样本数和最大落后，本轮先验证真实链路中的样本覆盖，并建立新增指标的观测起点。

沿用原基线的负载与服务配置，避免同时提高并发、延长会话或增加 Worker 后难以解释变化。替代方案包括直接扩大负载，以及保存逐块事件再分析分位数：前者留待服务端观测补齐后推进，后者有更细的分布和时间定位能力，但增加记录开销与数据量。本轮使用现有固定空间的计数与最大值，足以发现是否出现过明显晚发，不能定位具体哪一块或计算逐块 p95。

本轮属于观测能力复测，不是性能优化 A/B。原基线没有排期字段，不能把它记为零后计算改善比例。

## 执行前固定的条件与判据

- 同机独立客户端、Gateway、单 Mock Worker，正式二进制不启用 race；环境、源码与二进制哈希由 manifest 记录。
- Worker 共享处理名额 1，处理延迟 10ms，响应延迟 5ms；Gateway 未确认音频预算 32000 字节，其余条件与原基线一致。
- 先独立预热一场 2 秒；正式按 1/2/4 场顺序重复三轮，共九批、21 场。每场 5 秒静音 PCM，160000 字节、50 块，每块 3200 字节（100ms），实时发送，单场超时 20 秒。
- 保留全部尝试及原始报告；预热失败则不开始正式测量，失败不通过挑选或替换样本消除。
- 正确性要求：全部正式会话完整完成，输入量与结果数符合原基线，各场首条结果早于 end，摘要可复算；所有新报告版本为 2，每场排期样本数为 50，合计 1050，最大落后为非负整数纳秒。
- 提前固定只记录最大落后的数值，不设置未经业务论证的通过阈值；可与 100ms 块间隔比较量级，不能据此宣布满足临床 SLA 或稳定容量。

排期落后为有计划音频尝试的实际 Write 开始时间减原计划时间，提前则按零计。观察回调在 Write 返回后触发，失败尝试也可能计入；本轮完整会话应覆盖全部 50 块。排期落后与 Write 本身耗时分开报告。每组最大值是该组所有会话最大值的最大值，尾部 p50/p95 仍来自完整会话的尾部延迟。

## 实测结果

实际运行于 2026-09-29 14:12:18–14:13:09 UTC（含构建、预热与收尾）。源码为 ec4fc6d，业务目录无已跟踪差异；Apple M2 Pro、12 个逻辑 CPU、32GiB 内存，macOS 26.6.2，Go 1.26.5 darwin/arm64。三个二进制均未启用 race，未设置 GOMAXPROCS/GOGC/GOMEMLIMIT/GOFLAGS 覆盖。逐字段核对原基线 manifest，Worker、Gateway、负载、上述环境配置均一致；两次运行时间不同，本机其他负载未隔离。

九个正式批次全部退出 0，**21/21 场完整完成，1050/1050 块具有排期样本**；成功写出 3360000 字节，收到 84 条 partial 和 21 条 final，写入失败为 0。21 场首条结果均早于 end，各场恰有 50 个排期样本，全部报告为 JSON v2，输入与摘要复算通过。预热单独保存，不计入上述统计。

最大音频 Write 耗时在 1/2/4 场组分别为 2.105/1.467/3.016ms，与表中的开始发送落后是两项不同指标。尾部分位数按每组全部会话合并后计算；样本量仅 3/6/12，各组 p95 均等于最大值。

最大排期落后出现在第一轮单场会话，为 **34686333ns（34.686333ms）**，同场发送跨度为约 4.901 秒；其余两轮单场最大值分别为 2.714875ms 和 1.155833ms。该样本原样保留，不因与其他样本不同而重跑替换。所有已记录尝试的落后均不超过本轮全局最大值，约为 100ms 块间隔的 34.7%；这是量级描述，不是预先制定的通过阈值。

Gateway 收到 SIGTERM 后退出 0，Mock 随后被 SIGTERM 停止，退出状态 -15。只据此确认自有进程已收尾，不能推导每批内部活跃会话或 goroutine 已归零。

## 结论与下一步

新增观测在真实独立进程链路中覆盖了全部 1050 次音频写入。它提供了原来发送总跨度无法表达的信息：一次总跨度约 4.9 秒的正常会话，也出现过 34.7ms 的发送晚发。当前最大值不记录块序号、发生时间或每块耗时，不能定位这次晚发，更不能将其直接归因为操作系统调度、GC、源读取或服务端背压。

本轮所有会话完整完成且发送跨度接近原计划。排期落后未随 1/2/4 场计划数单调增大，短时同机样本也不足以支持“并发越高发送越准”的结论。原基线没有排期数据，本轮既不能计算排期优化比例，也没有建立稳定容量或临床长时负载保证。旧、新尾部数值仅作为各自运行事实保留，不将差异记为优化收益。

下一步补服务端观测，首先读取 Gateway 当前已接纳但尚未完成清理的会话数，以区分客户端的计划数与服务端实际活动量；随后观察 Worker 等待/占用和资源变化。使用已有 tracker 的一致快照作为数据来源，避免另建一套容易失配的活动计数。具体接口和实现拆分在下一小步确定。

# EXP-004-10：未确认处理音频量基线

日期：2026-09-23。阶段：第四阶段，进度计量已接入，积压上限尚未实现。

## 问题与实验前假设

发送、尾部及写回期限已经能够处理对应的阻塞，但 Send 很快返回时，Worker 仍可能落后。此前抖动实验观察到文本结果延迟，本次用新接入的累计确认直接观察：网关完整接收的音频中，有多少尚未获得处理确认。

实验前预期：正常处理时未确认量较小；短暂停顿产生可消退的暂时积压；持续降速导致输入期间积压增长，停止输入后才能逐步处理完。以上是待检验假设，不预设数值结论。

## 条件与测量方式

- 每次一个会话，一个 Mock Worker；三场景按正常、暂停、持续降速顺序执行，整组重复三次，正式共九个会话。
- 每会话 100 块，每块 3200 字节，每 100ms 计划发送一块，总计 320000 字节、10 秒音频。格式为 16kHz、单声道、16-bit PCM；内容为逐块可核对的合成字节，不是临床对话。
- 第 0 块在起点发送，第 99 块计划在 9.9 秒发送，随后立即发送 end。因此“10 秒音频”不等于 10 秒的发送墙钟耗时。
- 正常：每块 ProcessingDelay=50ms；短暂停顿：同样 50ms，完成第 20 块及对应文本后暂停一次 500ms；持续降速：每块 200ms，不暂停。
- ResponseDelay=0；每 500ms 音频产生一个 partial，共 20 个，输入结束后一个 final。新增处理进度每块一次，不转发给 WebSocket 客户端。
- Client、网关会话及 Worker 同进程，WebSocket 与 gRPC 均使用本机 TCP；没有修改 TCP 缓冲。
- 网关沿用默认等待期限：start 10s、输入空闲 30s、Send 2s、尾部 15s、结果写回 2s。实验接入上限为 1；未配置任何音频积压上限。
- 为读取 session 内计量器，使用测试专用 HTTP 接入壳，执行 tracker 登记、WebSocket Accept、读限制、newSession 和生产 session.run，并保留退出结果。**没有直接调用 Gateway.ServeHTTP；本实验验证会话链路，不用于重新证明准入实现或线上接入吞吐。**
- 正式数据不启用 race；先完成一次包含全三场景的全量 race 回归，再开始正式测量。

源码入口：[progress_baseline_experiment_test.go](../../internal/gateway/progress_baseline_experiment_test.go)。版本、源码哈希、环境和配置见 [manifest](results/progress-backlog-baseline-2026-09-23-manifest.json)；未提交代码差异另存 [source patch](results/progress-backlog-baseline-2026-09-23-source.patch)。

### 指标口径

| 指标 | 含义与限制 |
| --- | --- |
| 未确认处理字节数 | receivedBytes − processedBytes，包括传输中、等待处理、处理中以及确认返回中的音频；不是 Worker 物理队列大小 |
| 未确认音频时长 | 字节数除以 32000 字节/秒；是音频量换算，**不是已经等待的墙钟时长** |
| 观测峰值 | 每 5ms 尝试一次 snapshot 得到的最大值；可能漏掉采样间的瞬时峰值，不是精确上界 |
| 采样间隔与调用耗时 | 记录 snapshot 前后时刻及相邻样本间隔，说明调度与锁带来的测量边界 |
| end 附近未确认量 | 客户端 end Write 返回后立即采样，不表示网关已处理 end，也不保证最后一块已登记 |
| 尾部等待 | 客户端开始写 end 至读到 final 的时间，包含传输与处理 |
| 暂停恢复后的首次低位 | Worker 恢复下一次 Recv 调用后，首次采到未确认量 ≤ 3200 字节；不承诺此后持续稳定 |
| Send / Write 耗时 | 分别记录网关 gRPC Send、客户端 WebSocket Write 的调用起止；发送成功不等于处理完成 |

暂停边界以 Worker 第 20 块对应的 p4 发送返回、下一次 Recv 调用为观测点，包含少量函数和调度开销，不冒充内部计时器的精确边界。

### 方案取舍

本次选择周期采样，不在业务方法中增加指标钩子或高水位计数。优点是无需改变业务代码，也能拿到整段时间序列；代价是可能漏峰，并增加短暂加锁和记录开销。后续若需要证明严格的积压上限，应依靠控制点的不变量及边界测试，不能仅凭采样曲线下结论。

## 实测结果

九个正式会话全部完成，900 块、2,880,000 字节全部通过 Worker 内容及顺序校验；每次最终接收量和处理量均为 320000 字节、未确认量为 0。九次均正常关闭，清理后活跃会话均为 0，没有依靠主动取消服务来完成。

下表范围表示每个场景三次运行的最小值至最大值，不是百分位数。

| 场景 | 网关未确认量观测峰值 | 换算音频时长 | 客户端 end → final | 每次运行的最大 Send 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 正常，50ms/块 | 3200 字节（三次一致） | 0.1s | 50.69–51.18ms | 0.545–0.700ms |
| 暂停 500ms，50ms/块 | 16000 字节（三次一致） | 0.5s | 50.58–56.42ms | 0.054–2.449ms |
| 持续降速，200ms/块 | 137600 字节（三次一致） | 4.3s | 10.134–10.153s | 1.202–1.208s |

短暂停顿组在 Worker 恢复下一次 Recv 后，403.68–408.75ms 首次观测到未确认量回落至不超过一块（100ms 音频）。这是首次低位的时间，不是稳定恢复承诺：其中两次后续仍采到过两块未确认音频。三次最终尾部等待均回到上述约 51–56ms 范围。

### 同步转发已经产生背压，但计数只覆盖已读入的音频

持续降速三次均出现较长 Send 等待，最大值约 1.2 秒，仍未超过配置的 2 秒发送期限；尾部也未触发 15 秒期限，所以九次均能正常完成。长 Send 等待会使同步 upload 暂停下一次 WebSocket Read。

在持续降速组的客户端 end Write 返回后，三次立即采样均得到：

| 数量 | 字节数 | 音频时长 |
| --- | ---: | ---: |
| 客户端已完成 Write 的音频 | 320000 | 10.0s |
| 网关已完整读取并登记 | 288000 | 9.0s |
| 网关已收到 Worker 处理确认 | 156800 | 4.9s |
| 网关账目内未确认量 | 131200 | 4.1s |
| 客户端已写出、网关尚未登记的差额 | 32000 | 1.0s |
| 客户端已写出但尚未获处理确认的总差额 | 163200 | 5.1s |

因此，不能把网关的 4.1 秒未确认量当作这时整个输入链路的全部未确认量；另有 1 秒音频尚未计入网关账目。这里只证明两个观测点的差额，没有定位这些字节具体停在哪一个缓冲区。

类似地，暂停组 end Write 后的即时快照均为 pending=0，但 received=processed=316800，最后一块仍未计入。**单次 pending=0 不等于整场音频已处理完毕**，正常结束仍以原有 end 与 Worker EOF 规则为准。

### 采样与验证边界

- 目标采样周期为 5ms，正式运行实际最大相邻样本间隔最高为 **49.61ms**，snapshot 调用前后时间差最高为 **3.78ms**，包含调度及锁等待；不能解释为纯锁耗时。
- 三次同场景的观测峰值一致，仍不证明没有更短暂的更高峰。后续严格上界需要控制逻辑与边界测试证明。
- 含完整三场景的全量 race 回归通过，详见 [validation log](results/progress-backlog-baseline-2026-09-23-validation.log)。正式九次使用无 race 的单独运行，源码哈希在运行前后核对一致。
- 源码及模型不同于此前未汇报进度的基线，没有将旧版 Send 耗时直接拿来计算性能退化或提升倍数。

## 结论边界与后续

本次是改造前的问题基线，没有加入积压限制。即使九次正常完成，也不能证明真实 ASR 实时性、长时稳定性、总内存上界或稳定并发容量。源码中的应用层直接转发方式、gRPC/系统缓冲与模型资源仍需分别讨论。

实验支持三个具体结论：当前负载下正常与短暂停顿可完成并清空计数；持续降速会形成明显积压和长尾部等待；单次操作期限与处理落后程度是不同的控制目标。下一步的价值是明确允许继续承受多少未确认音频，并定义超过预算后的行为，而不是假定增加一层本地队列就能解决下游速度不足。

后续对照应保持同一负载、计量口径和退出验证，比较限制前后允许的未确认音频量、短暂停顿是否仍可恢复，以及持续降速时能否按约定结束。终止过慢会话会牺牲继续完成该场转录的能力，不能将“更早失败”描述为“推理变快”。

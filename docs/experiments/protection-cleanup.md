# EXP-004-12：反复保护退出与资源清理

日期：2026-09-26。第四阶段的补充资源验收，不是吞吐量、稳定并发容量或长时运行实验。

## 为什么要做

此前实验已经验证单次积压超限、发送超时、尾部超时和结果写回超时可以退出并归还名额。但单次成功不足以说明反复触发时没有遗留连接、阻塞调用或不断累积的对象。第三阶段的重复清理实验主要覆盖正常结束、客户端断开和 Worker 主动报错，没有覆盖本阶段全部新增保护路径。

本次检查同一 Gateway 持续处理这些故障后的清理与资源趋势，并用正常结束组作参照。预先要求每个会话都独立完成退出和连接关闭，应用在整个测量期间保持运行；内存不预设任意字节阈值，只保存逐轮数据分析。

## 方案与权衡

| 选择 | 收益与限制 |
| --- | --- |
| 每轮重建 Gateway/连接 | 隔离简单，但重启可能掩盖持久对象积累；本次不采用 |
| 用大量数据反复塞满真实网络缓冲 | 更接近停读/慢客户端压力，但分配量和 OS 缓冲状态会干扰重复清理趋势，且故障触发点依赖环境 |
| 保持真实连接，以门闩确定性阻塞 Send/Write | 可稳定反复触发期限与取消；本次采用，但不能用于网络缓冲容量或性能结论 |
| 设置固定 HeapAlloc 阈值 | 简单，但可能误判运行时缓存、GC 和测试自身分配；本次记录趋势，不作此断言 |

WebSocket 与 gRPC 都走本机 TCP，主入口直接调用生产 `Gateway.ServeHTTP`。发送故障在测试 stream 的 Send 方法中等待 RPC 取消；真实 RPC 已创建，Worker 会等待接收。写回故障在 WebSocket 握手结束后阻塞底层 net.Conn.Write，Close 解除阻塞。真实停读/慢客户端的缓冲行为另有此前实验，本次不把门闩当成真实流控。

## 负载、分组与计数

每次重复使用同一个 Gateway、HTTP Server、gRPC ClientConn 和 Worker，先运行正常组，再运行混合故障组。两组之间不重启、不中断应用；每次重复结束才销毁整套夹具。固定组顺序，没有随机化，不据此比较组间内存“节省量”。

每组先预热 2 轮，再测量 20 轮，每轮 5 个串行会话。每个会话清理验证完成后才接入下一个，MaxSessions=1。本次完整重复三次，共 **600 个正式会话、60 个预热会话**。

| 组别 | 每轮五个会话 | 三次正式会话数 |
| --- | --- | ---: |
| 正常对照 | 五次正常结束 | 300 |
| 混合故障 | 正常、积压超限、发送超时、尾部超时、写回超时各一次 | 300 |

混合组每类正式场景共 60 次，因此合计正常结束 360 次、四类保护退出各 60 次，共 240 次保护退出。

- 配置：MaxPendingAudioBytes=3200，Send/tail/result-write 期限各 75ms，其他配置沿用 Gateway 默认值。这些是加速清理验证的测试参数，不是生产建议。
- 每会话客户端先发送 start 和 3200 字节音频。正常 Worker 确认进度并回传 ready，收到 end 后返回 final。
- 积压场景不确认第一块处理进度，客户端收到 ready 后再发送 2 字节；未确认量达到 3202 > 3200，后两字节必须在发送前被拦截，Worker 只收到一块。
- 发送故障的首个 Send 等待 RPC 取消，Worker 收到零块；尾部场景 Worker 收到 end 后不完成；写回场景已确定进入阻塞 Write 后等待保护退出。
- 客户端在失败期间持续读取，断言前不主动关闭客户端或取消应用。单会话 4s 是实验兜底，依靠该兜底才退出的用例会失败。
- 本次为小输入、串行重复，未复现长问诊或多会话争用。

## 怎样确认已经清理

每个会话先验证客户端结果/关闭语义，再等待 Worker 退出通知和 Gateway handler 返回。之后验证：活跃会话为 0、服务端 WebSocket 底层 TCP 未关闭计数为 0、运行中的 Worker 为 0、受控阻塞的 Send 调用为 0，且应用 context 未被取消。

正常场景验证 ready、final、1000/completed；积压、Send 和尾部故障验证各自 1011 关闭原因；写回失败可能无法发出关闭帧，只要求在实验兜底之前断开，确定性错误分类由已有完整 run 的写回超时测试另行覆盖。Worker 正常返回或报告 Canceled，并核对收到的音频块数。

服务存活期间保留一条共享 gRPC TCP 连接是预期行为；每轮采样要求仍为 1。夹具最终关闭时另验证该连接数归零。不能把共享 transport 误算成单会话泄漏。

## 资源观测口径

每组预热后、每轮正式会话全部清理后，执行 GC 并记录 goroutine、HeapAlloc、HeapObjects、HeapInuse 和资源计数。报告样本数组提前分配，结果计数键在预热前初始化；不保存每条会话对象或音频历史。

每组末尾在清理检查已完成后额外等待 250ms，再 GC 并保存一条沉降样本，用于观察运行时后台工作和缓存变化。该等待不参与“会话是否清理”的判断，也不能解释为清理耗时。

goroutine 设辅助检查：末尾沉降值不超过预热基线 +8，超出时输出堆栈；这只能帮助发现明显累积，不能证明不存在少量泄漏。堆指标属于整个进程，包含客户端、Gateway、Worker、依赖、测试和 Go 运行时；GC 与等待本身也会干预观测，不能当作无 GC 干预时的内存峰值或单会话资源消耗。

## 实测结果

三次正式重复均通过，共 600 个正式会话及 60 个预热会话。正式结果为 360 次正常完成、积压超限/发送超时/尾部超时/写回超时各 60 次。保护退出属于预期的业务失败，不计为完整转录成功。

| 检查项 | 实测结果 |
| --- | --- |
| 每会话 Worker 和 handler 退出 | 600/600 正式会话通过 |
| 每会话活跃会话与底层 WebSocket TCP 连接 | 清理后均为 0 |
| 每会话运行中 Worker 与受控阻塞 Send | 清理后均为 0 |
| 应用是否被取消以帮助退出 | 否，测量过程中始终保持运行 |
| 后续接入 | 同一 Gateway 连续完成各轮接入，无需重启或重置 tracker |
| 服务存活时的共享 gRPC TCP 连接 | 132 个采样点均为 1，夹具销毁后为 0 |
| goroutine | 132 个采样点均为 12，包括六组预热基线和末尾沉降样本 |
| race 检查 | 包含快速探针及完整二十轮实验的全量回归通过 |

132 个资源样本由六组各一条预热基线、20 条正式轮次样本、一条额外沉降样本组成。最后一个混合故障会话是写回超时，因此“后续接入”指轮次间连续运行，不另声称每个故障之后都单独增加了一次正常转录探针；正常场景每轮均覆盖，前一轮写回超时后下一轮正常场景可完成。

下表单位为 KiB（1024 字节）。轮次范围仅包含正式第 1–20 轮，末尾沉降样本在这些会话清理验证完成后再等 250ms 并 GC。

| 重复 | 组别 | 预热后基线 | 第 1–20 轮范围 | 第 20 轮 | 末尾沉降后 | 第 20 轮相对基线 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 正常 | 867.91 | 825.01–892.73 | 855.41 | 649.81 | −12.50 |
| 1 | 混合故障 | 932.80 | 868.43–941.89 | 941.89 | 700.48 | +9.09 |
| 2 | 正常 | 984.87 | 914.38–961.91 | 934.35 | 725.53 | −50.52 |
| 2 | 混合故障 | 990.38 | 938.81–1008.04 | 986.55 | 741.23 | −3.82 |
| 3 | 正常 | 1000.73 | 898.49–965.24 | 938.45 | 738.17 | −62.28 |
| 3 | 混合故障 | 1010.90 | 934.60–1002.64 | 985.09 | 741.73 | −25.80 |

第一轮混合故障的第 20 轮存活堆比预热基线高 9.09 KiB，正式轮次的描述性线性拟合斜率为约 +2.31 KiB/轮；不能把它从报告中删掉。后两次混合组的第 20 轮均低于各自基线，斜率分别约 +0.23、−1.70 KiB/轮，没有跨三次重复一致的增长模式。描述性拟合不作为泄漏判定阈值。

各组末尾沉降后存活堆均低于该组预热基线，但单次下降同样不能证明没有泄漏。跨夹具重复的内存起点存在抬升，混合组沉降样本依次为 700.48、741.23、741.73 KiB；本次没有进一步用 profile 定位这些跨次差异，不能直接归因为某一项缓存，也不能据此推出整个进程长期有界。

这些数据支持的结论是：在本次有限、小输入、串行重复及 GC 干预条件下，没有观察到会话、底层 WebSocket 连接、Worker、受控发送调用或采样 goroutine 随轮次累积；存活堆也未出现跨重复一致的增长模式。**不宣称绝无泄漏、总内存严格有界或单会话固定消耗。**

### 可复核性

- 全量 race 验证包括完整实验，Gateway 包通过（18.977s），命令入口和 Mock 测试也通过；正式无 race 三次运行通过（18.051s）。这些时间是测试耗时，不是业务延迟指标。
- 实验前后测量源码哈希一致，原始日志、132 行采样 CSV、汇总及源码差异已归档。
- 当前工具链为 Go 1.26.5、macOS 26.6.2，Python 观察到 12 个逻辑 CPU；硬件型号与内存仅引用历史 manifest，本轮未重新测量。
- 本次没有使用第三阶段的 bufconn 内存传输，避免将其特定关闭计时器与固定缓冲分配混入本轮 TCP 资源观测；这不表示本次运行时与测试夹具不存在任何缓存影响。

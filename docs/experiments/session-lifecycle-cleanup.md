# 会话反复建立与退出的资源清理验证

日期：2026-09-20。

## 目的与范围

验证同一 Gateway 连续处理会话后，会话计数、Worker 和底层 WebSocket 连接能否释放。
这是第三阶段的资源清理验证，不是并发容量、吞吐量或长时间稳定性测试。

测试代码：`internal/gateway/resource_cleanup_test.go`。

## 实验条件

- 使用同一个 Gateway、HTTP 服务和 gRPC 客户端连接，不在每轮之间重启。
- 使用真实 WebSocket；通过 gRPC `bufconn` 运行可控 Worker，无真实 ASR 推理。
- 先运行 6 个会话预热，再执行 20 轮，每轮建立 6 个会话。
- 每轮包含 2 个正常结束、2 个客户端直接断开、2 个 Worker 主动报错的会话。
- 全部会话完成一次双向传输后才触发结束；每轮完成清理后才进入下一轮。
- 通过 Worker 退出通知和 HTTP handler 返回同步，不用固定延迟推测清理完成。
- 包装测试监听器及其连接，记录真实服务端连接的 Close，包括升级后的 WebSocket。
- 周期性触发 GC 后记录 goroutine、HeapAlloc 和堆对象数；内存没有设置硬性断言阈值。

## 重复测试结果

运行：

```sh
go test -race ./internal/gateway \
  -run '^TestGatewayRepeatedSessionCleanup$' -v -count=5 -timeout=60s
```

5 次均通过，共 600 个正式会话和 30 个预热会话。

| 检查项 | 观察结果 |
| --- | --- |
| 每轮活跃会话数 | 均回到 0 |
| 每轮服务端未关闭连接数 | 均回到 0 |
| Worker 与 Gateway handler | 每个会话均收到退出通知 |
| 服务状态 | 各轮之间保持运行并继续接纳会话 |
| goroutine | 每次运行预热后为 12，最终也为 12 |
| race 检查 | 本次运行没有报告数据竞争 |

测试允许 goroutine 相对预热基线有少量波动，并在超过阈值后等待回落；若仍不回落，输出堆栈。
该辅助检查不能证明不存在任何规模的 goroutine 泄漏。

## 重复创建测试夹具时的内存现象

同一次运行的 20 轮之间，堆分配量只有小幅波动；但连续启动 5 套测试夹具时，堆内存起点逐次增加约 2 MiB。

进一步检查：

1. 堆 profile 显示约 10 MiB 存活分配来自 `google.golang.org/grpc/test/bufconn.newPipe`。
2. 当前 gRPC v1.83.2 的客户端 transport 关闭逻辑设置了读、写期限；bufconn 使用捕获缓冲区对象的计时器实现期限。
3. 在临时副本中重复运行 5 套夹具，关闭全部夹具后继续等待 11 秒，再触发 GC。

| 时刻 | goroutine | HeapAlloc |
| --- | ---: | ---: |
| 创建夹具之前 | 2 | 426 KiB |
| 5 套夹具均已关闭 | 2 | 11018 KiB |
| 等待期限计时器结束并 GC 后 | 2 | 735 KiB |

这些证据支持：本次明显的跨夹具堆增长主要是测试内存连接缓冲区的延迟回收。
回收后的数值不要求等于进程启动时数值，运行时与依赖可以保留缓存。

11 秒等待只用于本次诊断，没有加入常规回归测试；也没有为此修改生产逻辑或依赖实现。

## 结论与边界

本轮正常结束、客户端断开和 Worker 主动报错场景中，没有观察到随会话轮次累积的会话、服务端连接或 goroutine。
测试依赖的明显堆增长已通过后续回收观察解释。

本结论不覆盖长时真实音频、慢 Worker、网络静默失联、发送阻塞或过载。
这些结果不能用于宣称系统达到某个并发容量，也不能替代后续长期运行与负载实验。

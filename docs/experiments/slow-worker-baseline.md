# EXP-004-01：持续慢 Worker 的基线实验

Date: 2026-09-21
Status: 首轮基线完成；正常与持续降速各重复 3 次，结果与原始记录如下。
Related: [Milestones](../MILESTONES.md)

## Question

在第三阶段的直接转发实现中，如果 Worker 持续以低于音频输入的速度处理数据，客户端发送与等待最终结果分别会受到什么影响？

本次先验证持续降速机制、发送耗时和尾部等待，不测稳定并发容量，也不预先断言 Gateway 会持续积压或内存无界增长。

## Hypothesis

- 当前 `ResponseDelay` 在发送 partial/final 前生效。partial 文本耗尽后，不再逐段返回 partial，因此无法保证长时间持续降速。
- 对每个有效音频块增加串行处理等待，可以让模拟处理速度持续低于实时输入速度。
- 底层缓冲可能暂时吸收数据，客户端写入成功不代表 Worker 已处理完成；短会话可能主要表现为尾部等待增加。
- 是否出现明显发送阻塞需要测量，不能由 Worker 变慢直接推出。

## Setup

Client:
- concurrency: 1
- format: PCM，16 kHz，单声道，16 bit
- chunk: 3200 字节，对应 100ms 音频
- source: 固定的 100 块合成 PCM，共 10 秒音频
- rate: 按音频时间轴发送，每 100ms 一块；第一块在起点发送

Worker:
- count: 1
- 已实现 `ProcessingDelay`：每个非空且通过 PCM 对齐校验的块，串行等待一次，再计入已处理音频量；等待响应 RPC context 取消。
- `ProcessingDelay <= 0`：不增加处理等待，沿用当前可取消等待函数的约定。
- 正常对照：每块 50ms；持续降速：每块 200ms。
- `ResponseDelay = 0`，隔离结果发送延迟的影响。
- partial/final 内容与频率在两组间保持一致。

Gateway:
- 使用第三阶段直接转发策略，不增加队列、准入或处理超时。
- Gateway 使用 `Config{}` 默认值：StartTimeout 10 秒、InputIdleTimeout 30 秒、MaxMessageBytes 1 MiB。
- 客户端实验总期限为 60 秒，期限到达记录为实验超时，不能当作成功完成。

Environment:
- macOS 26.6.2（25G83），Apple M2 Pro，32 GiB 内存，12 个逻辑 CPU。
- Go 1.26.5，darwin/arm64，GOMAXPROCS=12。
- Client、Gateway、Worker 在同一个 Go 测试进程，WebSocket 和 gRPC 均使用本机 TCP；不使用 bufconn，不模拟网络延迟或丢包。
- 两组使用相同运行条件，各重复 3 次，每次先正常组再慢速组，保留每次原始记录。
- 性能测量不启用 race。另以 race 运行行为回归与一轮完整实验，只用于检查正确性，不混入性能数据。

固定块大小是本次实验前提。同样的每块等待，在块大小改变后会代表不同的模拟处理速度；当前数值不是模型性能或产品阈值。

## Metrics

全部客户端时间采用同一进程的单调时钟间隔，不比较不同进程的绝对时间。

| 指标 | 定义 |
| --- | --- |
| 音频发送耗时 | 最后一块音频写入返回时刻减第一块计划发送时刻 |
| 单次写入耗时 | 每次 WebSocket 音频 Write 返回时刻减调用时刻；保存逐块数据 |
| 发送落后量 | 每块实际开始 Write 的时刻减该块计划发送时刻 |
| End 后等待 | 收到 final 结果时刻减发起 end 写入的时刻；另外记录 end 写入返回时刻 |
| 整场结果耗时 | 收到 final 结果时刻减第一块计划发送时刻 |
| 会话结局 | 正常关闭、业务错误、实验超时分别记录；失败样本不从记录中删除 |

当前 Mock final 代表整段输入处理后的输出。本实验的 final 等待指标不替代未来逐段转录延迟，也不代表真实模型识别延迟。现有 partial 数量有限，本步不报告转录延迟 P95。

## Procedure

1. 开发者实现 `ProcessingDelay`，保持原有返回结果规则。
2. 助手补充行为测试：每块均有等待、partial 耗尽后仍持续生效、取消能打断处理等待、零值兼容。
3. 助手编写基线实验测试，固定音频源与发送节奏，记录上述时间点，并确认 Worker 收到的总音频量与会话结局。
4. 先运行正常对照，再运行持续降速；重复并保存原始输出、版本和环境。
5. 根据观测决定下一项改造及验收阈值。引入背压控制后，复用本实验做前后对照。

## Results

每块 200ms × 100 块 = 20 秒是配置推导的串行处理等待总量。以下为真实时钟测量结果；表内范围是三次运行的最小值至最大值，不是置信区间。

| 指标 | 正常对照（50ms/块） | 持续降速（200ms/块） |
| --- | --- | --- |
| 音频发送耗时 | 9.9011–9.9017 秒 | 9.9004–9.9033 秒 |
| 每次实验的单次写入最大耗时 | 0.417–1.521ms | 0.329–5.156ms |
| 每次实验的最大发送落后量 | 1.806–3.281ms | 2.334–10.771ms |
| End 后等待 | 51.581–51.879ms | 10.1938–10.2035 秒 |
| 整场结果耗时 | 9.9530–9.9533 秒 | 20.0941–20.1068 秒 |
| 会话结局 | 3/3 正常完成 | 3/3 正常完成 |
| 每次实际音频量 | 100 块，320000 字节，10 秒 | 100 块，320000 字节，10 秒 |

第一块在起点发送，第 100 块的计划发送时刻是第 9.9 秒，因此“10 秒音频在约 9.9 秒发完”符合本实验的发送口径。

## Conclusion

1. 持续降速机制有效：100 块各处理 200ms 时，实测约 20.1 秒才返回最终结果，且三次运行一致地表现出约 10.2 秒尾部等待。
2. 客户端发送耗时仍约 9.9 秒。慢速组单次 Write 最长约 5.16ms，本次没有出现秒级发送阻塞。客户端音频发送顺畅不能证明 Worker 跟得上实时输入。
3. 结果与链路缓冲暂时吸收数据的解释相符，但尚未测量各层缓冲，不能确定数据具体积压在哪里。尤其不能把尾部等待直接等同于 Gateway 应用队列的等待时间。
4. 这是单会话、短音频、本机 TCP 的有限观测；没有测量内存、稳定容量、真实转录延迟分布或识别质量。三次重复没有建立广泛性能保证。

本小步完成条件已满足：持续降速行为经过测试；实验可重复；发送与结果等待有原始数据；结论明确区分观测与推测。

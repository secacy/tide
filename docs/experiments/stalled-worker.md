# EXP-004-02：Worker 停止读取后的发送阻塞与取消

Date: 2026-09-21
Status: 停读实现与行为测试通过；真实链路两种场景各运行三次。已复现发送阻塞，以及客户端断开后未在观察期内退出的缺口；Gateway 尚未修复这一缺口。

后续更新：本文件保留改造前基线。单次发送期限已在后续接入，其自主清理结果见 [EXP-004-03](worker-send-timeout.md)；不覆盖或改写下列旧数据。
Related: [Milestones](../MILESTONES.md)、[持续慢 Worker 基线](slow-worker-baseline.md)

## Question

前一实验中，客户端约 9.9 秒发完音频，但持续慢 Worker 在 End 后仍需约 10.2 秒才返回 final。尚未出现秒级写入阻塞，也没有定位积压位置。

本实验进一步确认：Worker 停止读取后，Gateway 的 gRPC Send 是否出现持续等待？客户端 WebSocket Write 是否随后受影响？主动取消会话后，阻塞操作和资源能否退出？

## Mock 行为约定

`mockasr.Config` 中 `StallAfterChunks int` 的约定：

- 小于等于 0 时关闭故障注入，默认行为兼容现有实现。
- 大于 0 时，每条 stream 独立统计已处理的有效音频块；空块不计数，非法音频仍立即报错。
- 正常处理前 N 块，包括已有的处理等待和该块触发的 partial 发送。
- 在下一次调用 Recv 之前停止推进，等待 stream context 取消，随后返回对应的 gRPC 取消或期限状态。
- 停读期间不再消费请求，也不主动返回 final 或正常 EOF。即使客户端随后发送 end，也不会恢复读取。
- 计数是 `StreamingRecognize` 的局部变量，不放在共享 Worker 上。

这是可取消的应用层停读，不是进程失联、网络黑洞或不可中断的模型调用。后几种故障不能由本实验结果推断。

## 实现顺序

1. 开发者实现停读配置、单 stream 计数及取消等待，保持 Gateway 业务代码不变。
2. 助手补 Mock 行为测试：准确停在 N 块之后、不调用下一次 Recv、无提前 final、取消可退出、默认兼容、多 stream 独立计数。
3. 助手编写真实链路诊断实验，分别观察 gRPC Send 与 WebSocket Write 的调用、返回和取消。

## 负载与观测方式

- 单会话，固定 3200 字节音频块；`ProcessingDelay=0`、`ResponseDelay=0`，`StallAfterChunks=5`、`PartialEvery=500ms`。
- 客户端先发送 5 块并读取第一条 partial，确认请求和结果已完成双向流动。Mock 的准确停读边界另由行为测试验证。
- 后续以加速发送诊断缓冲与阻塞；最多发送 5000 块（16000000 字节），故障观察阶段最多 15 秒。达到限制但没有观察到目标阻塞时，记录“未复现”，不能视为保护机制通过。
- 通过测试侧 gRPC client/stream 包装，记录 Gateway Send 的开始与返回。调用超过 1 秒仍未返回，记为本次诊断的“持续等待”；这不是业务超时，也不保证网络 I/O 永久卡住。
- 同时记录客户端每次 Write 的开始、返回，以及发生持续等待前各层已经成功交付的块数。Send 返回成功仅表示该调用返回，不表示 Worker 已处理。
- 观察到目标等待后，首先测试网关会话 context 的主动取消，分别测量 Send 退出、Worker 退出及 Gateway 清理完成的时间。
- 客户端主动断开场景单独验证；不能用“服务取消有效”推断“客户端断开一定能及时被发现”。若需要测试兜底取消才能清理，必须将兜底前的未退出记入结果。
- 客户端保持结果读取，以便回应关闭握手，避免本次发送阻塞观测混入不回应关闭帧的因素。

实际实验中，协调者在 Gateway Send 和客户端 Write 均连续等待至少一秒后执行动作；每 10ms 采样一次状态。两个调用独立记录开始、返回和成功计数。客户端断开采用 `CloseNow`，然后观察两秒，不取消服务 context；之后才按需兜底取消。

环境：macOS 26.6.2、Apple M2 Pro、32 GiB 内存、12 个逻辑 CPU，Go 1.26.5 darwin/arm64、GOMAXPROCS=12。Client、Gateway 与 Worker 同进程，WebSocket 和 gRPC 使用本机 TCP。Gateway 使用默认 Config，InputIdleTimeout 为 30 秒。本次加速发送不启用 race；另行启用 race 验证正确性。

上述大小、时间和观察阈值只限制诊断实验。加速发送的数据不能与前一实验的实时发送延迟直接比较，也不代表正常问诊负载或系统稳定容量。

## Results

首次代码检查发现 `processedChunks` 初始化后未递增，正值阈值无法触发。[停读行为测试](../../internal/mockasr/stall_test.go) 复现该问题。开发者补上处理成功后的递增，随后 Mock 全部测试使用 `-race -count=10` 通过，覆盖准确停读、空块、取消/期限、默认兼容和多 stream 独立计数。

真实链路实验：

```sh
TIDE_RUN_STALLED_WORKER_EXPERIMENT=1 \
GOCACHE=/private/tmp/tide-review-gocache GOPROXY=off GOSUMDB=off \
go test ./internal/gateway -run '^TestStalledWorkerExperiment$' \
  -v -count=3 -timeout=120s
```

测试默认跳过，显式设置环境变量才运行。全量 `go test -race ./... -count=1 -timeout=90s` 在启用该实验的条件下也通过；此轮只用于检查正确性，不混入测量数据。

以下为三次运行范围，非置信区间或服务时限保证。

| 指标 / 事件 | 服务主动取消 | 客户端断开 |
| --- | --- | --- |
| Worker 实际处理的音频块 | 每次 5 块，16000 字节 | 每次 5 块，16000 字节 |
| 动作前 Gateway Send 持续等待超过 1 秒 | 3/3 | 3/3 |
| 动作前客户端 Write 持续等待超过 1 秒 | 3/3 | 3/3 |
| 动作前 Gateway Send 成功返回数 | 41–52 块 | 41–52 块 |
| 动作前客户端 Write 成功返回数 | 253–473 块 | 253–443 块 |
| 客户端断开后观察约 2 秒 | 不适用 | 3/3 会话仍活跃，Worker 和 handler 均未退出，原 Send 仍等待 |
| 是否需要测试兜底取消 | 无需额外兜底 | 3/3 需要 |
| **取消发出后** Send 返回耗时 | 0.102–0.193ms | 兜底取消后 0.147–0.225ms |
| **取消发出后** Worker 退出耗时 | 0.432–0.600ms | 兜底取消后 0.472–2.323ms |
| **取消发出后** handler 返回耗时 | 4.406–10.275ms | 兜底取消后 3.607–8.365ms |
| 最终活跃会话 / 服务端未关闭连接数 | 均为 0 | 兜底后均为 0 |

服务取消组客户端均收到 1001 关闭码；客户端断开组由客户端直接关闭连接，不期待服务端关闭码。Worker 均以取消状态退出，没有读取第六块或产生 final。

上述 handler 返回包含会话内部 I/O 退出、连接兜底关闭和退出计数。其耗时不等于单次 cancel 调用耗时，也不是所有网络环境下的硬上限。

## 结论

1. 已直接复现两个发送方向的持续等待，不能再将问题仅归因于尾部结果返回慢。
2. Worker 实际只处理 5 块，Gateway Send 却已成功返回 41–52 次，客户端 Write 已成功返回数百次。各层调用成功不等于后端完成处理；这些计数揭示数据进度差异，不是对某一层缓冲容量的测量。缓冲与调度导致各次计数不同。
3. 服务主动取消能够打断当前等待并完成清理；客户端断开后，三次均未在约两秒观察期内自主退出。这里只证明观察期内未退出，不宣称通过实验证明永远不会退出。
4. 结合当前代码，upload 在 gRPC Send 中等待时无法继续执行 WebSocket Read；download 等待停读 Worker 的响应，没有结果可写。该场景缺少及时观察客户端断开的执行路径，InputIdleTimeout 也不约束 Send 等待。这是需要下一步解决的生命周期与背压交界问题。
5. 诊断测试通过表示观测和兜底清理符合记录，不能写成“客户端断开恢复测试通过”。没有测量内存增长、高并发容量、静默网络失联或不可取消的真实模型行为。

## 完成标准与边界

本小步诊断完成：停读行为有测试依据，发送阻塞已经复现，服务取消与客户端断开的结果分别记录，原始数据已保存。

下一步围绕“上传 Send 阻塞时，如何限制等待并推进会话退出”比较方案。可考虑发送等待期限，或将读取与发送通过有界缓冲解耦；后者仍须处理缓冲满后读取再次停住的情形，单纯增加队列不能保证持续感知断开。具体方案由后续设计确定，再用相同故障场景做改造前后对照。

本步不引入音频队列、会话准入或生产处理超时，不把库与操作系统缓冲的观测值当作 Gateway 已实现的容量边界。

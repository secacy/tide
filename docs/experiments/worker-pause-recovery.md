# EXP-004-04：Worker 暂停后恢复的抖动基线

Date: 2026-09-21
Status: 2026-09-22 已完成；暂停实现、行为测试、完整链路 race 检查与全量 race 回归通过；正式三组各三次，共九次测量完成。
Related: [发送期限保护](worker-send-timeout.md)、[Milestones](../MILESTONES.md)

## 问题与下一步选择

已有持续降速和永久停读实验，已实现单次 Send 期限。尚不知道 Worker 短暂没有进展、随后恢复时，当前直接转发能否继续完成问诊，以及恢复过程中结果会落后多久。

本步先建立可恢复抖动的基线，再决定是否引入队列。方案比较：

| 选择 | 优点 | 代价 / 当前缺少的依据 |
| --- | --- | --- |
| 立即引入有界队列 | 读取与发送可在队列未满时独立推进，缓冲可观测 | 会增加排队；底层已有缓冲；目前没有短暂抖动的对照数据说明新增队列的收益 |
| 调大发送期限 | 改动小，可能减少暂时阻塞导致的终止 | 更久占用资源，结果更旧；不能依据一次永久停读实验决定阈值 |
| 先测可恢复抖动 | 为缓冲大小、满载策略和超时取舍提供基线 | 需要一项小型 Mock 能力与实验测量，暂不改变网关策略 |
| 先引入识别进度反馈与落后控制 | 可以观察 Send 返回后模型仍未处理的数据 | 需要定义进度语义并修改协议或适配器，范围更大；仍需可恢复负载验证策略 |

当前选择先测可恢复抖动。它延续既定第四阶段的正常、抖动和过载实验，不将 Send 超时当作完整的实时性控制。

## Mock 实现方案与取舍

采用“处理 N 个有效块后，暂停一次”的确定性注入，复用现有可取消 wait。

- 对比每块随机延迟：确定性暂停更容易复现和做前后对照；暂不覆盖真实随机抖动分布。
- 对比按墙上时间触发：按处理块数可把故障放在相同音频边界；实际触发时刻随处理进展变化，必须记录而非假设。
- 对比通用故障脚本接口：两个配置字段足以表达当前实验；暂不增加接口与调度框架。

已增加配置：

```go
// PauseAfterChunks 指定处理多少个有效音频块后暂停一次。
// 大于 0 且 PauseDuration 大于 0 时启用；每条 stream 独立计数。
PauseAfterChunks int

// PauseDuration 是一次暂停的持续时间。
// 暂停期间不读取下一块音频，仍响应 RPC context 取消。
// 小于等于 0 时关闭暂停注入。
PauseDuration time.Duration
```

行为约定：

1. 每条 stream 增加局部 `pauseApplied bool`，不在共享 Worker 上记录状态。
2. 在循环顶部，先执行原有永久停读判断，再判断暂停；同一边界永久停读优先。
3. 当配置启用、尚未暂停且 `processedChunks >= PauseAfterChunks` 时，先设置 `pauseApplied=true`，再调用 `wait(ctx, PauseDuration)`。
4. 等待取消或期限到达时返回对应 gRPC 状态。正常等完后继续本轮 Recv，恢复原来的处理逻辑。
5. 前 N 块的处理和 partial 发送先完成，再暂停。空块不计数，恢复后即使下一条输入为空，也不应重复暂停。
6. 客户端恰好在第 N 块后结束输入时，EOF 读取会被这次暂停延后，final 随后正常生成；这属于明确的注入行为。

暂停本身不能调用 CloseSend、取消正常 RPC 或发送 final。正常恢复不创建新 stream，不属于第六阶段断线恢复。

## 实验配置与测量

- 单会话，10 秒 PCM，100 块，每块 100ms，实时发送；Worker 每块处理 50ms，ResponseDelay=0。
- 在处理 20 块（2 秒音频）后暂停，比较无暂停、500ms 暂停、3 秒暂停；各组的其他配置一致。
- Gateway 保留当前直接转发与 2 秒单次 Send 期限，不新增队列。
- Mock 在每 500ms 音频边界返回一次 partial，实验配置足够的文本条目覆盖全部 10 秒音频，避免原先有限 partial 耗尽后失去观察。
- 测试工具利用固定块大小、partial 顺序与预设文本编号对应音频边界，不为这次实验修改生产协议。该对应关系只适用于可控 Mock，不是通用的模型进度确认。

测量：

| 指标 | 口径 |
| --- | --- |
| 各 partial 的结果等待 | 收到结果时刻减包含对应音频边界的最后一块音频的计划发送时刻；第 k 条 partial 的对应块计划时刻为 `(5*k-1)*100ms` |
| 相邻结果最大间隔 | 两条连续 partial 到达时刻之差，观察中途长时间没有更新 |
| 发送等待 | 客户端 Write 与 Gateway Send 的调用/返回时间，不能用暂停时长推断发送阻塞时长 |
| 恢复后的追赶 | 展示暂停前后各 partial 的结果等待序列；实验暂用连续三条结果等待不超过 200ms 标记恢复，仅为分析阈值，不是业务 SLA |
| 会话结局 | 正常、发送超时、其他错误、实验超时分别保留；失败不能从统计中删除 |
| 正确性 | 音频顺序/数量、结果顺序及最终关闭方式 |

3 秒暂停不一定触发 2 秒 Send 超时：部分数据可能被底层缓冲接纳，单次 Send 未必等待满两秒。是否触发必须由观测决定。即使会话最终成功，中途结果也可能明显落后，因此不能只看最终尾部等待。

## 结果口径与复现

客户端、Gateway 和 Mock 在同一进程内，通过本机 TCP 连接。每次只有一个会话，各组顺序运行三次。环境为 Go 1.26.5、macOS 26.6.2、Apple M2 Pro、32GiB 内存、12 个逻辑 CPU，未设置 GOMAXPROCS 环境覆盖。

暂停边界取第 4 条 partial 在 Worker 侧发送返回的时刻；恢复边界取下一次 Recv 开始的时刻。两者之间包含函数和调度开销，是外部可观测边界，不是精确的内部计时器起止。

恢复确认取暂停后连续三条 partial 等待均不超过 200ms 时的第三条到达时刻；“恢复后确认耗时”从上述恢复边界开始计算。因此它包含追赶和确认窗口，不能理解为清空积压的精确耗时。无暂停组不计算此指标。

```sh
TIDE_RUN_WORKER_PAUSE_EXPERIMENT=1 go test ./internal/gateway \
  -run '^TestWorkerPauseExperiment$' -count=3 -timeout=120s -v
```

原始数据包含每次客户端 Write、Gateway Send、partial 到达、正常关闭和 Worker 读取数量。失败运行同样输出 JSON，不从日志中剔除；未发生的完成/恢复事件保留 null。

## Results

以下范围是每组 **3 次运行所得指标的最小值至最大值**，不是 P95 或置信区间。

| 指标 | 无暂停 | 暂停 500ms | 暂停 3 秒 |
| --- | --- | --- | --- |
| 正常完成 | 3/3 | 3/3 | 3/3 |
| 单次运行内最大结果等待 | 53.4–54.5ms | 306.6–309.1ms | 2807.2–2809.9ms |
| 单次运行内最大相邻 partial 间隔 | 501.3–501.7ms | 753.6–755.9ms | 3254.6–3256.3ms |
| 单次运行内最大客户端 Write 耗时 | 0.315–0.542ms | 0.500–0.949ms | 0.293–0.499ms |
| 单次运行内最大 Gateway Send 耗时 | 0.065–0.619ms | 0.061–0.281ms | 0.131–1.311ms |
| End 发起至 final 到达 | 51.7–52.3ms | 51.2–51.7ms | 52.0–52.5ms |
| 恢复后达到连续三条合格结果的确认耗时 | 不适用 | 1498.6–1500.9ms | 3998.3–3999.8ms |

九次均完整接收 100 块、320000 字节音频，内容和顺序一致；返回 20 条有序 partial 和 1 条 final，WebSocket 正常关闭，Gateway 等待清理完成。没有发生 Send 超时，也没有用服务取消兜底完成成功样本。

3 秒暂停组第一次运行，第 5–18 条结果的等待依次约为：

`2810 → 2565 → 2321 → 2075 → 1831 → 1588 → 1342 → 1098 → 853 → 608 → 364 → 119 → 54 → 53 ms`

这表明暂停后的结果逐步追上输入；第 16–18 条满足连续三条不超过 200ms，第三条到达时才记为恢复确认。由于正常时每块只需处理 50ms，而输入每 100ms 一块，Worker 有余力追赶。持续处理慢于输入的情况不能套用这个结果。

## Think：结果如何影响下一步

1. **最终完成快，不代表中途体验好。** 三组尾部等待都约 52ms，但 3 秒暂停组曾超过 3.25 秒没有新 partial。后续策略对照必须保留中途结果等待和更新间隔。
2. **发送期限保护不能代表识别实时性。** 本次 3 秒暂停没有让任何一次 Send 等待到 2 秒；音频可以先进入链路中的缓冲。实验没有定位各层分别存了多少数据，不能把积压归因于某一个缓冲区。
3. **这次记录的是可恢复抖动基线，没有新增性能优化收益。** 后续若增加有界队列，需要明确其价值是控制和观察应用层积压，并与本基线对照；队列本身不会使 Worker 处理得更快，也不能限制所有下游缓冲。
4. **结论有负载边界。** 当前只验证单会话、10 秒输入和确定性暂停；不证明长时稳定容量、真实模型表现或高并发性能。当前协议未提供通用的已处理音频进度，本实验依赖 Mock 的已知输出规则。

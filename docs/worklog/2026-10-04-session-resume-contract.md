# 第六阶段：短暂断连恢复契约与首步设计

日期：2026-10-04。状态：设计提案与实现指导；尚未实现或验证恢复能力。代码参照 `c297aa4`。

## 当前行为与本步目标

当前 [session.run](../../internal/gateway/session.go) 在合法 start 后选择一次 Worker，上传或下载发生决定性错误后取消 RPC、关闭 WebSocket 并等待两个 goroutine 退出。[tracker](../../internal/gateway/tracker.go) 只保存尚未清理完成的数量，没有按 ID 查找会话的能力。[WebSocket 协议](../../internal/wsprotocol/protocol.go) 没有恢复身份、音频位置和结果投递确认。

首个恢复范围建议限定为：客户端进程及有限缓存仍在，客户端短暂断网，原 Gateway 进程和原 Worker 识别流仍存活，新连接回到同一 Gateway。目标是在保留窗口内继续同一场问诊，明确重放范围、重复与缺口。重新建立一条连接本身不算恢复成功。

Gateway 重启、Worker 流失败、客户端丢失缓存及连接落到其他 Gateway 不在首个实现范围。此时应明确恢复失败，不自动创建新会话并伪装成连续问诊。实例异常处理仍是第六阶段后续任务，不因首步缩小范围而删除。

## 方案比较与建议

| 方案 | 收益 | 代价与适用范围 |
| --- | --- | --- |
| 断开即终止，重连新建一场 | 延续现有清理规则，释放快 | 旧识别上下文丢失；只恢复连接，无法保证问诊连续 |
| 保留逻辑会话及原 Worker 流，新连接重新附着 | 保留识别上下文，首步不要求模型支持状态快照 | 占用保留期名额；需要身份查询、过期清理、有界缓存与旧连接隔离；建议首个采用 |
| 重建 Worker 流并重放缓存音频 | 可覆盖原流丢失的一部分场景 | 有限音频未必足够重建模型上下文，文本分段可能改变；需定义缺口和跨流结果合并 |
| 持久化音频、结果及恢复状态 | 能进一步覆盖进程丢失、跨实例恢复 | 存储和一致性成本增加；音频持久化也不自动等于模型状态可恢复 |

建议先验证第二种方案，随后依据实例异常需求扩展。它需要调整 ADR-002 的断开终止规则和 ADR-003 的准入所有权；继续保持 ADR-007 的整场 Worker 绑定。现有 ADR 在功能尚未采用时不提前标记被替代。

## 拟定的恢复契约

1. **逻辑会话与连接分开。** 服务端创建不可预测的恢复凭据并返回给客户端，用于找到并证明有权接回该会话；凭据不放入普通日志。进程内注册表保存可恢复会话。原 Worker 流归逻辑会话所有，连接结束不直接决定其取消。
2. **保留是有限的。** 断开后启动恢复窗口，仍占一个逻辑会话名额。窗口到期、Worker 失败、保护触发或服务停止时终止并清理，清理完成后才释放名额。保留时间与现有输入空闲、尾部期限分别定义；不能让恢复操作无限延长识别收尾期限。
3. **最多一个有效连接。** 首版建议拒绝仍有有效连接时的恢复请求，由客户端在重试总期限内再试；不做主动抢占。代价是网络已断但服务端未检测到时，恢复需要等待断开被发现。端到端接入前须明确断连检测机制和期限。每次成功重附着递增连接代次，忽略旧代次迟到的断开事件。
4. **重试不能无限续租。** 同一代次重复报告断开不重置截止时间；错误凭据、冲突恢复或过期请求都不延长窗口。成功恢复后再发生新断开，才开始新的窗口。
5. **收到的音频与处理完的音频分别确认。** 拟增加 Gateway 连续接纳位置，用于客户端缓存释放和同一存活会话内的重放去重。只有音频已交给有界会话缓冲/转发所有者，并登记连续位置后才能确认；WebSocket Write 或 gRPC Send 返回本身都不充当这一契约。现有 processed_audio_bytes 继续表示本次 Worker 流的处理进度，用于积压保护；它不是持久恢复检查点。
6. **只接纳连续的新音频。** 拟用音频起始字节位置和负载长度标识范围。新数据从下一期待位置开始；已经完整接纳的重发范围不重复转给 Worker；位置跳跃或部分重叠不静默拼接。客户端重试保持相同位置对应相同音频。具体编码、合法范围及溢出检查在协议小步固定。
7. **两个方向都要恢复。** 断开期间 Worker 仍可能产出结果。结果需有独立投递序号和有界保留，客户端携带最后已应用结果位置以便重发及去重。segmentId 表示识别片段，同一片段可能多次更新，不能单凭它删除重复投递。正常结束后的完成通知也需要有限保留，否则“已经完成但通知丢失”会被误判。
8. **缓存耗尽必须显式失败。** 客户端音频缓存、Gateway 输入缓存、结果保留都需要字节/条目上限；客户端持续采集的音频超出缓存，或重连位置早于服务端可重放结果时，报告不可恢复的缺口。恢复期继续保留既有积压和处理保护，不承诺任意弱网下无损。
9. **end 必须绑定音频终点。** 后续协议应使 end 携带最终音频位置；重复相同 end 可确认，位置矛盾应拒绝。已接纳 end 的会话不再接纳新音频，但仍可恢复尾部结果投递。连接是否附着与输入是否结束是两个维度，不能混用一个状态枚举。

例如：客户端已发送到字节位置 32000，最后看到确认 25600。重连查询时 Gateway 的连续接纳位置为 28800，则从 28800 继续；若只能确定 25600，客户端可以从该处重放，由 Gateway 的当前接纳位置排除已接纳范围。前提是原逻辑会话和 Worker 流仍存活、缓存覆盖所需范围，且位置及内容契约成立。重新开始的 Worker 流不能套用旧流的位置省略前文。

## 第一实现小步：独立的连接保留状态

先实现纯状态部件，不立即拆 session.run 或改变 v1 行为。新文件建议为 `internal/gateway/resume_state.go`；测试由助手补充。类型及方法均需 Go 注释，写清参数、状态改变和资源所有权。

`resumeState` 只回答“当前连接代次能否断开、能否接回、是否已过期”。它不保存 WebSocket/Worker、不操作注册表、不启动 goroutine 或 timer，也不释放准入名额。后续由同一个会话协调者串行调用；自身不承诺并发安全。调用方传入处理当前事件时的 now，便于使用确定时间测试；不能把事件产生时的旧时间用于过期判断。

| 类型或字段 | 含义 |
| --- | --- |
| resumePhase | 连接保留状态的内部枚举 |
| resumeAttached | 当前有一个有效连接 |
| resumeDetached | 当前没有连接，仍处于可恢复窗口 |
| resumeClosed | 恢复资格已终止；不表示网络资源已经清理完成 |
| phase resumePhase | 当前保留状态 |
| generation uint64 | 当前/最近有效连接的代次，初始为 1，每次成功恢复递增 |
| window time.Duration | 每次有效断开后的保留时长，构造时必须大于零 |
| expiresAt time.Time | detached 状态的截止时间，其余状态清零 |

建议方法契约：

```go
// newResumeState 创建已附着、代次为 1 的状态；window 必须为正。
func newResumeState(window time.Duration) (*resumeState, error)

// detach 仅接受当前代次在 attached 状态下的断开。
// 成功时进入 detached，截止时间设为 now+window，并返回 true。
// 旧代次、重复断开或 closed 均返回 false，不延长窗口。
func (s *resumeState) detach(generation uint64, now time.Time) bool

// resume 仅在 detached 且 now 严格早于截止时间时成功。
// 成功后进入 attached、清除截止时间，返回递增后的代次。
// 到期则进入 closed 并返回过期错误；attached/closed 返回相应错误。
// 代次溢出必须拒绝且不得回绕为可复用的代次。
func (s *resumeState) resume(now time.Time) (uint64, error)

// expire 在 detached 且 now 已达到截止时间时进入 closed，返回 true。
// 其他情况返回 false；只改变状态，不承担资源清理。
func (s *resumeState) expire(now time.Time) bool

// close 永久结束恢复资格并清空截止时间，允许重复调用。
// 不关闭连接、不取消 RPC、不释放会话名额。
func (s *resumeState) close()
```

attached 状态的冲突、closed 状态、窗口过期及代次耗尽使用可 errors.Is 判断的内部哨兵错误，避免上层依赖错误文本。成功 resume 时无需增加逻辑会话数。连接代次用于隔离旧事件，不能作为恢复凭据。

边界规则为 `now >= expiresAt` 即过期。协调者执行 resume 时也检查期限，不能只等 timer 事件，否则 timer 调度迟到会延长恢复资格。旧 timer 即使迟到，也由 expire 根据当前状态与当前截止时间判断，不依赖“timer 已取消就绝不再来事件”的假设。

## 验收与后续顺序

首步测试使用明确的 time.Time，不 sleep、不打开端口：非法窗口拒绝、初始状态、正确断开、重复断开不续期、旧代次隔离、期限前恢复、恰好到期拒绝、重复 close，以及旧超时事件不能关闭新一轮仍有效的保留窗口。这里只验证状态规则，不能标记真实断线恢复完成。

随后分小步推进：会话身份与注册表所有权 → 明确 v2 音频位置/接纳确认及 end 语义 → 客户端有限重放缓存 → 结果序号/确认/有限保留 → 连接附着与逻辑会话协调接入 → 可控断连实验。接入前补齐断连检测、重试预算、终态保留、双层准入（连接握手与逻辑会话）及保护期限的配合，避免重连重复占位或被满额逻辑会话拒绝。具体线格式和预算值在对应步骤确定，当前不随意指定生产默认值。

恢复实验从开始就记录：计划音频/已接纳/实际送 Worker 范围、重放字节数、重复送入字节数、缺口、结果重复应用次数、恢复尝试成功率，以及注入断开到恢复完成和到首条新结果的时间。恢复完成需定义为重新附着且双方待补数据追平，不能仅以 WebSocket 握手成功代替。所有失败保留分母；真实客户端断连、超窗、缓存耗尽和 Worker 失败分别报告。

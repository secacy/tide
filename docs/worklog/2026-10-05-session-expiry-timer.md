# 第六阶段：断开保留的自动到期

日期：2026-10-05。状态：开发者实现已通过评审与独立验收；真实恢复链路尚未接入。依据 `c24a242` 和[控制循环验收](2026-10-05-session-control.md)。

## 问题与目标

当前控制循环在恢复请求到来时检查期限。如果客户端断开后一直没有新请求，恢复期限即使过去，循环也会继续等待命令，直到显式关闭或生命周期取消。后续真实会话将持有 Worker 流及名额，这个缺口必须在接入前补齐。

本步目标：进入 detached 后自动安排期限唤醒；期限到达且仍需终止时，关闭恢复资格并退出控制循环。不要求定时器精确在截止纳秒执行，实际退出受调度影响；要求在没有新请求时也有退出驱动，且不会在当前期限前关闭会话。

## 方案与权衡

| 方案 | 收益 | 代价与选择 |
| --- | --- | --- |
| 每场或全局 ticker 周期检查 | 容易统一轮询 | 增加周期扫描/唤醒，过期发现还取决于扫描间隔；当前无必要 |
| time.AfterFunc 回调直接关闭状态 | 启动方便 | 回调与控制循环并发，破坏状态单一所有者；改为发事件又要处理回调退出和事件投递 |
| 控制循环 select 一个 time.Timer.C | 状态和计时器由同一循环管理，无额外业务回调 | 需要明确启停及期限检查；本轮采用 |
| 共享期限堆或时间轮 | 大量保留会话时可能减少管理成本 | 增加集中调度和事件失效规则；出现实测瓶颈后再评估 |

每次有效断开创建新的 Timer；恢复时停止并丢弃它，新一轮断开再创建。也可复用 Timer.Reset 以减少分配，但当前只在断开/恢复边界操作，先选择所有权清楚的创建/停止方案。是否值得优化需要后续测量。

## 核心规则：截止时间负责判断，Timer 负责唤醒

resumeState.expiresAt 是恢复资格的截止时间。Timer 通知仅表示应该重新检查，不等于可以直接终止。接收通知时使用处理当下的 now() 调用 resume.expire，不使用 channel 消息里的旧时间戳，也不无条件调用 close。

例如：第一轮在 t=0 断开、期限 t=10；t=3 成功恢复，停止旧 Timer；t=5 再断开，新期限 t=15。旧期限 t=10 已不再适用。循环只监听新 Timer 的 channel，而且最终判断仍依据当前 expiresAt。

无效凭据不进入此内部循环；重复/旧代次断开、已取消的请求、未知命令及失败恢复都不得延长 expiresAt。代次耗尽仍保留原 Timer，最终可自动过期。

## 实现范围

仅修改 `internal/gateway/session_control.go` 的 runControl，并更新注释。submitControl 和三个请求包装继续使用已有的交付与回复规则；不新增控制命令、goroutine、注册表扫描或会话字段。

runControl 中增加两个局部变量：

```go
var expiryTimer *time.Timer  // 当前恢复期限的 Timer，仅由本循环创建和停止。
var expiryC <-chan time.Time // 当前监听来源；为 nil 时禁用 select 的到期分支。
```

nil channel 的 select 分支不会就绪，因此 attached 时让 expiryC=nil 即可，不需要空转判断或额外等待协程。两个变量只由控制循环访问。

再定义两个局部闭包，保留对应注释：

- **stopExpiryTimer()：** 若 expiryTimer 非 nil 则调用 Stop，随后将 expiryTimer 和 expiryC 都置 nil；可重复调用。不从旧 channel 阻塞读取，不关闭 Timer.C。
- **armExpiryTimer()：** 先停止旧 Timer；仅当当前状态为 detached 才安排新 Timer。计算 `remaining := s.resume.expiresAt.Sub(now())`，小于零按零处理；创建 `time.NewTimer(remaining)` 并保存其 C。它依据已有绝对截止时间安排剩余等待，不能把期限改为 now()+window。

当前 Go 1.26 模块下，已从本地 time.NewTimer / Timer.Stop 文档核对默认 channel timer 的停止行为。本方案不复用已丢弃的 channel，即使 Stop 返回 false，也不靠阻塞 drain 保证业务正确性；当前状态/截止时间仍是判断依据。显式兼容开关及其他 Go 版本的运行行为没有在本步做实验。

## 六处接入点

| 位置 | 应做的事情 |
| --- | --- |
| 循环启动前 | 若已经是 detached，调用 armExpiryTimer；attached 不启动 Timer。支持测试或内部创建流程预置的保留状态 |
| controlDetach | 只有 detach 返回 true 时才 armExpiryTimer；返回 false 保持原 Timer 和截止时间 |
| controlResume 成功 | stopExpiryTimer，然后返回成功代次；错误时保留原 Timer，若状态变 closed 则回复后退出 |
| select 收到 expiryC | 停止并清空当前 Timer，执行 resume.expire(now())；true 则退出；false 且仍 detached 则按剩余期限重新 arm |
| controlClose / 生命周期取消 / 过期退出 | 共用 defer 停止 Timer，再关闭恢复资格，最后关闭 controlDone |
| 已取消请求 / 未知命令 | 沿用错误回复，不改变期限安排 |

把已有 defer 移到局部计时器闭包定义之后，且在首次 arm 之前登记，确保所有正常退出路径都先停止 Timer。计时器分支没有接收新命令，不需要给任何人发回复；已在命令分支接收的请求仍必须先回复再返回。

select 新分支的逻辑顺序为：

```text
收到当前 expiryC
    停止并清空 Timer
    用处理当下的时间检查 resume.expire
    已过期：退出循环
    尚未过期且仍 detached：按原截止时间重新安排
```

正常时钟下通知通常不会早于期限。保留再次检查和重新安排的分支，避免把一次早到或当前期限已改变的通知误解为过期；也避免消费一次性通知后再无自动到期驱动。

## 恢复与到期同时就绪

Go select 不保证恢复命令优先于到期通知。保留两条符合当前接口的结果路径：

- 命令分支先接收且处理时间达到截止：resume 返回 errResumeExpired，先回复再退出。
- 到期分支先处理并退出：尚未交付的调用看到 controlDone，返回 errResumeClosed。

两者都不得恢复成功或递增代次。调用方不能依赖边界竞争时唯一固定的错误文本；后续如需对外稳定区分所有终止原因，需要增加独立的终态记录，目前不扩展该协议。

截止前的恢复以协调者实际检查时刻为准。提交动作早于截止，并不保证处理时仍在窗口内。生命周期取消、显式关闭与到期竞争也按循环观察顺序处理；此前已接收命令的回复责任保持不变。

## 时间来源与测试调整

runControl 保留 now 参数，但现在它同时用于状态判断和 Timer 剩余时长计算。生产传 time.Now；测试的 now 也必须随 Timer 所在时钟一致推进。不能让 now 永远返回固定日期，再期望一个真实或虚拟 Timer 到期后证明相应时间已过去，否则可能反复重新安排而无法到期。

现有部分测试使用固定 resumeTestTime 和在 now 内暂停的同步点。加入启动期与断开后的 Timer 安排会增加 now 调用次数，助手在实现后会调整这些测试：以 testing/synctest 内的 time.Now 作为主要时间源；需要构造取消竞争时，明确暂停发生在目标命令处理阶段，保留原来的交付/回复断言。

本步核心代码由开发者完成；测试改造和新测试由助手负责。由于边界错误允许到期先处理后的 errResumeClosed，旧的“预置已过期，再期待必然收到 errResumeExpired”用例也须改为控制交付顺序，或者在并发到期测试中接受两条已定义路径，仍严格检查不成功、代次不变和循环退出。

## 助手后续验收计划

使用 synctest 虚拟时间，不等待真实恢复窗口：

1. attached 状态经过多个窗口仍保持控制循环运行。
2. 有效断开后不再发送请求，截止前仍存活，达到期限后自行退出。
3. 重复或旧代次断开不延长窗口。
4. 截止前恢复成功，经过旧期限仍保持新连接有效。
5. 恢复后再次断开，旧期限不终止新窗口，新期限到达后自动退出。
6. 显式关闭和生命周期取消停止期限等待；controlDone 关闭时恢复资格已终止。
7. 恢复/到期边界竞争不会成功恢复过期状态，不遗留已交付请求的等待者。
8. 代次耗尽后仍会在原期限自动退出。

继续运行此前身份、注册表、状态与控制取消测试。观察到期与退出即可证明本步行为；尚未接入的注册表删除、名额释放、Worker 取消和真实恢复耗时分别在后续集成验收，不能由 controlDone 推断已完成。


## 自动到期验收（2026-10-05）

开发者完成 [session_control.go](../../internal/gateway/session_control.go) 的 Timer 管理。评审确认有效断开才安排新期限、恢复成功停止旧 Timer、通知触发后按当前截止时间判断、所有退出路径经 defer 停止 Timer。核心逻辑无需修改；助手补充 now 与 Timer 时钟一致推进的注释，调整已有测试，并新增 [session_expiry_test.go](../../internal/gateway/session_expiry_test.go)。

执行：

```sh

  go test -race ./internal/gateway \
  -run '^Test(SessionControl|ResumableSession|SessionRegistry|ResumeState|SessionIdentity)' \
  -count=1 -timeout=45s -json
```

新增 **9 个顶层测试、14 个叶级场景**（含父测试共 17 项）；与此前部件合计 **46 个顶层、104 个叶级场景**（含父测试共 123 项）全部通过，无失败或跳过，未报告数据竞争。包耗时 2.026 秒，仅是测试执行耗时，不是实际恢复延迟或生产到期清理耗时。

测试在 testing/synctest 中让 time.Now 和 Timer 同步推进。time.Sleep 用于推进已知的虚拟业务期限，不等待真实的 10 秒窗口，也不用它猜测命令处理阶段；命令交付及取消竞争仍用 channel 信号与 synctest.Wait 确定阶段。运行中的恢复状态不直接读取，退出后通过 controlDone 同步再检查。

| 场景 | 验证结果 |
| --- | --- |
| 持续 attached | 虚拟时间经过 30 秒、三个窗口，循环仍可用 |
| 断开后没有任何新请求 | 命令断开与初始 detached 两种路径均在 10 秒减 1ns 时仍存活，在 10 秒时自行退出、恢复资格关闭 |
| 无效操作不续期 | t=9 秒发送重复断开、旧代次断开、已取消命令或未知命令，四组均在原 t=10 秒退出 |
| 窗口内恢复 | t=9 秒恢复取得代次 2，推进到 t=30 秒仍保持 attached，旧期限没有误关连接 |
| 恢复后再次断开 | t=3 秒恢复、t=5 秒再次断开；t=10 秒旧期限不影响新窗口，t=15 秒按新期限退出 |
| 提前关闭 | t=5 秒显式关闭或取消生命周期，两组均在同一虚拟时刻退出，没有等到 t=10 秒 |
| 到期与恢复竞争 | 32 个等待恢复调用参与已到期会话的竞争，全部返回 Expired 或 Closed，成功恢复 0 次，代次保持 1 |
| 已交付恢复跨过截止 | 调整原测试，在命令已接收后推进到截止，调用方收到明确 Expired 回复，循环随后退出 |
| 代次耗尽 | t=9 秒恢复失败不续期，原 t=10 秒自行退出，代次保持 MaxUint64 |
| 启动时已过期 | 截止早于启动 1 秒，在当前虚拟时刻退出，没有重新给出窗口 |

这些纳秒边界是虚拟时钟下的状态规则验证，不代表操作系统调度能按纳秒执行 Timer。竞争测试不要求 select 固定选择某个分支；已交付回复和到期先退出的拒绝分别有覆盖。

本步补齐了“没有重连请求也会结束保留状态”的驱动。controlDone 只证明控制循环及其状态已终止；注册表删除、准入名额释放、Worker/网络资源清理尚未接入，不能从本步测试推断已完成。现有 Gateway 没有启动这条恢复控制路径，因此本次执行相关独立部件的定向 race，没有重复全项目网络实验。下一步先明确连接资源交接与最终清理的所有权，再指导真实链路接入。

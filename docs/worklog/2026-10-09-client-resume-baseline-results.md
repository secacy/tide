# EXP-006-01 正式恢复对照与复核

日期：2026-10-09。对应[完整实验报告](../experiments/client-resume-baseline.md)。本步完成预登记的 15 场非 race 测量，没有改变生产逻辑或实验负载。

## 执行与证据

实测版本 `aa91222`。同一 Go 1.26.5 构建、本机公开 v2 Gateway / WebSocket 代理 / TCP gRPC 实验 Worker；Mac14,10，Apple M2 Pro，12 逻辑 CPU，32GiB 内存，macOS 26.6.2 / 25G83，运行日志 GOMAXPROCS=12。源码 255 个 Go/mod/sum 文件的 SHA256 在测量前、测量后与 Git 提交对象三方一致；用户无关修改未纳入实验。

三轮均按 A→B→C→D→E 顺序执行，每场 6 秒 / 192000 字节 / 60 块，故障在首次连接第 20 块 `[60800,64000)` 丢失后关闭连接。Worker 每块固定 10ms，可被取消，仍是实验 Mock。实际断网分别约 500.2–500.6ms、2000.1–2000.2ms 和 6000.4–6000.5ms。每场独立环境，客户端 5s 恢复窗口、服务端 10s 保留窗口保持原配置。

执行命令与运行时临时 caffeinate 断言、起止时间及环境在[manifest](../experiments/results/client-resume-baseline-2026-10-09-run-1/manifest.json)；完整 Go JSON、解码报告和采集脚本原样归档。正式命令未启用 race，退出码 0；15 个子场景、三轮父测试和包终态完整。这里的 Go pass 表示预设行为判据满足，B/E 业务仍失败。

## 数据分析与首次失败

[分析器](../experiments/scripts/summarize_client_resume.py)按原始源读取、代理范围/摘要、实际 Worker 音频、客户端应用和资源时间复算，核对固定条件、原场选择/建流、音频逐字一致及序号连续。长 JSON 日志被 test2json 拆成最多约 1024 字节片段，分析器先按输出顺序重组，不能逐条 Output 单独解析报告。固定 15 场分母，缺场和矛盾证据直接中止解释，不自动替换。

首次分析按序列化时间复算耗时并要求 1ns 精度一致，拒绝了报告。核对本机 Go 标准库 `time.Time` 实现确认：`time.Now` 值包含单调时钟，`Sub` 优先使用它，而 JSON 不保存单调读数。本次不是 Python 纳秒解析错误：计划位置时间可逐纳秒重现，运行中单调耗时与离线日历时间差不能要求完全相同。

在成功分析前，将双时钟核对调整为最多 1ms 一致性上界，并逐项保存原始单调耗时、离线日历耗时和差值；还要求二者对 `0 <= wait <= 200ms` 的分类相同。这个上界是**分析工具修正，未在实验前登记为业务判据**，不能称逐纳秒复现或计时精度达到 1ns。正式 200ms 追赶判据、音频位置、预算和运行数据均未改变。实际最大时钟差为 0.101834ms，未改变任一结果的阈值分类。正文展示离线复算值至 0.1ms，原始 Go 单调数值另存。

首次失败脚本和错误栈原样保留；第二次分析因摘要构造重复 `worker_bytes` 关键字失败，修正该分析代码后再读同一原始数据，没有重新运行或替换任何业务场景。两次分析失败与成功结果均见[归档目录](../experiments/results/client-resume-baseline-2026-10-09-run-1)。

新增分析器 8 项 unittest 通过：真实 15 场复算、跨时区纳秒、长日志重组/截断、缺轮拒绝、失败分母保留、凭据拒绝及配置/字节/位置/确认/清理等证据篡改拒绝。Go 核心和测量工具未改，本步没有重复全项目 race；沿用已归档的工具 race 验收。

## Results

| 组 | 业务完整完成 | 预设行为达标 | Worker 实际音频 | 原场恢复 |
| --- | ---: | ---: | --- | --- |
| 正常 | 3/3 | 3/3 | 每场 192000 字节完整一致 | 无尝试 |
| 500ms 中断、关闭恢复 | 0/3 | 3/3 | 每场收到前 60800 字节 | 无尝试，断线失败 |
| 500ms 中断、开启恢复 | 3/3 | 3/3 | 每场 192000 字节完整一致 | 每场一次尝试成功 |
| 2s 中断、开启恢复 | 3/3 | 3/3 | 每场 192000 字节完整一致 | 每场一次尝试成功 |
| 6s 中断、开启恢复 | 0/3 | 3/3 | 每场收到前 60800 字节 | 每场一次尝试，预算耗尽 |

同样 500ms 故障，关闭恢复 0/3 → 开启恢复 3/3，观察到完整完成率 +100 个百分点；三次样本不能估计真实网络恢复成功率。六场成功恢复均保持一次 Worker 选择/建流，192000 字节逐字一致，seq 1–61 各应用一次，共 366 次应用，没有重复或缺失。每场代理多观察到 3200 字节重复音频负载，占本场输入 1.67%；这是丢失帧重传，不是 Worker 重复处理，也不代表全 TCP 流量开销。

通路开放到新采集音频结果返回：500ms 组 24.3–25.8ms，2s 组 23.2–27.0ms；从故障发生计时则分别为 524.6–526.0ms、2023.3–2027.2ms，不能把断网本身从用户等待中隐去。连续三条等待不超过 200ms 的追赶确认，分别在开放后 110.4–112.4ms、310.8–311.4ms。

正常组单场最大结果等待为 12.7–13.5ms；500ms 组升至 514.6–515.4ms，2s 组升至 2013.2–2015.7ms。最大无新 partial 间隔分别为正常 101.2–101.8ms、500ms 组 602.3–603.4ms、2s 组 2100.9–2103.8ms。最终完成不等于中途一直实时。

6s 中断组故障后约 5000.8–5001.0ms 返回 `recovery_exhausted`，没有重新 start 或创建第二条 Worker 流。每场仍采集完整 192000 字节，仅前 60800 到达 Worker，其余 `[60800,192000)` 共 131200 字节没有恢复，不能称无损。关闭恢复组采集 64000 字节，其中 `[60800,64000)` 未到 Worker，后面的 128000 字节未采集，二者分开记账。

15 场源均恰好 Close 一次、远端资源自然归零、相关任务自然退出、未用服务取消兜底。客户端返回后的自然空闲观察：正常/预算内恢复最多 7.4ms；关闭恢复仍等待约 10.008s；超出窗口仍等待约 5.006–5.008s。原因是服务器保留窗口独立于客户端窗口，不能把客户端返回解释成名额已释放。

## 数据质量和限制

共 12564 条资源样本。非空音频 Read 的最大计划落后 1.414ms；最大资源采样间隔 102.257ms 出现在第二轮 2s 中断组尾部完成附近（最后应用结果前），不覆盖该场恢复/追赶计时点。该场仍完整保留；这段窗口的资源中间状态不可由采样推断，也不能断言该缺口来自 GC、OS 调度或某个组件。EOF Read/尾部完成不属于“非空音频 Read 落后”指标。

本实验为单会话、6 秒、同实例、确定性中断、每块 10ms 的 Mock。Worker 相对 100ms 输入块有足够处理余力，所以能追赶；慢于输入的模型不一定有相同行为。缓存容量、并发恢复、重试退避性能、半开检测、真实 ASR、长时问诊和跨实例续传未在此获得证据。本轮每次只启动一个 resume，不能用结果证明多次退避策略性能。

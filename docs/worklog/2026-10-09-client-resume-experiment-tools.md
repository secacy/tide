# 同实例恢复实验工具与验收

日期：2026-10-09。对应 [EXP-006-01](../experiments/client-resume-baseline.md)。本步完成工具与短时行为验收，未执行五组各三次的正式性能测量。

## 当前目标与选择

上一步已经预登记同版本关闭/开启恢复的五组对照。此前功能验收没有固定实时输入、断网时长和观察窗口，不能由测试包耗时推断恢复耗时。

本步把源采集、代理看到的字节范围、Worker 实际处理位置和客户端结果应用关联起来。实现位于 Gateway 的现有实验测试体系，仅增加三个 `_test.go` 文件，不改客户端、Gateway 或生产 Mock 的运行逻辑。

相比立即扩展客户端 OnEvent 公共 API，本轮已有 source 包装、OnResult、RunResult 和代理边界足够测量预登记指标；代价是没有客户端内部 ready 接纳/断线判定时刻。相比扩展生产结果协议，实验 Worker 用文本标记累计处理位置即可验证关联；它不代表真实模型已有相同的位置语义或输出频率。相比 OS 故障注入，本机真实 WebSocket 代理能固定丢失位置，复测简单；它不覆盖随机丢包、网络切换或半开连接。

## 实现与原理

- [观测与分析](../../internal/gateway/client_resume_observation_test.go)：固定条件、原始报告、位置相关输入、SHA256、范围并集重传计算、新音频关联、逐结果等待、连续三条追赶确认及自然清理分析。不存在的时刻/延迟保留 null；应用序号、源/Worker/代理位置、处理顺序、内容和配置交叉核对。
- [实验链路](../../internal/gateway/client_resume_harness_test.go)：有限源、真实 TCP gRPC 位置 Worker、公开 `ServeV2HTTP`、双向代理和独立清理观察。Worker 每块先报告真实处理进度，再发位置结果，EOF 后发尾部 final。客户端继续使用生产 `NewV2` / `Run`。
- [入口与验收](../../internal/gateway/client_resume_experiment_test.go)：固定五组配置、环境日志、完整 JSON、短时网络 probe、强制清理反例和分析测试。正式入口显式开启；每组先保留报告再给出验收结局，建环境失败也保留“未取得报告”的计划尝试。

输入每个字节位置使用固定种子的 xorshift32 序列，逐字比较 Worker 接收的真实音频；不能用静音的相同块冒充顺序一致。报告同时保留实际音频 base64、输入摘要和代理实际读取的块摘要，可独立核对。

重传量取代理读取的音频范围长度之和减去范围并集长度，包括故意读到后丢弃的帧。首次补发的断线期间新采集音频不算重复传输，Worker 收到重复内容仍会使完整性检查失败。

新音频恢复等待先找到故障后实际开始 Read 的第一块，再找覆盖其结束位置的已应用结果；重连后旧结果补发不会被误当作新输入恢复。代理 ready Write 返回只叫 ready 转发时刻，不声称是客户端接纳时刻。结果等待沿第一块 Read 的代理原点推导计划位置，包含调度、缓存、处理和网络开销，不是纯推理耗时。

## 并发与清理边界

每场独立 recorder，锁只保护内存记录，不跨 I/O 或计时等待；冻结报告深拷贝可变切片，清理失败时也不与活跃任务共享数组。报告保存实际生效的 Gateway/客户端配置，排除 URL、回调和身份凭据。

代理的前端只有一个 reader；它在等待通路开放时也能监测客户端关闭，避免恢复窗口已到期后仍把旧握手转发给 Gateway。每次交付帧须等转发方回执，才读下一帧，防止 EOF 越过尚未转发的 completed_ack。后端只有一个结果读取/前端写入任务；连接退出共同取消并等待任务结束。

业务期限、服务端生命期、自然清理观察期分开。客户端 Run 返回后继续采样服务端活动/握手计数、注册表、Worker 活动数，并核对 Gateway handler、代理 handler 和故障计时器退出；不通过先 cancel 服务制造自然归零。观察到期则固定记录 `forced_cleanup=true`，后续 stop 不参与自然清理指标。跨组件计数依次读取，报告保留采样调用起止，不宣称是跨组件原子快照。

清理等待实现使用 Run 返回后的首个共同空闲样本，因此即使已在返回前归零，也可能有极小的正观察延迟；没有前后可靠观测时不假定为 0。这是对预登记中“返回前归零记 0”的保守细化，业务判据、故障位置和恢复预算不变。

## 验证与首次失败

初版纯分析检查和初版五组真实网络/race 检查通过。补充时间顺序、配置、摘要、Worker 退出等交叉核对后，一项人工“连续三条低等待”计时样例失败：把第三条旧音频结果调到 305ms 后，其等待为 105ms，仍满足原样例 200ms 阈值，因此合法地提前参与连续计数。失败发生在测试预期，没有发现生产恢复逻辑错误。

人工样例改用明确的 50ms 阈值，保证旧结果不参与该例的连续计数，并同步对应 Worker 处理时间；**正式实验仍固定 200ms**。首次失败的完整 Go JSON 留存于 [analysis-first-failure](../experiments/results/client-resume-tool-analysis-first-failure-2026-10-09.jsonl)，不删除失败记录。

最终结果见下方验收记录。所有 probe 缩短输入、故障持续时间和恢复/清理预算；它们只证明工具行为，不能代替正式实验的恢复等待或成功率。

## 验收记录

新增 8 顶层、38 叶级检查全部通过 race，包括五组短时真实网络 probe 和一个自然清理失败后兜底场景。验证了预算内接回原 Worker、每块内容/顺序一致、结果连续应用、代理观测到第 20 块对应方式的单块重传（probe 在第 3 块触发）、断线期间继续采集、窗口到期后旧握手不再转发，以及 JSON 往返后重新分析保持一致。人工范围/计时检查覆盖重叠、乱序范围、缺失事件、旧音频与新采集音频区分、连续窗口中断及多类证据矛盾；冻结报告检查验证后续写入不改变副本。

全项目 `go test -race -p=1 ./... -count=1 -timeout=180s -json`：2704 叶级通过、0 失败、13 显式实验跳过（包含新正式恢复实验）；14 个包都有正常 pass/无测试 skip 终态。Go 1.26.5，darwin/arm64。测试数量表示检查规模，不是恢复成功率或性能收益。

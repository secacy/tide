# 群体恢复：尝试次数对照设计

日期：2026-10-11。关联 [EXP-006-02 基线结果](2026-10-11-group-resume-results.md)、[EXP-006-03 预登记](../experiments/group-resume-budget-comparison.md)。

## 当前问题与本步目标

上一轮八场共享 Gateway 的正式基线中，500ms 握手占位组完成 22/24，2s 占位组完成 0/24。后者全部在故障后约 1.51s 用完五次恢复尝试，入口约 2s 才开放；客户端虽然配置了 5s 恢复窗口，却已经没有剩余次数。前者还有两场在入口开放后连续被拒绝，耗尽次数。这是两种已经观察到的失败，不能笼统归为“恢复超时”。

本步确定一个可归因的对照：只把 MaxAttempts 从 5 改为 8，重新测量同版本的两种配置，观察完成率、请求成本、结果等待和原 RPC 保留时间。此次只完成设计与预登记；工具扩展、行为验收和正式测量随后进行，没有调整生产默认值。

## 原理：时间够，不代表机会够

当前 [恢复协调器](../../internal/wsclient/client_v2_run.go) 使用两个不同的限制：

- MaxAttempts 是整场 Run 累计启动的 resume Dial 次数。首次 start 不计；恢复成功也不会把次数清零。
- Window 是每轮断线的固定时间窗口，包含旧连接清理、退避和握手。恢复 ready 被接纳后清除本轮截止点；再次断线才开启下一轮窗口。

两者任一耗尽都可以停止恢复。一次握手若长时间等待，会消耗窗口；若很快被拒绝，会快速消耗次数。本实验每场只注入一次断线，用全新 Run 开始，因此不涉及前次恢复已经消耗预算的情况。不能据此声称八次配置足以覆盖长时问诊中的多次断线。

首次恢复在旧连接退出后立即开始，后续失败等待 100、200、400、800、1000、1000、1000ms。忽略清理、握手和调度耗时，以第一次恢复尝试为零点，理论时间轴如下：

| 尝试编号 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 相对时间（秒） | 0 | 0.1 | 0.3 | 0.7 | 1.5 | 2.5 | 3.5 | 4.5 |

五次配置在 2s 开放前就可能耗尽。六次提供一次开放后的机会，七次提供两次，八次提供三次，也能继续处理开放后的竞争；理论第九次在 5.5s，已越过 5s 窗口。因此选八次作为本轮候选，检验有限次数能否更充分利用已有窗口，而不是寻找最优次数。

这张表是快速拒绝下的推导，不是测量结果：窗口在旧连接清理前就已开始，握手和退避之间的处理也耗时；第八次可能因为窗口到期而根本没有启动。真实请求仍以代理事件计时，不能把表中的零点直接等同于代理故障 T0。

## 备选方案与本次权衡

| 方案 | 能解决什么 | 代价与此次选择 |
| --- | --- | --- |
| 五次改为八次 | 在相同退避下保留更多机会，可能等到开放并承受后续拒绝 | 请求上限增加，失败可能返回更晚；单独比较，原因容易解释，选作本轮实验变量 |
| 只延长 Window | 单次握手或清理很慢时能提供更多时间 | 本轮五次已提前用完，仅加时间不增加机会；暂不采用 |
| 增大退避间隔 | 用相同次数覆盖更长故障，减少早期请求 | 立即可恢复或短暂占位时可能等得更久；这是另一种预算分配，留作后续对照 |
| 加入 jitter | 分散同一时刻的恢复请求，可能减少开放后的竞争 | 同时涉及等待分布和平均等待；full jitter 在相同上限下通常缩短平均等待，不能保证五次撑到 2s，待预算对照后独立设计 |
| 增加握手名额 | 可能减少开放后的短暂竞争 | 改变服务端容量和资源；本轮两个名额在占位期间均不可用，先固定入口条件 |
| 服务端排队或提示何时重试 | 减少盲目快速重试，协调入口 | 需要新增队列预算、取消语义或协议约定；现有数据尚不足以支撑这项改造 |

八次不是生产推荐值。它增加了每场最多三次请求；一批八场的恢复请求上限从 40 到 64。是否实际用到这些请求、换来多少完整场、是否拉长失败等待，必须同时测量。

## 对照怎样做到可信

使用 D（占位 500ms）与 E（占位 2s）两个已暴露问题的场景，各测五次和八次、各三批。共 12 批、96 个计划会话，每个条件分母 24。正常组与立即恢复组已经建立夹具基线，不在本轮重复为正式条件；新增配置的正确性由单独 probe 验收。

两种预算用同一版本、一次构建重新测量。历史 22/24 和 0/24 只解释为何选这些场景，不代替本轮五次对照。每对条件相邻运行，交替先后顺序；各批重新创建夹具并等待自然空闲，避免继承积压。三轮每个场景的先后次数仍是 2:1，保留顺序局限，不宣称统计显著性。

完整性先于性能：每场保持原 RPC，音频逐字核对、结果按序应用，失败和未知项保留在计划分母。成功者变多可能改变时延样本组成，不能把两组成功者中位数相减称为同一个患者的延迟改善。

清理还需要避免一个误判：若客户端从 1.5s 改为 4.5s 才失败，而原 RPC 都在 T0 后约 10s 退出，“客户端返回后等待”会从约 8.5s 降为约 5.5s，但服务器并没有更早释放。因此同时报告 T0 到每条原 RPC 退出、T0 到整批自然空闲，以及客户端返回后的等待。八条 RPC 的故障后保留时长之和可表示 RPC·秒；这是原流存活成本，不是 CPU 计算时间。

## 当前能力到哪里了

当前客户端可以在原 Gateway 和原 Worker 流仍存活、身份有效且各项预算尚未耗尽时，接回原场，按位置补发音频并继续应用结果。客户端与服务端有独立的时间和缓存边界，不能把“支持恢复”理解为任意断线都能接回。

| 情况 | 当前行为与证据 | 仍然不能承诺什么 |
| --- | --- | --- |
| 原场存活，短暂断线 | [EXP-006-01](../experiments/client-resume-baseline.md) 中 500ms、2s 各三场均完成，六场音频完整、结果应用无重复、保持原 RPC | 代理暂扣恢复请求，未测快速拒绝下的连续重试或多人竞争 |
| 同条件关闭/开启恢复 | 500ms 中断完成数 0/3 → 3/3；成功恢复的六场，通路开放后新采集音频结果等待为 23.2–27.0ms | 小样本、位置 Mock、本机网络，不能当作生产 SLO |
| 超出客户端恢复窗口 | 6s 故障三场均明确预算耗尽，失败样本记录已采集、已处理和未覆盖范围 | 客户端返回不代表远端同步释放；服务端可能仍在等待自己的保留期限 |
| Worker 或 Gateway 实例失效 | [实例故障验收](2026-10-11-instance-failure-boundary.md) 覆盖受控停止、独立进程 SIGKILL 与原地址重启；旧场失败、存活端收尾、显式新场完成 | 没有跨实例恢复、模型上下文重建或音频持久提交 |

## 为什么下一步是群体重连

假设一条网络链路中断，同时影响八场问诊。通路恢复后，八个客户端都要重新握手。即使每场单独都能恢复，共用入口也可能只能同时处理其中几条；其余客户端需要在自己的预算内再试。

这里有两道限制：逻辑会话名额保留给原问诊；临时握手名额保护正在接入的连接。resume 不应再次申请逻辑会话名额，但仍须经过握手准入。先建立八场并设置 `MaxSessions=8`，可以验证满额恢复；再设置 `MaxHandshakes=2`，研究入口竞争。

源码依据：[entryGate](../../internal/gateway/entry_gate.go)、[公开入口](../../internal/gateway/handler_v2.go)、[客户端运行器](../../internal/wsclient/client_v2_run.go)。入口满额立即拒绝，不排队；客户端把 `handshake_limit` 视为可重试。

## 当前退避的关键边界

客户端在旧连接清理完成后立即首次恢复，失败后依次等待 100、200、400、800ms，默认整场最多五次恢复拨号。忽略连接清理、网络和调度耗时，快速拒绝时五次请求大约落在首次尝试后的 0、0.1、0.3、0.7、1.5s。

所以 `Window=5s` 不保证至少尝试五秒：次数可能先用完。以前的 2s 实验暂扣一次请求，没有制造五次快速失败。因此，那次 2s 恢复成功，不证明连续拒绝 2s 也能恢复。上述时刻只是代码推导，真实分布待测。

同时断线且采用相同确定性等待的客户端，后续请求可能仍聚在一起；网络与调度也可能自然将它们分散。先测聚集及其影响，不预设随机等待一定提高完成率。

## 备选方案与选择

| 方案 | 价值 | 代价与本轮判断 |
| --- | --- | --- |
| 保持确定性退避，建立共享入口基线 | 区分次数预算、入口容量与请求聚集各自的影响 | 本轮采用；建立事实后再选改动 |
| 增加随机退避（jitter） | 可能分散失败后的再试时刻 | 不能增加服务能力，也可能推迟部分请求；随机范围会改变平均等待及预算消耗，需单独对照 |
| 增加 MaxAttempts 或窗口 | 给暂时不可用的入口更多机会 | 增加请求量或保留时间；多次断线还共享整场次数预算 |
| 增大 MaxHandshakes | 允许更多握手同时进入 | 增加临时连接和处理工作量；不能凭八场样本定生产配置 |
| 服务端排队或建议重试时间 | 表达入口等待策略，减少盲试 | 新增队列预算、取消/期限管理或协议语义，当前尚无证据要求引入 |

首次恢复是否也加随机等待，与失败后的退避是两个决策。前者可能分散第一波，也会使原本能立刻恢复的会话等待。后续比较策略须明确平均等待、上限、次数、随机种子及首试规则的差异。

## 如何验证及后续步骤

采用一个共享 Gateway、一个支持多流的位置 Worker、八个独立客户端和一个可控代理。沿用真实 WebSocket/TCP gRPC、固定采集时间轴、音频逐字检查及结果应用序号。旧实验每场创建独立 Gateway，不能简单并行调用它来测共同入口。

自然竞争与确定性满额分开观察。后者用两条真实连接完成 WebSocket 升级后暂不发送首条消息，只占握手名额，不创建逻辑会话或 RPC。它模拟入口资源暂时不足，不冒充实际网络丢包或生产握手耗时。只在代理前等待不会占 Gateway 名额；客户端数大于名额也不保证发生拒绝，因为本机握手可能很快。

具体条件见 [EXP-006-02 预登记](../experiments/group-resume-baseline.md)。接下来按三个可验收步骤推进：

1. 助手实现共享夹具及行为测试，验证多场输入/RPC 关联、统一故障、真实拒绝传播、满额恢复和自然清理；失败也输出报告。
2. 助手完成采集、分析与五组各三批正式非 race 基线，保留全部计划会话和原始事件。race 只验证并发行为，采样峰值不作为严格资源上限。
3. 依据结果决定业务改动：次数先耗尽则讨论预算；请求明显聚集并伴随重复拒绝则设计 jitter 对照；没有问题则保留方案并说明范围。核心改动先解释设计，由开发者实现或另行明确委托。

本步完成能力梳理和实验预登记，第六阶段仍在进行中。长时多次断线、隐蔽半开连接、真实模型及临床环境尚无新证据。

## 共享夹具与行为验收（2026-10-11）

已实现 [group_resume_harness_test.go](../../internal/gateway/group_resume_harness_test.go) 和 [group_resume_test.go](../../internal/gateway/group_resume_test.go)。一个 Gateway、一条共享 TCP ClientConn、一个多流位置 Worker 与一个代理服务承载八个独立客户端；故障前实际观察到八场注册、八个逻辑名额与八条活动原 RPC。不同场的首块编码实验编号，整场内容不同，Worker 按编号绑定记录器而非按建流顺序；结果附带编号，客户端应用前再次校验。

每条初始连接在第三块音频处等待位置屏障，统一放行或关闭。占位连接经过真实 WebSocket 升级，只占临时握手名额；释放时间在对应 handler 返回、gate 已归还名额后记录。Gateway 的升级前 HTTP 503 错误体由代理传入前端 v2 error，记录真实状态、错误码及写出事实；失败客户端返回错误中还可提取 `handshake_limit`，不只依靠代理写成功推断客户端收到。

串行启动使用 ready 和首次源读取的事件通知，没有在 Read 内阻塞，也没有按采样间隔拖慢逐场初始化。客户端、故障任务、占位计时器、代理及 Worker 收尾分别等待；报告冻结时复制可变切片。独立自然观察失败后才取消服务，强制收尾不能回填自然空闲时刻。

### Probe 条件与观察

本步是行为验收，不是 EXP-006-02 的正式条件：每场八块 × 3200 字节（0.8 秒音频）、第三块屏障、Worker 每块 1ms；客户端窗口 2s、初始退避 20ms、上限 80ms，默认五次尝试；服务端保留 1s、业务观察 5s、自然清理观察 2s、采样 2ms、同步偏差上限 500ms。正式预登记的六秒输入、100ms 初始退避、500ms/2s 占位及 50ms 同步判据保持不变。

最终五组各重复三轮，每轮八场，共 120 个群体 probe 会话：

| 组 | 特有条件 | 三轮观察 |
| --- | --- | --- |
| A_normal | 两个握手名额，不切断 | 24/24 原场完成，无恢复拨号 |
| B_resume_h8 | 八个握手名额，统一切断 | 24/24 原场恢复并完成 |
| C_resume_h2 | 两个握手名额，统一切断 | 24/24 原场恢复并完成；三轮实际握手拒绝 5/7/5 次 |
| D_busy_short | 两个握手名额占用 40ms | 24/24 原场恢复并完成；三轮实际握手拒绝 21/20/23 次 |
| E_attempt_exhausted | 占用 200ms，最多两次尝试 | 0/24 完成，24/24 明确 recovery_exhausted；各场尝试两次，最近入口原因 handshake_limit，次数先于 2s 窗口耗尽 |

每批保持 Pick/RPC 各八次，没有替代 start 或串场。成功场 Worker 逐字处理 25600 字节、九条结果按序应用并完成 completed/completed_ack；失败组只处理屏障前 6400 字节并应用两条结果。全体源关闭一次，15 批在最终停服之前自然归零，包含原场、注册、握手、RPC 与代理任务。这里只说明当前 probe 行为；拒绝次数受调度影响，不能作为正式退避收益或吞吐数据。

额外的反例验证不计上述 120 场：17 项报告反例覆盖分母、身份、原 RPC、音频/帧摘要、源范围、处理记录、结果顺序/位置、完成事实、清理、屏障和计数；12 项非法工具配置检查；一项真实强制清理反例把自然观察缩为 10ms，保留八场失败及未自然退出事实。错误日志中的 holder release canceled 是该反例的预期注入，不是被掩盖的正式样本。

## 采集与分析工具验收（2026-10-11）

本步完成可复核的测量工具，不执行正式 15 批测量。只有测试日志里的“通过”无法解释恢复等待、失败音频缺口和请求聚集，也无法追溯当时实际生效的条件。直接在 Go 报告中计算所有指标实现较省事，但若记录和计算共用错误假设，难以发现问题。因此保留原始字节/位置/时间事件，由独立 Python 分析重新检查并计算；代价是报告和归档较大，需要维护明确版本。暂不新增监控中间件，这些事件已经足够支撑当前固定实验。

### 本步实现

1. `group_resume_experiment_test.go` 固定正式五组条件，默认跳过，显式开启且非 race 才运行；故障组的真实业务失败不自动判为工具失败。A 正常组要求完整完成，工具/正确性失败仍输出观察。
2. 群体报告 version=2，字段使用 snake_case 和明确纳秒单位；复用单场记录器，但去掉旧单场配置/派生指标。保留实际 Gateway v2 副本、客户端条件和每场输入摘要。race 标记由 build constraints 决定，记录实际 Go/OS/架构、CPU、GOMAXPROCS 和同进程 loopback 拓扑。
3. 增加整进程 goroutine、HeapAlloc/HeapInuse 采样，保存调用起止时刻及间隔。定期与屏障采样通过独立 sampleMu 串行化，避免先采样后写入的调度差异造成时间乱序；不持有报告锁跨网络 I/O，不宣称组件快照原子一致。
4. [采集脚本](../experiments/scripts/run_group_resume.py) 独占新目录，快照全部相关 Go/proto、依赖清单、实验工具及预登记，保存 SHA256、commit、工作区状态、环境和参数；构建一次，再执行固定入口。源码变化、构建/运行失败、丢批或强制清理保留原记录，不重复覆盖以换取通过。
5. [独立分析](../experiments/scripts/summarize_group_resume.py) 按 Test 重组拆分的 Go Output，核对场数/顺序、实际配置、逐字输入、原 RPC、连续结果、真实升级/拒绝及自然退出。分别统计 Dial 尝试、代理到达、解析 resume 和后端请求；50ms 桶含首波、重试、拒绝与空桶，覆盖 T0 至整批业务返回。
6. 输出原始报告、逐场 CSV、请求桶 CSV、固定分母汇总及分析摘要。实际读取到应用的等待与固定采集时间轴到应用的等待分别计算；采集缺口、接收缺口和处理缺口分开。没有新音频结果或 ready 时用 null，成功场时延明确样本数，同时列业务失败/未知会话。

macOS 正式采集使用脚本自有 caffeinate 进程，并记录是否提前退出；结束只关闭自己启动的进程。保持唤醒不替代采样间隔和输入同步检查，不能自动证明操作系统从未暂停。

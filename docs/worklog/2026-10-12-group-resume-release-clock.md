## 原因与方案

当前 Go `Time` 保留单调时钟；有该分量的 Sub/Before 使用它，Add 同时增加两个分量。MarshalJSON 丢弃单调分量，Python 从 RFC3339Nano 解析的是墙钟。该行为已从本机 Go 1.26.5 标准库 `src/time/time.go` 文档核对。由同一对时间的 Go 检查通过、导出间隔不足可知，本轮两种口径存在差异；不是 Python 纳秒解析精度损失。

现有注入只等一次单调定时器，然后归还占位连接。选择补足故障注入的约束：定时器唤醒后检查“单调剩余”和“墙钟剩余”的较大值，两者都非正才开始关闭占位连接；其后仍等真实 handler 归还名额再记录释放。内部证据校验也检查两种 Before。

没有给独立分析增加容差，也没有改写原时间戳。若墙钟偏慢，实际占位可能增加少量等待；实际释放时刻继续如实记录，原判据本来就要求至少配置时长，并允许 handler/调度带来的延后。若墙钟反复后退，业务 context 仍限制等待，注入会明确失败，而不是无限占位或制造合格证据。

另一种方案是在全体事件导出单调偏移。这能让时延测量更独立于墙钟，但需修改源、代理、Worker、结果和采样的完整报告口径；当前问题集中于故障占位下限，先修复注入。墙钟时延仍可能受小幅调整，结果不会声称精确的亚毫秒差异。单纯放宽下限会改变已登记判据，未采用。

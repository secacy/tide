# 第六阶段：长问诊恢复预算评审

日期：2026-10-13。状态：设计与实现指导；尚未修改业务代码或验证新策略。依据[十分钟多轮结果](2026-10-13-repeated-resume-extended-results.md)与[堆诊断结果](2026-10-13-repeated-resume-heap-results.md)。本步由开发者实现核心逻辑，助手随后评审并补测试。

## 问题与目标

当前 `V2ResumeConfig.MaxAttempts` 默认 5，计数覆盖整个 Run，成功恢复也占用一次。EXP-006-05 的 C 两场均在第六轮断线耗尽；B 的八次预算两场均完成六次恢复。这证明当前规则确实执行，并暴露了它与长问诊的矛盾：前几分钟的偶发故障，会永久消耗后面几十分钟的恢复机会。不能据此认定八次就是合适的生产默认值。

目标是允许相隔较久的恢复机会重新可用，同时限制短时间密集重连。保留同一会话身份、原 RPC、有限重放及完整退出；已有默认配置和实验基线保持原语义。指标继续记录整场尝试总数，不能因为限额更新而抹掉历史。

## 方案与取舍

| 方案 | 价值 | 代价与判断 |
| --- | --- | --- |
| 提高整场次数 | 改动最少，整场尝试上限清楚 | 只是延后耗尽，没有解决会话越长越容易用完的问题 |
| 每轮断线重新给 N 次，接纳 ready 后清零 | 易理解，也能处理分散故障 | ready 后立即断开也重新获得预算；现有首个恢复尝试不退避，短时反复成功握手可能绕开连续失败退避 |
| 连续稳定一段时间后清零 | 不因短暂 ready 就立即补满 | 必须定义稳定是保持连接、音频确认还是新结果推进；静默、尾部及 Worker 变慢使规则更复杂，整批清零仍存在边界突发 |
| 最近 W 时间最多 N 次尝试 | 旧尝试自然过期，成功握手不重置，适合同时区分零散故障和密集抖动 | 需要有界时间记录；仍允许 N 次短时突发，不保证各次均匀间隔，也不限制整场总次数 |
| 固定时间桶或令牌桶 | 前者状态少，后者可按速率补充额度 | 固定桶边界两侧可聚集两批；令牌桶的速率/突发语义不同于最近 W 内最多 N 次。当前规模下不值得为减少几个时间戳改变语义 |

建议显式启用精确滑动窗口，并保留已有每轮 `Window`。前者控制近期拨号数量，后者控制一次故障最多尝试多久；两者解决不同问题。沿用现有退避和可选 jitter。客户端的单场预算不替代 Gateway 握手准入，也不证明多个客户端同步故障时安全。

采用兼容选项而非直接改变 `MaxAttempts` 默认含义：旧调用方和冻结实验不应在升级后悄悄改变结果。当前不叠加第三个整场硬上限，避免再次让零散故障耗尽；调用方 context、完成期限和缓冲上限继续生效。如果产品以后要求一场最多自动恢复多少次，再单独定义。

## 建议契约

在 `V2ResumeConfig` 增加：

```go
// AttemptWindow 为恢复尝试计数的回看时长；负值非法。
// 0 保持 MaxAttempts 限制整个 Run；正值限制最近该时长内的尝试数。
// 与 Window（一次断线的恢复期限）独立，不在成功 ready 后重置。
AttemptWindow time.Duration `json:"AttemptWindow,omitempty"`
```

同时更新 `MaxAttempts` 注释，说明由 AttemptWindow 决定计数范围。零值不填充为正时长，旧 JSON 格式保持不变。`Resume == nil` 仍关闭自动恢复，NewV2 继续复制配置。

契约细节：

1. 时刻 t 准备开始恢复时，只计算 `(t - AttemptWindow, t]` 内已启动的恢复尝试。恰好满一个窗口的旧记录已过期；使用进程内带单调时钟的 time.Time，不转 Unix 秒判断。
2. 沿用当前 startHandshake(true) 的计数点：协调者启动恢复握手任务时记一次。失败、握手拒绝及成功接纳均消耗额度，首次 start 不计。它是本地启动尝试的事实，不保证 TCP SYN 已上网或服务端收到请求。
3. 成功接纳合法 ready 仍结束本轮恢复期限并重置退避失败数，但不清空滑动记录，也不清空整场 attempts / ResumeAttempts。
4. 需要恢复时如果已满，立即返回 ErrV2RecoveryExhausted 并保留最近故障原因，不排队等最早记录过期。窗口耗尽与次数耗尽的错误语义沿用现有区分。
5. 不等待额度是明确取舍：等待期间音频仍产生，服务端原场可能过期，最后未必能恢复。本次只允许正常运行期间旧额度自然过期；一次耗尽导致 Run 返回后，不会自动复活。
6. 恰好第 N 次尝试成功，可以继续正常工作；只有需要下一次尝试且近期额度仍满时失败。额度检查不应放进每轮都会执行的 checkBudget，避免刚用完最后一次就立即结束正常传输。
7. `Window`、握手期限、完成期限及调用方取消保持现有优先关系；任何一次失败或额度过期都不能续期本轮恢复期限。缓存满、源/协议/回调错误等既有终止条件仍直接终止。
8. 不新增 goroutine、锁或清理定时器；记录由现有协调者独占，在需要检查时清除过期项。最多保留 MaxAttempts 个有效时间戳，避免保存整场全部历史或预分配任意大的用户配置。

例：仅作为可控验证参数，MaxAttempts=5、AttemptWindow=60s、Window=5s。相隔 90s 的六轮断线，每轮一次尝试成功，整场 ResumeAttempts 最终为 6；短时间五次 ready 后立即断开，第六次恢复请求不应启动。持续失败仍可能先因 5s 单轮期限退出。60s 不是已经验证的生产建议。

## 实现入口与顺序

只需先完成 wsclient 中一组完整能力，不先扩展 CLI、负载工具或调整实验参数：

1. `client_v2.go`：增加配置、负值校验和注释，保留所有原默认值与独立配置副本。
2. `client_v2_run.go`：在 v2RecoveryState 保留 attempts 作为整场统计，增加 attemptTimes。成功 ready 分支不清空它。
3. 把 recover 和 coordinate 的两处次数判断收拢到同一方法；启动前再次检查，在 startHandshake(true) 唯一位置计数。避免一个入口看累计、另一个入口看窗口。
4. 清理过期项可先采用小 slice 原地压缩并清零尾部，按需追加；成本为 O(N)，N 是配置额度。环形队列是可选实现，不是这一步的必要组件。正常流式循环不扫描记录。

建议骨架（名称可按项目习惯调整）：

```go
// attempts 保持原字段；以下字段仅协调者访问。
attemptTimes []time.Time // 滑动模式的近期启动时刻；有效记录数不超过 MaxAttempts。

// resumeAttemptAllowed 清除过期记录后判断是否还有额度，不消耗额度。
// now 使用本次事件的当前时间；累计模式仅检查整场 attempts。
// 只在可恢复故障和准备启动恢复握手时调用，不限制正常 streaming。
func (r *v2ClientRun) resumeAttemptAllowed(now time.Time) bool

// recordResumeAttempt 在确认有额度并启动恢复任务时调用一次。
// 累计统计两种模式都递增；只有滑动模式追加 now，不记录首次 start。
// 检查与记录由同一协调者串行完成，无其他 goroutine 抢占额度。
func (r *v2ClientRun) recordResumeAttempt(now time.Time)
```

实现时统一 startHandshake 内的时间读取用于记录和本次握手期限计算。辅助方法需要 Resume 非 nil 的调用前提；初始 start 不访问恢复配置。不要把 failures 复用为本轮或窗口尝试计数，它只表达连续失败退避。

## 验收与后续两步

开发者实现后，助手评审并补可控时钟测试：旧默认累计语义/JSON 不变；新配置负值拒绝及副本隔离；超过整场 N 次的分散恢复允许；近期密集恢复拒绝且无第 N+1 次 Dial；失败握手也计数；恰好窗口边界、只释放最旧部分额度及迟到 ready；成功不抹掉历史；单轮期限/完成期限不续期，取消与自然清理仍有效。旧累计测试保留原断言，新增场景不能靠改旧期望制造通过。

下一步用真实 Gateway/TCP Mock 做短场组合验收：分散故障、密集 ready 后再断、持续握手失败，核对原 RPC/Worker pick、输入结果完整性、实际尝试数与退出。之后再决定是否做一次长时策略对照，预登记同负载下累计/滑动策略的完成率、耗尽轮次、尝试数、音频缺口和资源回落；旧证据不覆盖，不先重跑堆诊断。

本步结果是澄清预算的适用范围与可检验契约；新策略尚无完成率或性能收益数据。第六阶段仍在进行，第七阶段尚未开始。

# 多轮恢复堆诊断：目的、方案与实现边界

日期：2026-10-13。状态：设计及预登记完成，[工具及短场验收](2026-10-13-repeated-resume-heap-tools.md)已落地；[正式四场诊断](2026-10-13-repeated-resume-heap-results.md)已核实，分配路径已分类，原自然 GC 增长未完全归因。依据[十分钟正式结果](2026-10-13-repeated-resume-extended-results.md)，执行条件见 [EXP-006-06](../experiments/repeated-resume-heap-diagnostic.md)。

## 要解释的现象

EXP-006-05 五个时间/资源合格场中，四个触发 HeapAlloc 增长线索。正常 A 第一轮首窗→尾窗最小值增加 26424 字节，恢复 B 第一轮增加 49040 字节。与此同时，31 个合格窗口 goroutine 均为 30，原场最终自然归零。

目前只能说“有一小部分堆值得检查”。HeapAlloc 包含尚未回收的垃圾；HeapInuse 包含已使用的堆 span，也不是业务对象净大小。窗口最小值没有保证处于完全相同的 GC 阶段。计数归零证明任务/会话退出，却不能说明哪些对象还被引用。

下一步的目标是找到增长对应的分配调用栈，并观察这些对象在自然结束、环境拆除后是否回落；不凭总量曲线直接修改业务代码。

## 备选方案与取舍

| 方案 | 能回答什么 | 局限与本次选择 |
| --- | --- | --- |
| 只延长原实验、继续采 HeapAlloc | 增长是否随时间持续 | 仍不知道对象来源，重复长测定位价值有限；暂不采用 |
| 只用 `go test -memprofile` 保存结束时快照 | 结束时有哪些分配栈 | 丢失运行早晚及会话结束前后的差异；可作简单起点，但不足以解释本次现象 |
| 为服务添加 HTTP pprof 端点 | 外部随时取样，适合后续独立服务诊断 | 当前客户端/代理/Worker/网关同进程，增加端点也不能自动分离各自内存；当前无需新增业务入口 |
| 专用测试进程固定时点写 heap profile | 同一进程内比较早晚、自然结束、拆除后的调用栈 | 采集会扰动运行；采用，单独标为诊断，不重写原性能结论 |
| 一开始就关闭记录器或拆成多个进程 | 可做观测开销或进程边界对照 | 同时改变证据、拓扑和资源条件；待分配栈给出方向后，再设计有针对性的对照 |

采用 A 正常、B 六轮恢复两组，两轮 A→B、B→A，共四个独立进程。两组都运行完整十分钟，便于比较相同运行长度；本轮先不增加提前结束的 C，也不调整恢复预算。这个规模用于定位线索，不估计生产泄漏率。

## 怎样读懂五个快照

| 快照 | 时点与资源状态 | 用途 |
| --- | --- | --- |
| P0 `before_fixture` | profile 编码预热后，尚未建立服务环境 | 记录测试运行时/诊断器基线 |
| P1 `early_active` | 首块开始后 90s，原会话仍活动 | 排除部分初始化影响的早期基线；B 已有一次恢复 |
| P2 `late_active` | 首块开始后 570s，原会话仍活动 | 与 P1 比较后续 480s 及 B 后五次恢复期间的存活分配变化 |
| P3 `session_idle` | 会话自然归零，尚未拆除共享测试环境 | 看逻辑会话退出后哪些分配消失、哪些仍被环境保留 |
| P4 `after_fixture` | 核实连接关闭、服务 Serve 退出和夹具拥有的任务退出，场景作用域返回 | 与 P0 比较拆除后的残留，并与 P3 区分正常环境保留 |

代码核对发现：[网络夹具](../../internal/gateway/network_fixture_test.go)用 `t.Cleanup` 关闭 gRPC ClientConn、停止服务器并等待 Serve 退出；[当前运行器](../../internal/gateway/extended_resume_harness_test.go)记录 `natural_idle` 时，这些清理尚未执行。因此不能在 `runExtendedProbe` 返回前把一次 GC 后的堆叫作“整个环境已释放”。

诊断外层用非并行子测试承载完整场景；子测试所有清理完成后，外层才取 P4。实现须补可核实的关闭/退出结果，不能只依赖函数名或一次 goroutine 数量下降。这里的拆除指夹具拥有的任务已 join、连接 Close 返回、服务 Serve 退出；不能据此断言第三方库内部所有后台任务都已退出，库侧残留仍须结合调用栈解释。外层只保存配置、数值摘要、路径和关闭结果，不保存 Gateway、Client、Worker、连接或捕获它们的闭包。即使 P4 仍有分配，也可能是运行时、测试框架或库缓存，需要查看调用栈，不自动认定会话泄漏。

## 采集原理与代价

`runtime/pprof` 的 heap profile 同时带存活量和累计分配量：`inuse_space` / `inuse_objects` 用来找仍存活的字节/对象，`alloc_space` / `alloc_objects` 用来解释分配压力。累计分配持续增长本身不证明泄漏。profile 展示分配栈，不提供“谁正在持有这个对象”的引用图；找到可疑栈后仍要回到代码检查所有权。[Go 1.26.5 pprof 文档](https://pkg.go.dev/runtime/pprof@go1.26.5)

默认 MemProfileRate 是 512KiB，本次变化只有几十 KB，默认采样可能遗漏关键对象。专用子进程从启动时设置 `GODEBUG=memprofilerate=1`，全程核对 rate=1，避免中途改变比例。代价是更高采集开销，所以先用缩短 probe 验证能否维持原场，再冻结正式工具版本；如成本不可接受，应先修订方案、记录新采样率及精度限制，再运行，不能看完正式结果后改口径。[Go 1.26.5 runtime 文档](https://pkg.go.dev/runtime@go1.26.5#MemProfileRate)

每个快照固定先读 MemStats，再连续执行两次 `runtime.GC()`、再次读 MemStats，随后写二进制 heap profile，并记录结束统计与完整耗时。这里两次 GC 是一致的诊断干预，不是“运行中对象必然全部释放”的保证；后台任务可能继续分配，统计和 profile 也不是同一个原子快照。GC 会改变缓存保留和调度，尤其可能清除 sync.Pool 内容，因此诊断未复现增长不等于原现象不存在。此流程参考 runtime 内存 profile 的 GC 周期记账及 pprof 的最近 GC 语义，具体有效性还需已知存活/释放对象的工具验收。[runtime MemProfile](https://pkg.go.dev/runtime@go1.26.5#MemProfile)

保留 HeapAlloc、HeapObjects、HeapInuse、HeapIdle、HeapReleased、HeapSys、StackInuse、BuckHashSys、NumGC 和累计分配，以免把 span 保留、剖析器元数据或分配压力全部算作业务存活对象。不用强制向 OS 还页的方式人为压低结果，也不把这些数值当 RSS。

## 实现划分与约束

实现工作由助手负责，均在测试/实验工具范围：

1. **独立快照写入器。** 接收快照名、计划时点和数值状态，串行完成 GC、profile 写入、Close 及元数据记录。文件独占创建；部分文件、写入/关闭失败和退出错误保留。外部拥有的测试进程期限处理不可取消的采集/磁盘卡住。
2. **测试夹具可选观察点。** 原入口仍走无诊断的路径；专用入口增加独立 profile 调度任务，在已有首块单调时间后定时触发 P1/P2，P3 放在自然空闲与环境拆除之间。不在会话协调循环、源 Read、结果回调或持锁位置同步采集。任务必须取消并 join；晚到、错过或跨越 Run 返回的快照明确无效，不改名成成功时点。
3. **完整环境拆除。** 在子测试清理中确认 gRPC 连接关闭、服务 Serve 退出、HTTP/代理/采样/profile 任务退出，外层不保留业务实例；P4 从子测试返回后采集。无法确认拆除时保留 P4 诊断文件并标记状态不合格。
4. **轻量外部编排与离线对比。** 复用已有源码冻结、独占目录、逐进程执行和归档能力；新诊断清单固定四场，不冒用 EXP-006-05 的六场 manifest。原事件格式沿用，profile 元数据单独保存，避免改变已验收分析器的事件 schema。复用逐场完整性核对，另外核对快照阶段、GC/rate、产物和拆除状态。

重点接口可围绕以下责任命名，具体签名在实现时保持最小：`captureHeapCheckpoint` 负责单个快照及文件生命周期；`heapCheckpointRunner` 只拥有固定计划、串行采集及停止等待；`runHeapDiagnosticCase` 负责子测试边界与 P0/P4。诊断器不能持有整个历史事件列表，快照元数据至多五条，profile 直接写文件。

## 如何分析及决定后续动作

使用受测二进制和相同 Go 工具版本，对 P2−P1、P3−P2、P4−P0 生成四种 sample_index 的差分，保存完整 profile、raw 和不裁剪节点的 top 报告。保留负值，不归一化、不把多个函数的 cumulative 值相加；先看具体分配栈，再解释来自业务、网络库、记录器或诊断器的路径。不能因为堆栈包含测试入口就把整条调用链都归为工具开销。

- 运行后期增加、自然结束后消失：支持本次观察中与活动会话有关的暂时保留，仍需解释增长为何出现。
- P3 保留、P4 消失：支持完整环境所持资源造成差异，不把尚未关闭的共享 gRPC 环境当作会话泄漏。
- 两次独立运行均出现相同栈的活动期增长，且 P4 仍高于 P0：升级为优先检查项，核对具体引用和释放路径；四个场本身仍不证明无限增长。
- 只见累计分配增长、存活差分无一致增长：先解释分配压力和 GC，不据此直接做泄漏修复。
- profile 未复现、对象来源歧义、采集导致业务失败或清理未完成：结论为未定位，保留证据；再决定是否补无强制 GC 对照、缩小采集频率或做同进程重复生命周期诊断，不随意加长全部实验。

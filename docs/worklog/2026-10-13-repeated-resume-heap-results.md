# EXP-006-06：十分钟四场堆诊断结果

日期：2026-10-13。依据[预登记](../experiments/repeated-resume-heap-diagnostic.md)、[工具验收](2026-10-13-repeated-resume-heap-tools.md)。四场正式诊断完成，已定位若干分配来源与阶段差异；没有新增业务修复或内存优化，未证明整个进程无泄漏，原自然 GC 条件下的小幅增长尚未完全归因。

## 运行与证据资格

冻结 bda6e26，332 份源码/计划，单次非 race 构建，A→B→B→A 四个独立进程，条件与预算均未调整。2026-10-13 14:40:59–15:21:01（Asia/Taipei），采集运行窗口 2402.109s；分析/归档在窗口之后执行。每场 6000 块、3200 字节/100ms，Mock 每块 10ms；B 在 30/120/210/300/390/480s 各阻断 500ms，八次累计预算。

全部四场从原事件核实完整输入摘要、连续位置、结果顺序、尾部、完成确认、原 RPC / Worker pick、源关闭及自然空闲；每场 19,200,000 字节、6001 条结果，合计 76,800,000 字节、24004 条结果。两个 B 各六次恢复，没有替换 RPC。四场均无兜底清理，ClientConn Close / Serve 退出及夹具拥有任务 join 核实。20/20 快照阶段有效，160/160 pprof 命令成功，stderr 无警告。

源码摘要前后不变；自有 caffeinate 在清理前仍运行，睡眠审计成功且无 Sleep/Wake/DarkWake 转换。本轮原节奏/采样判据四场均合格：最大源计划落后 35.801ms，最大采样间隔 131.123ms；28 个固定窗口均在线合格，goroutine 范围 31–32，末窗采集任务退出后出现 31。它们只说明此次剖析干预下的观察质量，不替代 EXP-006-05 延迟结论。

20 个快照的固定 GC / WriteHeapProfile / Close / 最终 MemStats 耗时 20.613–107.734ms，八个活动点开始迟到 1.311–2.292ms，低于固定 1s 上限。完整原始证据见[归档](../experiments/results/repeated-resume-heap-2026-10-13-run-1/README.md)。

## 先分清三种数值

MemStats 描述读取瞬间的堆；heap profile 描述分配栈的已发布记账；累计分配量描述分配压力。后台音频和采样继续运行，二者不构成原子快照。runtime 文档也说明内存 profile 可能滞后 GC 周期，不能把不同口径的差额直接拼成某个对象的大小。[Go runtime 文档](https://pkg.go.dev/runtime@go1.26.5#MemProfile)、[pprof 文档](https://pkg.go.dev/runtime/pprof@go1.26.5)

下表 MemStats 使用各点 `after_gc`，profile 使用完整 raw 样本精确求和，均为 P2−P1。符号为真实正负变化；没有归一化、删除负值或把 cumulative 多次相加。

| --- | ---: | ---: | ---: | ---: |

A1 的约 49KB HeapAlloc 差不能写成“profile 查出了同样 49KB 存活对象”；两种采集数值都保留，时点和 GC 记账差异提供机制解释，未将具体差额逐对象归因。两场正常组不一致，四个独立进程也不支持估计泄漏率。P1→P2 整个同进程客户端/网关/Worker/记录器/诊断器累计分配约 409–415MB，并非网关自身净消耗。

## 拆除后保留来自哪里

P4−P0 的 profile 存活差为 223320、227480、237960、223960B（与同点 MemStats 差相同）。仅 JSON 字段缓存与 HPACK Huffman 构建路径即覆盖差额的 51.9%–54.0%；这两组路径不重叠，比例使用 raw 样本计数，未相加 cumulative。

| 槽位 | JSON cachedTypeFields 路径差（B） | Huffman 表构建路径差（B） | 拆除后总存活差（B） |
| --- | ---: | ---: | ---: |
| A1 | 81040 | 39664 | 223320 |
| B1 | 83264 | 39664 | 227480 |
| B2 | 83728 | 39664 | 237960 |
| A2 | 80400 | 39664 | 223960 |

本机 SDK 的 JSON `fieldCache`/`encoderCache` 为全局类型缓存；HPACK 的表经 `sync.Once` 建立并保存在包级根。它们的 P1→P2 存活差均为零，主要解释启动后与 P0 的差，不用它们解释晚期增长。诊断元数据编码及终态序列化也会建立类型缓存：经过 `heapCaseObserver.capture` 的 P4−P0 路径约 16.5–16.9KB，包含共享缓存等，未把该整条调用链自动认定为独占诊断器对象。实际复核源码与 SHA 保存在归档的 source-references 中。[JSON 源码对照](https://go.dev/src/encoding/json/encode.go)

另有 `runtime.malg`、`allocm` 等运行时分配。特别是代理、协调者、submitCommand 的 `select` 位置出现许多约 112B 条目，容易被误读为会话或命令越积越多。代码位置不是构造音频或结果；本机 `select.go` 分配等待节点，退出选择时清除 elem/c，再交还 `proc.go` 的 P/中央 sudog 缓存。其大小和路径与此机制一致，支持运行时等待节点缓存的推断；profile 没有对象类型或引用图，所以没有逐条证明它们都是 sudog。[运行时机制对照](https://go.dev/src/runtime/proc.go)

晚期增长的重复候选已按预登记检查：B 两场都有运行时 G/M 路径增长，也有上述 select 位置条目，但固定会话/缓冲构造路径无增长、退出为零。具体旧自然 GC 条件下的持有关系仍未证实，不能把缓存推断包装成已经修复的泄漏。

`BuckHashSys` 从每场约 1.95MB 增到拆除时约 3.23–3.30MB，是剖析等哈希记账资源，另表保留；没有把它混入 HeapAlloc、profile 合计或 RSS。全量剖析及 GC 干预的开销因此不仅是几份 profile 文件。

## 可复算性与限制

存档保留原 `.pb.gz`、完整 top/raw（四种指标、五个绝对点、三类差分）、命令及错误流。小格式器只整理 raw 样本和完整符号栈，保留负值/未知符号；32 个 raw 文件没有缺符号条目，12 份逐场差分在四项指标上均与绝对样本相减精确一致。五个新格式器反例通过，含负值与 inline 栈、错误 rate/计数列、缺位置、未解析数字行、未知符号。

原目录冻结分析器复算 325 个分析文件逐字节一致；722 文件全部归档读回摘要一致；搬移后冻结复算 325 文件、格式器的完整栈 JSON / 三份 CSV 分别逐字节一致，见归档验证清单。本步 Go 业务/夹具/采集器未修改，沿用 bda6e26 的验收，没有重跑无关测试。独立复算是可复核证据，不是分析天然正确的保证。

本轮进展是把“小幅总堆增长”细化到固定业务存储释放、分配压力、启动后的共享缓存、运行时等待节点候选及未解释残留。强制 GC 会影响池缓存，全量剖析改变调度；四场、单会话、可控 Mock 和本机网络不支持严格进程内存上界、生产无泄漏、真实 ASR 性能或群体长时稳定性结论。EXP-006-05 的原质量降级与原自然 GC 增长事实保留。

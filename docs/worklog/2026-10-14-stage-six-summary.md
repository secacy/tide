# 第六阶段总结：同实例有限恢复与验收边界

日期：2026-10-14。代码参照 `47cec51`；实验分别使用各自报告中的冻结版本。本步整理已有实现与证据，没有新增实验、修改业务代码或调整默认参数。承接 [10 月 12 日检查点](2026-10-12-stage-six-review.md)，补齐此后多轮断线、十分钟观察、堆诊断及滑动预算对照的结论。

**阶段判断：第六阶段在当前 Mock 与可控故障范围内已验收，可以进入第七阶段接入前评审。** 这里验收的是同一存活 Gateway / 原 Worker 流上的有限恢复，以及状态丢失时明确失败和新场可用；不包含跨实例无损恢复、真实临床时长稳定性或生产可靠性承诺。

## 背景、难点与目标

前五阶段已能持续转发音频、控制积压并分配 Worker，但网络连接与一次问诊的寿命不同：连接可能短暂中断，音频仍在产生，Worker 也可能继续处理已经收到的内容。直接结束问诊会截断后续记录；简单重连又不知道哪些音频已被接纳、哪些结果已被应用。重复发送可能重复处理，跳过发送可能留下缺口，而从头新建 Worker 流还会丢失原识别上下文。

难点是让客户端、Gateway 和 Worker 对“继续到哪里”保持一致，同时约束断网期间的缓存、等待和占用；恢复不成立时还要准确结束，不能把新场成功或一次握手成功误报为原场完整恢复。多个客户端同时断线，以及单场长期零散断线，又对重试策略提出了不同要求。

目标是：在原场仍存活、保留期与缓存覆盖范围内，更换连接后继续同一条识别流，补齐未确认音频、接续结果和尾部；超过边界则明确失败并完成资源清理。用固定输入、故障计划和对照实验回答完成了多少、等待多久、增加多少请求，而不只统计测试通过数。

## 采取的行动与方案取舍

以下比较是当前设计复盘，历史决策与实施顺序以链接中的同期记录为准。

| 行动 | 其他方案与代价 | 当前选择及成本 |
| --- | --- | --- |
| 分离逻辑会话与连接，登记身份并保留原 Worker RPC | 每次重连新建流容易实现，但处理位置和模型上下文不再延续；持久化迁移还需要解决提交点、状态重建和所有权转移 | 保留同实例原场，只交接连接；断网仍占名额和 Worker，必须设置保留期限。见[资源所有权](2026-10-05-session-resource-ownership.md) |
| 按音频位置确认和补发，结果按序确认与去重 | 网络 Write 成功不足以证明业务接纳；保存整场数据会随时长增长 | 双方有界保留未确认内容，覆盖不到则失败；增加确认丢失、旧连接交接和缓存满的处理。见[恢复契约](2026-10-04-session-resume-contract.md)、[客户端方案](2026-10-08-client-v2-resume.md) |
| 集中协调恢复、正常完成及任务退出 | 各读写任务自行重连容易竞争修改状态；只发 cancel 不能证明旧任务已经退出 | 协调者独占状态，旧连接关闭并等待退出后再建立下一次；网络任务有明确所有者和退出通知。输入 end、片段 final、整场 completed 分开判定 |
| 同时约束每轮恢复时间与尝试次数，新增可选滑动窗口 | 提高整场次数只是延后耗尽；每次 ready 清零容易放过密集反复断线；令牌桶表达的是平均速率和突发额度 | 最近 W 内最多 N 次，成功不清历史，旧记录过期后释放机会；仍允许短时 N 次突发，满额时直接失败，不等待补额。逐轮期限独立生效。见[预算评审](2026-10-13-recovery-budget-review.md) |
| 用群体对照评估可选 jitter | 固定退避可复现但容易同时争抢；随机退避分散请求，也可能错过刚开放的入口 | 实现可选随机退避，默认仍关闭；请求减少和等待变化分别衡量，没有凭最好结果修改默认。见[jitter 结果](2026-10-12-group-resume-jitter-results.md) |
| 先验证行为，再测负载与资源，保存可独立复算的原始事件 | 只看最终成功会漏掉中途停顿；只看堆曲线难以区分业务对象、运行时和夹具 | 固定计划与分母，核对实际音频、结果、RPC 及自然退出；时间质量不合格保留并降级，堆增长另做诊断。代价是工具与证据维护成本 |

当前配置事实：`Resume == nil` 关闭自动恢复；启用后 `MaxAttempts` 默认 5，`Window` 默认 5s；`AttemptWindow=0` 仍为整场累计，正值才启用滑动计数。实验中的 60s 没有成为默认配置。滑动记录由现有协调者维护，有效项不超过配置额度，不新增锁、goroutine 或清理定时器。配置及实现见 [client_v2.go](../../internal/wsclient/client_v2.go)、[client_v2_run.go](../../internal/wsclient/client_v2_run.go)。

## 量化成果及其依据

各行是不同问题的独立实验，不合并为一个总体成功率；正式运行的环境、参数、原始失败和归档入口见对应报告。百分比只描述这些固定样本。

| 要回答的问题 | 固定条件与主要结果 | 收益与代价 |
| --- | --- | --- |
| 短暂断网后能否保住完整输入 | [EXP-006-01](2026-10-09-client-resume-baseline-results.md)：单场六秒、500ms 中断，关闭/开启恢复各三场，完整完成 **0/3 → 3/3**；开启恢复的 500ms 与 2s 两组六场均处理 192000B，seq 1–61 各应用一次 | 这些样本保住后续音频和尾部，均沿用原 RPC；每场代理重复音频负载 3200B，不是 Worker 重复处理量 |
| 群体恢复的次数额度是否够用 | [EXP-006-03](2026-10-11-group-resume-budget-results.md)：八场同时断线，握手入口占位 2s，五次/八次各三批，完整完成 **0/24 → 24/24**，恢复请求 **120 → 154（+28.3%）** | 新增机会使会话等到入口开放；代价是更多请求，不能解释为处理性能提高 |
| jitter 是否减少同时争抢 | [EXP-006-04](2026-10-12-group-resume-jitter-results.md)：八场、500ms 入口占位，固定/随机各四批，均 **32/32** 完成；请求 **144 → 129（−10.4%）**，开放后拒绝 **16 → 0**，最大 partial 间隔 **2626.574 → 1404.862ms（−46.5%）** | 此场景请求和观察到的最坏停顿改善；最大间隔是组内各场相邻 partial 最大间隔再取最大值，不是 P99 |
| jitter 是否总能缩短等待 | 同一 EXP-006-04 的 2s 占位，均 **32/32** 完成；请求 **203 → 195（−3.9%）**，开放后拒绝 **11 → 0**；各场最大 partial 间隔的中位数却 **增加 146.505ms（5.6%）** | 更少争抢不等于典型等待更短；第四轮最大间隔也变差，保留默认关闭 |
| 原场能否反复接回并运行更久 | [EXP-006-05](2026-10-13-repeated-resume-extended-results.md)：十分钟计划，正常/六轮断线八次额度/六轮断线五次额度各两场，完整完成分别 **2/2、2/2、0/2**；恢复成功组各六次接回原 RPC | 将组合证据延长到十分钟，也暴露累计五次预算的限制；时间/资源质量 **5/6**，一场源落后降级，不与后续策略对照合并分母 |
| 长期零散断线会不会耗尽机会 | [EXP-006-07](2026-10-14-recovery-budget-comparison-results.md)：十分钟、六轮各 500ms 断线、两组额度同为五次，累计/最近 60s 各两场，完整完成 **0/2 → 2/2**；滑动组各六次恢复、处理 **19,200,000B / 6001 条结果** | 每场多处理后续 **3,840,000B** 并收到尾部，支持恢复机会可重新获得；默认语义未改变，也未证明 60s 最优 |

十分钟对照的累计组第六轮明确耗尽，均无第六次尝试、替代 RPC 或假完成。各场已采集未处理 **3200B**，尚未采集 **3,836,800B**；后者不能写成已丢失录音。四场原 RPC、Worker 选择、源关闭各一次，全部在兜底取消前自然释放；失败客户端返回后远端约十秒才释放，符合服务端独立保留期限。

EXP-006-07 完整性与预期行为核实 **4/4**，时间/资源质量 **3/4**。第一场滑动组故障前出现 **185.781ms** 源计划落后，超过固定判据；整场时间/资源解释降级，未补场替换。另一场合格滑动组的六轮“故障→新采集音频结果”为 **523.849–526.284ms**，其中包含约 500ms 实际阻断；“开放→追赶”为 **110.605–112.207ms**。只有一场合格滑动组时间证据，不能据此声称策略提升速度或两次重复均验证延迟稳定。

## 验收对应与资源边界

| 阶段要求 | 已有证据 | 保留的限制 |
| --- | --- | --- |
| 说明续接的是哪个会话 | 同一身份、连接代次、原 Worker RPC；单场/群体/多轮实际字节与结果核对 | 会话注册在内存中，原实例和 Worker 流须仍存活 |
| 说明恢复了哪些内容、有无重复与缺口 | 固定音频位置、摘要与结果序号；失败分开记录已采集未处理、未采集，完成核对尾部 | Gateway 接纳不等于模型处理或持久提交；产品客户端尚无与实验工具等价的精确缺口诊断，回调外部副作用不承诺 exactly-once |
| 有限重试在组合路径仍有效 | [三类短场网络验收](2026-10-14-recovery-attempt-window-network.md)：分散三次恢复、密集成功后耗尽、ready 丢失后耗尽，各三场符合预期 | 九场中只有分散组三场是业务完整完成；其余六场是预期失败。可控屏障测试不提供恢复延迟结论 |
| 资源随任务实际结束释放 | EXP-006-07 四场自然清理，17 个合格观察窗 goroutine 均为 30，会话/注册/RPC 各一；[EXP-006-06](2026-10-13-repeated-resume-heap-results.md)四场中，三类缓冲及会话构造路径活动点存活量固定、自然空闲后为零 | 不证明全进程内存上界或无限期无泄漏；十分钟对照三场合格 HeapAlloc 首末窗口最小值仍增加 31888–41792B，不能自动归因于滑动状态 |
| 实例失效后不冒充恢复成功 | [实例故障验收](2026-10-11-instance-failure-boundary.md)：Worker/Gateway 受控停止及独立子进程 SIGKILL，旧场失败，原地址重启后显式新场完成 | 死亡进程不执行清理的事实不能写成正常退出；没有跨实例恢复或模型状态重建，客户端不一定能精确判断底层故障原因 |

堆诊断还留下一个结果克隆路径 **16B** 的单场残留，持有者未知；启动后的部分缓存已分类，但原自然 GC 条件下的增量没有完全归因。剖析使用固定 GC 和全量采样，不能拿它直接替代正常运行的延迟或内存曲线。实验夹具与 Gateway 同进程，整进程数值也不等于 Gateway 独占消耗。

## 反思与重新评估条件

1. **恢复首先是位置与所有权问题。** 拨号成功只是换回通道；原流、未确认内容、完成判定和旧任务退出必须一起成立。仅引入重连库或共享会话 ID 不足以解决这些问题。
2. **限额应对应要控制的风险。** 整场累计防止总请求无限增长，却会惩罚长会话中的零散故障；滑动窗口控制近期密集尝试，但不限制整场总量。单轮等待、近期次数、服务端准入与保留期各有职责，不能相互替代。
3. **完成率、等待和请求成本要一起看。** 次数增加让更多样本完成，成本是请求增加；jitter 减少请求，部分场景典型等待反而更长。没有一种参数能由单项最好结果直接推为生产默认。
4. **证据范围比数字大小更重要。** 预期失败通过测试不等于恢复成功；采集不准不能通过删慢样本解决；profile 分配路径也不等于对象持有者。保留这些区别，让后续变化能与旧结论比较。

若目标变成进程重启后继续原问诊，需要另立持久提交、音频保留、模型重建和结果一致性方案；若出现多个客户端长期反复断网，应做群体滑动预算与准入的组合实验；若业务对象在重复运行后持续保留，再针对持有关系诊断。当前小幅堆变化和有限样本不自动触发更多参数扫描或剖析。

## 下一步：真实 ASR 接入前评审

现有恢复机制已在 Mock 上形成闭环；下一项主要不确定性来自真实模型能否满足流式契约。继续扩大 Mock 参数扫描不能回答这个问题，因此先评审一个具体模型的适配能力，再实现最小纵向链路。第七阶段尚未开始实现，本步没有选定模型或部署方案。

下一轮需要产出一份具体后端的能力表与最小验收方案：

| 要核对的内容 | 需要明确的事实 | 对实现的影响 |
| --- | --- | --- |
| 后端与音频输入 | 模型/服务版本、运行硬件、采样率、声道、编码、分块限制、状态是否跨块保留 | 当前 [gRPC 请求](../../proto/tide/asr/v1/asr.proto)只有 bytes，没有格式协商；首版应明确固定格式及转换边界 |
| 处理进度 | 哪个事件能证明原始音频的连续前缀已完成处理，静音时能否推进 | 当前 AudioProgress 明确排除仅收到/入队；不能用 Write 返回或文本长度伪造处理确认。后端若没有可信依据，须先调整适配契约并说明保护范围 |
| 结果与正常结束 | partial 修订、segment_id、片段 final、输入结束后的尾部、结果流结束 | 映射到现有结果与整场完成规则；不能沿用 Mock 的固定文本、每块一条或 6001 条作为真实模型成功判据 |
| 说话人及时间信息 | 后端是否提供、何时稳定、粒度是什么 | 当前响应没有说话人字段；识别与说话人区分分别声明能力，必要时设计协议扩展 |
| 取消、故障与上下文 | 推理能否取消、内部缓冲是否可控、原流失败后的语义 | 复用已有退出与同原流恢复规则，另测模型计算资源何时真正释放 |
| 验收素材与指标 | 可使用的小段音频、参考转录、记录方式 | 先单场实时送入、尾部与取消；然后将识别质量和链路延迟分开评估，再加入断线和并发 |

后续顺序：**具体后端契约评审 → 单场真实音频纵向接通 → 断线、取消及小规模并发验证**。核心适配实现继续由开发者负责，助手解释方案、评审并完成测试和实验；明确委托的实现按委托执行。更长临床时长、更广弱网、群体反复恢复、严格资源边界及产品故障诊断作为显式待办保留。

本步只维护工程总结和阶段状态，核对来源与文档链接；没有用重复运行既有测试增加成果数量，也没有改写冻结实验归档。

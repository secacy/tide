## 目标与业务前提

第六阶段已完成当前 Mock 范围验收。现在要检验真实模型能否持续接收音频、产生中间结果、处理输入尾部，并为已有保护提供可信依据。首步是模型能力探针，随后才实现 Worker 适配器及完整链路。

开发者询问本地与租用 Linux GPU 的选择，愿意为效果考虑 GPU，但尚未决定租用。建议先在当前 Mac 做单场探针，再依据候选模型的质量和速度决定 GPU 对照；这不是生产部署选型，也不是要求所有模型都用 Go 实现。

## 为什么先本地，再决定 GPU

质量与速度要分别验证。模型、解码配置、精度和输入相同的情况下，换计算设备本身不能作为准确率提升依据；GPU 的并行计算能力可能使较重的模型或更多会话可用，但具体加速比、数值差异与识别变化仍需测量。

| 路线 | 价值 | 代价及本轮判断 |
| --- | --- | --- |
| Mac 上运行可本地推理的中文流式模型 | 可直接观察模型状态、分块和尾部，便于 Go 接入与重复排错 | 依赖原生库和模型支持；本机性能、中文医疗准确率未知。优先用于单场契约验证 |
| Linux GPU 上自部署模型服务 | 当候选模型需要或受益于 GPU 时，可评估更重模型与并发 | 多出设备、驱动、运行环境和租用成本；远端网络也影响端到端等待。先明确模型及输入，再按其要求选择硬件 |
| 接已有或云端识别服务 | 可以减少模型部署工作 | 输入/结果/进度/取消能力受具体 API 限制；尚无指定服务，不能预设它提供已处理音频位置。作为有现成服务时的备选 |

租用触发条件：候选模型的官方运行要求需要 GPU，或本机实测持续落后、无法满足拟定负载；若主要问题是术语错误，应先比较模型或其词汇适配能力，而不是只升级硬件。先做短时同素材对照，再考虑长期资源；本轮不推荐具体 GPU 型号、租期或价格。

## 候选后端与当前证据

**本地探针优先候选：sherpa-onnx Go API + 一个中文流式模型，先以官方提供的 `sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20` 作为接口基线候选。** 选择理由是有明确 Go 入口、流式模型及中文支持，便于定位接口问题；不是最新模型排名，也没有医疗场景质量优势的证据。运行前需固定 Go 绑定、原生运行库和模型文件版本/摘要，核对模型使用条件；当前未作安装兼容性验收。

- 官方 [Go API 文档](https://k2-fsa.github.io/sherpa/onnx/go-api/index.html)列出流式/非流式支持、macOS arm64/x86_64 预构建库，并明确需要 cgo。因此 Gateway 仍保持 Go 与现有 gRPC 边界，原生推理依赖放在独立 Worker 一侧；不能把它描述为纯 Go 推理。
- 官方 [Zipformer 模型目录](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html)提供上述中英流式模型。目录中的示例耗时不是 Tide 本机结果，也不用于预估本项目容量。
- 备选是独立部署 FunASR 流式 Paraformer，Gateway 继续使用 Go；官方 [流式示例](https://github.com/modelscope/FunASR/blob/main/examples/industrial_data_pretraining/paraformer/README.md)使用逐块输入、cache 与末块 is_final。选择它需额外维护模型运行环境及服务适配；有 Python 模型运行时不改变网关侧 Go 技术栈。示例并未证明其输出可以直接作为 Tide 的逐字节处理确认。

以上在线资料于本步查阅，链接指向可变化页面，尚不是冻结依赖或复现清单。没有对不同后端准确率作未经实测的排序。

## 现有契约核对

| 内容 | 当前代码事实 | 真实适配必须回答的问题 |
| --- | --- | --- |
| 音频格式 | [audio/format.go](../../internal/audio/format.go)按 16kHz、单声道、16bit 计时，默认 3200B/块；[gRPC 请求](../../proto/tide/asr/v1/asr.proto)仅携带 bytes | 首个验证固定 PCM S16LE，WAV 解析后只送音频样本，不能把容器头当 PCM；禁止静默重采样后继续沿用未换算的原始偏移 |
| 处理确认 | AudioProgress 表示连续已处理原始字节，文本字段必须为空；[v2 会话](../../internal/gateway/session_worker.go)拒绝倒退或超过已交付位置的确认 | 模型哪个事件能证明处理到哪里？入队、API 接收返回、文本长度、最后一个词的时间戳均不能直接代替该依据 |
| 积压保护 | v2 在新音频接纳前比较新末端减 processedBytes 与 MaxPendingAudioBytes；0 关闭。见同一 session_worker.go | 进度未知时不能填成已全部处理；接通实验可显式关闭这一项并报告未验证范围，不能当作已恢复完整保护，更不能伪造确认让预算通过 |
| 结果与结束 | [worker_receiver.go](../../internal/gateway/worker_receiver.go)分开处理文本/进度；[session_control.go](../../internal/gateway/session_control.go)协调半关闭和响应 EOF 后进入结果保留 | partial 是追加还是替换？片段何时 final？输入 EOF 后怎样 flush？空文本和静音也应正常结束，不能以出现某段文本代替整场完成 |
| 说话人 | 当前 protobuf 响应无 speaker 字段 | 首个探针只验证转录；说话人区分需单独确认后端能力并设计映射，不能通过文本猜成医生/患者 |
| 取消和生命周期 | 当前 Gateway 等待原 RPC 任务退出后释放自身缓冲 | Go context 取消能否停止实际推理？尤其需核对原生调用期间行为，不将 RPC 返回当作计算/显存已经释放 |

以 16kHz 单声道 16bit 为例：接收 32000B 表示收到一秒音频。若模型只完成前 800ms 的可确认处理，进度最多报 25600B；余下 6400B 必须继续算作未确认。即使没有识别出任何字，可信的计算进度仍可以前进；反之，输出一个字也不证明后续静音已经处理完。这是语义示例，不是对候选模型内部步长的断言。

首个候选的精确处理前缀尚未确认。官方 [Go 文件解码示例](https://github.com/k2-fsa/sherpa-onnx/blob/master/go-api-examples/streaming-decode-files/main.go)区分接收波形、判断可解码、执行解码和取结果，并添加首尾 padding；它一次送入整段音频，不是 Tide 实时输入验收。需要在固定版本中检查输入缓存、特征窗口、右侧上下文、解码位置与尾部处理。不能只因 IsReady 变为 false 就把所有接收字节报告为已处理；padding 也不能计入原始音频位置。

## 下一小步：单模型探针，而后设计适配器

探针和测试由助手完成，核心 Worker 适配仍按协作约定由开发者实现，明确委托除外。探针建议采用独立实验模块，避免在验证原生依赖之前改变主项目 go.mod 或让常规 Mock 测试依赖模型下载。当前只确定范围，不创建通用多模型接口或后台任务系统。

1. **固定输入与依赖。** 选一段可使用的中文语音及参考文本，另有纯静音、短尾块；记录样本 SHA、格式、样本数、绑定/运行库/模型版本和线程设置。优先小段公开示例或自录内容，先不依赖临床录音。
2. **分块运行。** 同一模型状态接收每块 100ms，串行调用，记录输入偏移、调用起止、文本变化、片段及结束事件。实时排期用原始计划时刻，不把模型计算耗时不断加到下一块计划里；同时保存计划落后。源文件读完与模型尾部处理完分别记录。
3. **核对边界。** 静音不因没文字被误判失败；不足一块的尾音经过结束刷新；padding 单独记账；取消后不再提交新块，并等待正在使用模型状态的调用结束才释放，避免 use-after-free。若底层没有可中断调用，明确测其最坏等待，不宣称硬取消。
4. **调查处理进度。** 将可观察事实与推断分开。无法证明连续处理前缀时记录 unknown，不自行定义 processed=accepted。输出“现有 API 可映射 / 需要补充观测 / 需调整保护契约”的结论，再决定实现路径。
5. **分开输出质量与速度。** 参考文本按预先约定规范计算中文 CER，保留术语错误；冷启动加载与热推理解码耗时分开，另记首条非空文本等待、末块送入到尾部完成、源排期落后。RTF 使用声明范围内的处理耗时/音频时长，排除人为实时等待，不能由单场 RTF 推断并发容量。

首次成功标准是：输入仍在继续时出现可解释的文本更新，尾部可结束、状态可释放，关键未知项清楚可见；不是字符零错误，也不是“每块一条结果”。纯静音不要求非空文本。若候选不满足目标，保留现象并换候选或调整契约，不能为了通过沿用 Mock 的固定尾部文本判断。

后续两步：根据探针输出指导最小 Worker 适配（原 RPC 内的模型状态、输入/结果/进度/EOF/取消映射），再通过现有 Gateway 做单场真实音频闭环；有必要时再做 GPU 的同素材质量/速度对照。说话人区分、完整录音与延后转录继续独立列为未完成项。

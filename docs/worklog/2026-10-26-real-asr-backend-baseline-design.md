# 第七阶段回到流式后端：真实 Worker 连续会话运行基线

日期：2026-10-26。状态：设计完成；后续工具与五轮完整复测已完成，见[结果](2026-10-26-real-asr-backend-baseline-results.md)。下文保留实施前的设计与取舍。依据开发者确认，停止继续扩展模型准确率实验，保留已有质量报告作为后端背景。

## 当前目标

本项目负责连接客户端与 ASR 计算后端，重点是流式传输、会话生命周期、实时性、背压、调度及恢复。识别准确率影响产品体验，但不作为本轮 Go 后端工作的主要成果或继续开发的前置条件。仍需检查音频完整、结果正确替换以及尾部没有因网关收尾而丢失；已有独立探针和网关对照为这些判断提供依据。

第七阶段接下来要回答：**换成真实计算后端后，已有链路能否持续建立和清理会话，等待时间来自哪里，资源是否随重复运行积累？** 质量比较已完成并收口；回听错误、录制质量验证素材、更换模型和调解码参数退出当前主线。保留原报告，不重写过去测量所得的数值和限制。

本轮固定已经接入当前 Worker 的原 bilingual/int8 模型、greedy、CPU 两线程。其接口和输入身份已有闭环依据，适合作为后端实验负载；不因 CER 或候选资格继续改变当前任务。候选模型尚未接入正式 Worker，不将探针对照当成已完成服务切换。

## 核对后的实际边界

| 当前代码事实 | 对下一步的影响 |
| --- | --- |
| [真实 Worker](../../internal/realasr/worker.go)只有一个名额，忙时直接拒绝，名额覆盖创建到 Close 返回 | 先测单会话运行；“最大一场”是配置限制，不是实测容量 |
| [进程入口](../../workers/sherpa/cmd/asr-worker/main.go)每场创建模型，记录 model_created/engine_closed | 加载是每场成本，可测；原生释放返回可观察，不能只看客户端 Run 返回 |
| 输入上限 960000B、块上限 3200B、全文快照上限 4096B | 本轮保持短输入；持续运行进程并反复建会话，不把它称为长问诊验证 |
| [原生 Engine](../../workers/sherpa/internal/native/engine.go)串行调用，在调用间观察取消 | context 取消不代表原生计算已停止；不能用并发释放对象实现硬取消 |
| 不提供 AudioProgress；接通配置显式 MaxPendingAudioBytes=0 | 本轮不能核算模型内部未处理音频量，也不能宣称已验证该项背压；发送耗时和文本间隔不能冒充处理进度 |
| 现有 Gateway/v2 夹具保留默认十秒恢复窗口 | 客户端停止后会话可能合理保留；清理时间需包含并说明该政策，不能误算为模型取消耗时 |
| [当前观察器](../../workers/sherpa/cmd/asr-worker/gateway_observer_test.go)在 calls 中保留全部块与结果 | 多轮测试须在证据落盘、RPC 任务完成后释放已完成 trace，避免把工具自身积累当成 Gateway 泄漏 |

已有闭环验证正常、静音、取消及取消后新场；已有质量测试也顺序运行过六场。新增实验的价值是**相同输入、相同进程、重复退出路径和连续资源采样**，补齐原生资源与逐场时间基线，而非再次证明模型能输出一段文字。

## 为什么选择这一步

| 方案 | 价值 | 取舍 |
| --- | --- | --- |
| 复用真实网络夹具，连续正常/取消会话并采样 | 同时观察生命周期、逐场加载、端到端等待与原生进程内存；改动主要在测试工具 | 本轮采用。Gateway 与客户端同在驱动进程，Go 堆不能归因于 Gateway 独占 |
| 立即扩成多 Worker 并发压测 | 可开始验证调度与总吞吐 | 当前缺少单场资源成本基线，且真实处理进度未知；排在本轮之后，先固定保护与准入边界 |
| 立即放大时长上限或做长对话分段 | 更接近长问诊需求 | 需要明确模型状态、片段结束、上下文与结果存储边界；单纯放大限制不能算长对话实现 |
| 为每场启动全新 Worker 进程 | 容易隔离故障与清空资源 | 会掩盖跨会话残留，不能回答本轮问题 |

不另建通用采集平台。优先在 `workers/sherpa/cmd/asr-worker` 增加显式启用的实验测试，复用启动进程、真实 Gateway/V2Client 和 PCM/结果观察代码；独立 Python 复核负责检查证据及汇总。本轮工具、测试和实验由助手完成，若发现核心业务问题，先解释再按协作约定指导修改。

## 实验草案与验收口径

以下是在实现前明确的方案，实际执行前还要冻结代码、输入、程序及条件清单；目前没有实测成果。

1. 启动一个真实 Worker 进程、一套 Gateway 和同一个 gRPC 连接；使用已固定的公开 `test_wavs/0.wav`，约十秒，输入摘要沿用旧模型资产清单。Gateway MaxSessions=1，关闭未知处理进度预算，客户端实时发送且不自动恢复。
2. 先运行一场正常输入作预热，单独保存。预热自然清理后固定观察五秒，取得预热后的空闲参考；不把未加载时的进程 RSS 当成每轮必须返回的值。
3. 连续五轮，每轮依次执行“第一条非空 partial 后取消客户端”“随后正常完成同一份输入”。每场均先观察自然清理，成功后再进入下一场，五轮共十场正式会话。每次取消之后的正常场同时检查名额是否能再次使用。
4. 每场清理后固定观察两秒，最后正常场清理后再观察五秒。全过程按 500ms 采样，不靠缩短恢复窗口改善数字，不在正式测量中主动强制 GC 或为了回收内存重启进程。
5. 预先登记全部槽位。若自然清理超时，保存失败与采样，兜底停止后结束该次运行，其余槽位列未执行；不能重启进程后把余下会话拼进同一条资源曲线。

正常输入保留现有校验：PCM 字节数/SHA 一致、同片段全文替换、结果顺序一致、一次 final、整场 completed 与 completion ACK、源恰好关闭一次。转录原文不要求匹配人工参考，静音或识别错词不作为生命周期失败。

取消场沿用现有“partial 后取消”触发，记录触发时刻、当时输入位置及回调/AppliedSeq 状态。它证明可观察文本后的客户端取消行为，不证明取消发生在某个 C 调用内部。会话保留默认十秒恢复窗口；记录取消至客户端返回、取消至观察到 Engine Close、取消至 Gateway ActiveSessions=0，均为驱动侧观测口径。

自然清理观察预算沿用现有正常场五秒、取消场十五秒。它们是实验等待与失败分类边界，不是新的生产 SLA。各场在原生释放和 Gateway 清理后才能算释放完成。正常尾部、模型创建和客户端完成的语义继续分开。

## 指标如何解释

| 问题 | 本轮记录 | 避免错误归因 |
| --- | --- | --- |
| 连续会话是否正确完成/退出 | 正常完成数、取消符合预期数、失败/未执行数、源关闭数、原生创建/关闭数、每场自然清理状态 | 取消按取消路径判定，不计入正常转录完成率分母；预热单列 |
| 每场为什么要等 | Worker load_ms、Run 起点到首条非空回调、源 EOF 到 Run 返回、客户端返回到观察到清理 | 首字含握手、加载和网络；不拿独立探针加载后时钟直接相减来声称网关开销 |
| 名额是否真的归还 | 每次取消后的正常场成功，Gateway 活跃数归零且对应原生关闭事件出现 | 不以客户端已返回或 Stop 兜底后的归零代替自然释放 |
| 原生进程内存如何变化 | 按 Worker PID 采样 RSS，列出运行期采样最大值及各轮空闲值 | RSS 含原生堆、映射和分配器缓存；不把“不回到进程启动值”直接判断为泄漏，采样最大值不叫精确峰值 |
| Go 侧是否持续积累 | 驱动进程 goroutine 与 HeapAlloc，配合 Gateway ActiveSessions | 驱动包含 Gateway、客户端和测试工具；仅作异常线索，不能直接称为单会话 Gateway 内存 |
| 数据是否可信 | 采样起止、间隔、缺失/失败、进程 PID、版本与输入摘要 | 采样失败记录 unavailable 和原因，不填成零；每场仅短时观测，不推导长期稳定容量 |

五轮小样本报告逐场值、范围及空闲曲线即可，不用不稳定的 p99 包装成果。资源是否随轮次增长，结合空闲值和任务/原生关闭证据判断；若有可疑趋势，再针对其来源做一次堆或原生内存诊断。没有异常证据时不自动扩成长时间泄漏调查。

## 工具设计要点

以下是采样记录的建议骨架，实施时可按现有测试组织调整；字段注释保留观测范围：

```go
// backendRuntimeSample 是驱动侧一次观测；不引用 Gateway 内部可变对象。
// 不同进程的单调时钟不相减，全部采样时间由驱动记录。
type backendRuntimeSample struct {
    ElapsedNS          int64   // 相对本次驱动开始的时刻；原始值用于检查采样缺口。
    Phase              string  // 预热、取消、正常、空闲；用于解释资源曲线。
    Round              int     // 正式轮次 1..5；预热为 0。
    ActiveSessions     int     // Gateway Snapshot 中尚未清理的会话数。
    DriverGoroutines   int     // 整个驱动进程，包含客户端和测试任务。
    DriverHeapBytes    uint64  // 驱动 Go HeapAlloc；不包含独立 Worker 的原生内存。
    WorkerRSSBytes     *uint64 // 由 Worker PID 采集；失败为 nil，不填 0。
    WorkerRSSError     string  // 本次 RSS 采样失败原因；不影响已保存的原始事件。
    ModelsCreated     int     // 已读取的完整 model_created 日志行累计数。
    ModelsClosed      int     // 已读取的完整 engine_closed 日志行累计数。
}
```

采样任务使用自己的 context，拥有并关闭采样输出文件，结束前等待任务退出；RSS 子命令设单次超时，失去进程或读取失败保留证据。记录实际采样间隔，不用循环次数推算时间。

生命周期事件的日志读取采用增量完整行方式，并记录驱动观察时刻；不要从别的进程日志墙钟直接减驱动单调时钟。现有总数工具可继续用于最终一致性校验。

已有 `runGatewayCase` 把 RPC 序号与累计关闭数绑定。扩展时明确区分累计创建/关闭计数、当前场 trace 和已归档的 trace，避免清空观察器后误索引。原始事件落盘且相关任务已退出后，释放上一场 consumer/trace；内存里只保留固定规模摘要。资源采样期间不不断积累全文结果。

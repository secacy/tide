# 中文流式模型对照设计：先比较候选，再决定是否接入

日期：2026-10-26。状态：设计完成，候选资产冻结、探针改造和测量尚未执行。本步不改变生产 Worker 的默认模型。

后续进展：同日完成[资产冻结与技术冒烟](2026-10-26-real-asr-model-smoke.md)。发现候选自动采用 Whisper 特征，后续须按模型与配套配置组合对照解释；候选权重使用条件未确认，六对正式测量仍未开始。下面保留设计时的方案与判据。

## 当前问题与目标

现有真实链路已经能够完成短音频转录，但“完成请求”并不等于“内容正确”。六段已见录音共 200 个参考字符，当前 greedy CER 为 35%；beam/4 为 42.5%，没有修正体温错误。直接探针也复现了重复字，因此继续改网关转发或增加搜索路径，目前没有改善识别质量的证据。详见[上一轮结果](2026-10-26-real-asr-decoding-results.md)。

本步要回答：**在同一批录音和本机运行条件下，换一个中文流式模型，是否能减少字符错误，同时保留输入期间出字和正常结束的能力？** 先做独立探针对照，得到值得继续接入的候选；不以六段已见录音证明临床可用，也不把选模型扩成无期限的算法调参工作。

## 备选方案与选择

| 方案 | 能获得什么 | 代价与局限 | 本轮处理 |
| --- | --- | --- | --- |
| 同一 sherpa 运行时，换中文流式 Zipformer | 保留 Go 调用方式和现有记录工具，集中观察模型包变化 | 共用运行时与音频处理，不能排除共性问题；中文模型不保证医疗内容更准 | 首轮选择 |
| sherpa 流式 Paraformer | 保留 SDK，但换模型架构，提供另一类对照 | 需重新核对模型配置、尾部刷新和输出行为 | 首候选无收益时的备选 |
| 独立 FunASR 流式 Paraformer | 换模型运行路线，有助于排查 sherpa 共性问题 | 增加 Python 环境、流式 cache 和结果适配；与现有探针不是单一变量对照 | 后续独立路线，先设计探针再决定设备 |
| 当前模型改为 fp32 | 可调查当前量化是否影响结果 | 仍是同一模型，不能直接解决模型选择；质量收益未知 | 需要定位量化原因时另立实验 |
| 直接租 GPU、接更大模型 | 为需要 GPU 的候选提供运行环境 | 设备本身不保证纠正识别错误，增加环境和成本变量 | 暂无租用依据 |

首个候选固定为 **`sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`**，区别于名称带 `xlarge` 的版本。官方目录提供中文流式模型及 encoder、decoder、joiner、tokens 文件，使用与现有探针相同的 Transducer 配置入口。注意该包的 decoder 名为 `decoder.onnx`，不能根据包名假设每个组件都是 int8。[官方模型与运行示例](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html#sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30-chinese)

选择依据是中文目标与较小的接入改动，不是发布日期或未经验证的质量排名。先用非 xlarge 候选控制首轮范围；本机实际内存、速度、质量均待测。官方示例耗时不能代替 Tide 测量。

备选资料：[sherpa 流式 Paraformer](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-paraformer/paraformer-models.html)；[FunASR 官方仓库](https://github.com/modelscope/FunASR)。FunASR 流式示例维护 cache，并用末块 `is_final` 刷新；接入它需要单独确认结果是增量还是全文，不能直接套用当前快照替换逻辑。

以上网页于本步查阅，属于候选来源，不是已经冻结的依赖。模型包许可证、准确来源版本、文件 SHA256、ONNX 元数据与固定 SDK 的兼容性留到资产准备时核实；未核实前不能进入正式质量比较，也不宣称可以部署。训练 checkpoint 页面本次读取失败，不据此推定导出包许可。

## 先解决配置身份，再运行实验

当前 [native.go](../../experiments/asrprobe/native.go)写死四个旧文件名，[verify.py](../../experiments/asrprobe/verify.py)写死旧模型摘要。仅把新文件改成旧名字虽然改动少，却容易留下“报告看起来是旧模型，实际跑了新模型”的错误。因此在独立探针内增加两个明确的模型 profile；本轮不设计任意模型插件系统。

建议增加 `-model-profile`，默认 `zipformer-bilingual-2023` 保留旧命令行为；候选为 `zipformer-zh-2025`。`-model-dir` 只定位磁盘目录，不决定模型身份。保留现有解码参数，正式对照两组都显式 greedy/0。

下面是设计骨架，不是已实现 API。字段注释说明它们承担的责任：

```go
// modelProfile 是探针支持的一套明确模型配置，按值传递，不拥有原生资源。
// ID 便于阅读；真实资产身份仍由执行前冻结的摘要清单证明。
type modelProfile struct {
    ID           string // 稳定配置名；未知名称必须报错，不回退默认模型。
    Encoder      string // 模型目录内的文件名，例如 encoder.int8.onnx。
    Decoder      string // 独立声明，候选为 decoder.onnx。
    Joiner       string // 模型目录内的 joiner 文件名。
    Tokens       string // 与该模型匹配的 tokens 文件名。
    ModelType    string // SDK 模型类型提示；空值允许从元数据识别。
    ModelingUnit string // SDK 建模单元；旧配置保留原值，候选核对 cjkchar。
}

// lookupModelProfile 只返回两个已定义配置之一；不读文件、不下载、不加载模型。
func lookupModelProfile(id string) (modelProfile, error)

// recognizerConfig 将已验证的配置映射到 SDK；不分配 recognizer/stream。
// dir 是资产目录，threads 是 CPU 线程数，decoding 是现有解码策略配置。
func recognizerConfig(dir string, profile modelProfile,
    threads int, decoding decodingConfig) sherpa.OnlineRecognizerConfig
```

实现约束：

1. **配置和摘要分工。** profile 说明“怎样加载”；执行前 manifest 说明“允许加载哪些确切文件”。记录来源 URL/修订或 release 资产身份、下载包摘要、各文件摘要、许可证据、SDK/原生库和程序摘要。校验实际资产后才调用原生构造器；不能事后将报告自报的摘要当成期望值。
2. **报告升级为 v3。** 记录有效 profile、实际 SDK 模型字段、文件摘要、采样/特征/分块/padding/endpoint 配置以及解码设置。记录执行值，不能只把命令参数原样抄进报告。
3. **历史证据保持严格。** v1/v2 仍按原固定模型解释；不能把旧摘要约束改成“任意模型都能通过”。v3 必须与运行前冻结清单匹配。可抽取公共事件核对函数，但历史入口继续绑定原清单，新比较入口显式传入候选清单。
4. **原生资源责任不变。** 每场独立进程、一个 recognizer/stream；串行调用、等待当前调用返回后释放。换 profile 不代表新增并发或硬取消能力。
5. **旧路径有回归依据。** 单元测试验证两套文件映射和非法 profile；复核旧归档仍通过。正式 A 组重新运行后与历史 greedy 全文比对，变化须调查，不能把探针改造造成的变化归为模型收益。

## 实验分两道门

### 第一门：候选确实能按预期工作

先准备资产并检查固定 SDK `v1.13.8` 的加载兼容性，再用官方随包短语音、静音、短尾块及主动取消检查输入/输出/释放。官方样例用于确认配置，不计入六段质量收益。记录首次失败，不通过时先定位配置或兼容性，不跳过失败直接出质量结论。

固定原来的 16kHz 单声道 PCM16 输入、CPU 两线程、每 100ms 送入、300ms/600ms 首尾 padding、关闭 endpoint/reset，核对候选是否适配。100ms 是探针提交音频的节奏，不代表模型每 100ms 都能解码或返回结果。如果必须调整 SDK、padding 或特征配置，先修订并冻结方案；结果称为“后端配置组合对照”，不再声称仅换权重。任何新增配置不得依据 q01～q06 的得分反复挑选。

模型加载失败属于准备失败；原生崩溃或超时也保留日志与退出状态。无非空文本的静音正常结束不算失败；有语音的冒烟场需观察输入结束前出现文字。取消依然是协作式，进程保护不是原生调用已及时停止的证明。

### 第二门：固定六对测量

资产与工具通过第一门后，冻结正式计划并执行：

- A 为旧 bilingual/int8 + greedy；B 为新 zh/int8 包 + greedy。同一新探针程序、同机器、两线程，每格独立进程。每格一次，十二槽位；顺序 A1→B1、B2→A2、A3→B3、B4→A4、A5→B5、B6→A6。
- 复用已有 WAV/PCM/参考摘要，共 82.8586875 秒、200 个规范化参考字符。禁止改音量、重录、热词、纠错或重复字符删除。参考不输入模型，只用于离线计分。
- 运行器每场六十秒外部保护，保存起止、退出状态、原始事件与全文。超时、失败、缺场均进入十二槽位，不补成成功样本；若修程序则另开运行编号，保留原轮。
- 保持电脑唤醒，记录排期落后和运行期间采样缺口。两组都完整六段时才计算整体差值；不完整时展示完成率和可用逐段结果，不用不同分母宣称整体改善。

| 维度 | 必须记录 | 如何解读 |
| --- | --- | --- |
| 完整性 | 完成/失败/未知数量、提交字节、Finish、Close、退出状态 | 先确认读完和收尾，再计入成功质量分母 |
| 文字质量 | 每段及合计 N/S/D/I/CER、原文、对齐 | 沿用已有评分规范；加权汇总，不平均六个 CER |
| 关键内容 | 原有 19 项事实，重点体温、药物过敏、否定和自我纠正 | CER 下降不能抵消关键事实错误；助手初评与人工确认分开 |
| 流式行为 | 输入结束前出字的段数、首字等待、排期最大落后、末块到刷新结束 | 同一探针时钟比较；不与 Gateway 的 Run 起点指标混算 |
| 运行代价 | 模型加载、EngineCallNS、call RTF；可获得时另记峰值 RSS 和采集口径 | 调用计时不含全进程成本；单次观察不推断并发容量 |

数字格式可能不同，例如“三十七点八”和“37.8”。主 CER 保持既有规则，不为新模型改评分以取得好结果；同时在事实审核中判断数值语义。文本格式差异与实际数值错误应分开说明，原始结果全部保留。

## 决策与停止条件

这里的“进入下一步”仅表示值得进行新素材验证，不表示生产采用：

- B 六段完整结束、六段均在输入结束前出字、合计字符错误少于 A，且文字初评未发现相对 A 新增的关键事实错误，才推荐进入新素材验证。即使只改善一字，也需原样给出规模，不称为显著提升。事实判断不确定时标记待审，不当作通过。
- B 关键体温等仍错时明确列出，即使 CER 改善也不能称为解决医疗质量；候选可以保留研究价值，正式替换仍待人工审核和新素材结果。
- B 质量无改善、兼容性失败或不能维持流式行为，则保留失败证据。本轮到此结束，不自动试 xlarge、多个精度和多个 beam。下一次另选一个 Paraformer 路线，并解释它能回答的新问题。
- 性能先报告原值。本轮不设未经讨论的业务延迟 SLA，不用 call RTF<1 推导容量；明显运行落后时，先说明质量与速度的取舍，再决定是否测其他设备。

当前六段已经多次用于分析，是选择素材。新候选即使获胜，也要先固定配置，再录制未参与选择的素材、核对参考及关键事实；随后验证真实 Worker/Gateway 的结果与独立探针一致。不能用这六段的胜出结果替代这两步。

## 接下来三步与本步产物

1. **资产冻结 + 探针 profile + 冒烟验证。** 工具与测试由助手负责。完成依据是加载配置可核对、旧证据仍有效、候选流式/结束/释放行为有记录；不是已经质量更好。
2. **十二场配对测量与原始证据归档。** 运行前冻结、运行后重算，输出继续或停止的决定，保留所有不利结果。
3. **有收益才做新素材和完整链路确认。** 之后再决定生产适配、长对话分段或独立运行时方案。

本步只新增设计并更新 Milestones；未下载候选权重、未改探针或生产代码、未运行推理。真实处理字节仍未知，长对话、说话人、完整录音保存及延后转录不因换模型而自动完成。

# 长对话：分段与状态边界设计

日期：2026-10-27。代码依据 `e6c3fac`。状态：设计与第一块实现指导；尚未实现、未运行长音频实验。本步不新增性能或容量结论。

## 为什么现在做

[两真实 Worker 对照](2026-10-27-real-asr-admission-results.md)已证明预设错峰场景的新场完成数由 0/3 变为 3/3。本地分配机制已经接通，但每场仍受真实 Worker 的 30 秒累计输入上限约束。

当前 [Worker](../../internal/realasr/worker.go) 在整个 RPC 内使用一个 Engine 和一个 `segment_id="1"` 的映射器；只有输入 EOF 才 Finish、排空并定稿。[原生 Engine](../../workers/sherpa/internal/native/engine.go) 持有一个 recognizer 和一个 online stream，端点检测关闭。提高输入上限后，整场仍是一个可修订快照，也没有分段释放模型流的边界。

本轮目标是：**同一个逻辑会话和 RPC 内，连续处理多个有限长度片段，旧段定稿后释放旧模型流，后续音频继续处理；最后一次合法输入结束才结束整场。** 这是长问诊的基础能力，仍不是完整问诊保存或长期容量验收。

## 备选方案与本轮选择

| 方案 | 收益 | 代价及取舍 |
| --- | --- | --- |
| 直接提高整场输入和文本上限 | 改动少，可以送入更长输入 | 没有新增状态释放边界；不能单凭配置变大推断资源稳定，不采用 |
| 模型端点检测后 Reset | 可依照模型规则在停顿等位置定稿，适合连续识别 | 需核对端点规则、已送入但尚未消耗的输入、Reset 对特征/解码缓存的具体影响；不能仅根据接口名字保证全量状态释放，留作下一种策略 |
| 固定音频长度，复用 recognizer、删除并重建 online stream | 原始样本边界确定；旧流有明确析构位置；无需每段重新加载模型 | 丢失跨段声学上下文，可能切断词句；尾部刷新和新流启动有额外成本，本轮采用 |
| 每段重新加载整份 Engine/模型 | 可以沿用现有 Factory 和 Close 边界 | 重复模型加载和初始化增加成本，不作为默认路线 |
| Gateway 每段新建 RPC 或换 Worker | 可将片段分散处理 | 要重新定义准入、会话亲和性、结果身份和故障一致性；当前把分段留在 Worker 内 |

本轮固定分段是**可控的工程基线**，不是最佳自然断句方案。自然端点结合最大时长兜底是后续候选；若采用重叠窗口，还需单独设计重叠输出裁剪，不能直接拼接两个完整快照。

本机固定 SDK `sherpa-onnx-go-macos v1.13.8` 的 `sherpa_onnx.go` 已核对：`NewOnlineStream` 使用 recognizer 创建流，`DeleteOnlineStream` 销毁流；`Reset` 的说明是重置神经网络状态并清空当前结果，`InputFinished` 后不得再向原流 Accept。它们支持提出此方案，但不能从 Go 包装声明推断 RSS 会立即下降。绑定不暴露内部 C 指针的限制继续保留；真实组装还须验证流重建后的可用性与资源趋势。

## 三层生命周期

| 对象 | 生命周期及所有者 |
| --- | --- |
| 逻辑会话、RPC、Gateway Lease、Worker 实际名额 | 整场持有；片段结束不重新准入、不释放名额、不关闭 RPC；断线恢复继续使用同一场 |
| recognizer（加载模型的对象） | 一场独占；多个片段串行复用，不引入跨会话共享或并行解码；整场清理时释放 |
| online stream、snapshotMapper | 一段独占；旧段刷新和 final 发送成功后，旧流释放；有下一段非空输入才创建新流和新 mapper |

Worker 不保留所有历史片段的文本。片段 ID 在 RPC 内递增为 `"1"`、`"2"`……；同段 partial 替换前一快照，final 后不再修订该 ID。ID 不是说话人、轮次或音频处理确认。Gateway 的结果 Seq 在整场内连续，不能随分段归零。

现有 [结果缓冲](../../internal/gateway/result_buffer.go) 已区分片段 final 与整场完成，并在累计 ACK 后删除历史负载；[v2 客户端](../../internal/wsclient/client_v2.go) 按序调用 OnResult，自身不组装全量转录。消费者应更新当前片段，定稿后交付下游或写入受控存储，再释放当前快照；如果实验回调把所有结果存入数组，它的内存仍会随时长增加，不能归因于模型流。现有 v1 CLI 只是打印消息，尚不是完整转录展示器。

## 音频边界与执行顺序

首轮建议每段最多 960000B 原始 PCM（16kHz、单声道、S16LE，即 30 秒）。这是拟用实验参数，不是测得的最佳段长。按**原始样本数**切分，不按请求数或墙上时钟切分：一个请求可能跨过边界，必须拆成两份偶数字节切片。

例如某段只剩 1000B，收到 3200B：本段接收前 1000B；完成本段后，下一段接收剩余 2200B。分段器不缓存这份请求，也不复制整场音频。模型所需前后零 padding 不计入原始位置和输入预算。

拟采用以下顺序：

1. 先校验整个非空请求的样本对齐、单请求大小、整场剩余额度。超出整场预算时，该请求全部拒绝，不能提交一半后才发现越界。
2. 按当前段剩余额度取前缀，Accept 成功后更新原始输入计数，再 drain 当前可执行解码步骤并输出变化的 partial。
3. 达到段上限时立即 Finish → drain → 读取快照 → 发送该段 final。即使文本为空也保留 final；不依赖下一块到来才刷新。
4. 释放已完成段的 online stream，保留 recognizer、RPC 和整场名额。处于“段已结束，等待后续输入或 EOF”的状态。
5. 有下一份非空音频时才创建下一段流、递增 ID、建立新 mapper，再提交音频；每段各自添加所需 padding。
6. EOF 若落在未满的非空段内，完成该段后返回成功；若恰好落在已定稿边界，直接结束，不能多生成一个空段或重复 final。整场没有任何原始输入仍报错。

**异常不伪装为完整结束。** 取消、Finish/Decode/发送/换流失败均终止本 RPC；失败前已经发送的旧段 final 保留，当前段不补造 final，Gateway 不能发送整场 completed。取消发生于原生调用中时仍等待调用返回和实际 Close，不能把分段说成原生硬中断。

`final` 仅说明该段不再修订；`completed` 仍要求整场合法 end、Worker 正常 EOF 及既有终态确认条件。前段 final 出现时，Gateway 不得停掉后续上传。

## 限额与兼容方式

- 保留 Worker `MaxAudioBytes` 的整场累计语义，不悄悄改成每段预算；新增明确的每段预算。首轮长音频实验拟显式设置整场 120 秒、每段 30 秒，现有默认短场行为先保持。
- 单块上限继续 3200B，单条快照上限继续 4096B；分段不保证文本必然小于上限，仍应按现有错误路径处理。
- Gateway v2 的 `MaxAudioBytes` 是未释放音频存储预算，不因为总时长变长就同步加大。未确认结果预算、发送期限、收尾期限、恢复预算均继续生效。
- 原始输入计数只代表成功提交给模型的量，不能转换为 AudioProgress。`MaxPendingAudioBytes` 继续为 0。
- 每段有限输入及释放旧流限制的是单段工作集和对象寿命；recognizer 内部缓存、分配器保留、传输层和慢原生调用仍需测量，不能宣称整个进程内存严格有界。
- 新模式使用明确的分段 Engine 契约和显式构造入口；保留现有短场入口作为回归基线，不用可选 type assertion 暗中切换行为。具体接口与 Worker/原生适配器在集成块一起完成，不能只改生产接口而遗漏测试替身和包装器。

本轮不增加录音持久保存、后台补算、说话人分离或 AIGC。[TODO-001](../TODO.md) 的完整记录需求继续单独设计。120 秒开发验证不等于数十分钟门诊能力。

1. **原始音频分段计数。** 独立纯 Go 组件，明确跨块边界、整场预算和提交时点；开发者实现，助手补边界测试。
2. **Worker 与原生生命周期成组接入。** 增加明确的分段模式、分段 Engine 契约和逐段流创建/释放，组合完成输出 ID、正常 EOF、取消清理与名额所有权；助手补可控 Engine、TCP gRPC 及 Gateway/v2 测试。不会让新组件长期停留在孤立可用状态。
3. **真实后端有限延长验证。** 先验证短输入和边界，再跑固定 120 秒输入、4 个 30 秒段；输入拼接只作后端负载，不能当作自然问诊或准确率实验。本步结束后再决定十分钟观察或端点策略比较。

### 第一块：segmentCursor

新文件建议 `internal/realasr/segment_cursor.go`。仅记录“哪些原始字节已成功提交、这段还能接收多少”；不管理 Engine、网络、final 发送或 goroutine。避免把音频数量、模型收尾和 RPC 结束混成一个状态。

```go
// segmentCursor 由单个 RPC 串行拥有；通过构造器创建，不缓存音频。
// 满段时停留在原编号，直到调用者完成旧段收尾并准备好下一段。
type segmentCursor struct {
    maxTotalBytes   int // 整场原始输入上限；不包含 padding。
    maxSegmentBytes int // 单段原始输入上限；不大于整场上限。
    totalBytes      int // 本 RPC 已成功 Accept 的原始字节总数。
    segmentBytes    int // 当前段已成功 Accept 的原始字节数。
    segmentNumber   int // 从 1 开始；只在 advance 成功时加一。
}

// newSegmentCursor 要求两个上限均为正偶数，且 maxSegment <= maxTotal。
// 不采用隐式默认值；默认配置由后续 Worker 构造入口负责。
func newSegmentCursor(maxTotal, maxSegment int) (*segmentCursor, error)

// plan 校验本次尚未提交的请求余量 bytes（正偶数）能完全容纳于整场。
// 返回当前段可接收的前缀长度，不改变状态、不分配音频副本。
// 满段但整场仍能容纳该请求时返回 0,nil，提示调用者先完成换段。
// 使用 bytes > maxTotalBytes-totalBytes 检查，避免加法溢出。
// 单请求大小由 Worker 在拆分前校验，本组件不重复承担该配置。
func (c *segmentCursor) plan(bytes int) (int, error)

// commit 仅在这一份前缀 Accept 成功后调用；增加整场和当前段计数。
// bytes 必须是正偶数，且不超过整场及本段剩余额度。
// 失败不修改任何状态；Accept 失败后终止 RPC，不调用 commit 或重试。
func (c *segmentCursor) commit(bytes int) error

// advance 要求当前段恰好满额，且整场仍有剩余额度。
// 调用者保证旧段已成功刷新/发送 final/释放，且下一段模型流已就绪。
// 本方法不能检查这些外部事实；它只将编号加一、segmentBytes 清零。
// totalBytes 保持；非法调用返回错误，所有字段不变。
func (c *segmentCursor) advance() error
```

这里不需要锁、定时器、channel、历史片段列表或可复制的凭证。字段不导出，同包 Worker 直接读取编号/计数；不为了每个字段再增加 getter。错误可定义少量包内 sentinel，区分非法输入、整场超限、本段超限和不可换段；错误文本不包含音频或转录。

建议实现顺序：构造校验 → plan → commit → advance。`plan` 返回 `min(bytes, maxSegmentBytes-segmentBytes)`，但先完整执行参数与整场预算校验。`commit` 在所有校验成功后一起更新两个计数。`advance` 只在条件全部满足后更新字段；每段至少两个字节、总量受正 int 上限约束，因此合法调用下编号不会回绕。

**不要在 commit 内自动换段。** 计数达到上限与 final 发送成功是两件事，自动归零会让调用者无法区分尚未收尾和已经进入下一段。满段收到 EOF 时也不调用 advance。

小例子用字节缩小边界：整场 24B、每段 10B。commit(8) 后 plan(6)=2；提交 2B 后第 1 段满。完成外部收尾并准备下一段，advance 后 plan(4)=4，commit(4) 后 total=14、当前段=4、编号=2。此时 plan(12) 应直接拒绝，因为整场只剩 10B，拒绝后计数完全不变。

### 助手接手后的验证

- 非法预算、奇数字节、零/负输入、整场和段边界、超大整数输入均明确拒绝且不修改状态。
- plan 可重复读取，无隐式提交；commit 成功才推进；满段 plan 返回 0，不越界或自动换段。
- 跨段拆分重新拼接后逐字节等于原请求；不同请求块划分得到同样的固定段边界。
- 正好满段与总上限、最后短段、非法 advance；无需为串行计数器编造并发争抢测试。
- 集成时另测多个 final 后上传继续、恰好边界 EOF 无空段、下一段创建失败、Finish/发送失败、换段取消、旧流实际释放前不复用，以及整场 Lease 始终只取得一次。

组件测试只证明计数与边界。真正的 final 顺序、原生流回收和整场完成必须由第二块及真实实验提供证据。

## 事先固定结果口径

真实实验实施前单独登记素材、代码、配置和运行次数。本轮设计提出如下判据，当前均无实测值：

- **输入守恒**：可控 Engine 收到的所有非 padding 原始片段拼接等于源音频，遗漏/重复字节为 0；实际原生调用边界记录段字节数及摘要，与冻结源切片一致。这证明提交完整性，不证明每个音素均正确识别。
- **完成正确性**：120 秒固定输入预期 4 个唯一片段 final、一份整场 completed；最终音频 offset 与源长度一致。失败仍进总分母，不能跳过失败段继续报整场成功。
- **生命周期**：整场 1 次模型创建，正常运行 4 次流创建和对应释放；实际计数由新增观察点验证，不能沿用 model_created 数充当片段数。整场结束后 Gateway、Lease 和 Worker 名额按各自边界归还。
- **时间**：记录每段源输入边界至 final 收取、换流耗时、整场 end 至 completed；同时记录客户端发送落后，区分累计延迟与尾部等待。无预先测量，暂不填写性能目标数字。
- **资源**：持续采样 Worker RSS、Gateway/客户端堆与 goroutine、未确认缓冲，记录最大采样间隔和批后状态。确认当前片段对象不会累计，不把一次 RSS 曲线或四段成功包装成长期稳定容量。

达到这些判据之后，再决定是否开展更长运行和端点分段。暂不把数十分钟无损问诊、严格实时性、跨实例恢复或记录可靠保存写成已完成。

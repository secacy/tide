# 第七阶段总结：真实 ASR 接入、局部准入与固定分段

日期：2026-10-27。代码核对至 `58f3416`；各实验采用其报告中的冻结版本。本步整理已有代码、实验和边界，没有新增运行、改变配置或调整模型。承接[接入前评审](2026-10-25-real-asr-entry-review.md)及后续范围调整；不延续早期质量诊断作为开发前置条件。

**阶段判断：真实后端的流式接入、生命周期、单 Gateway 局部准入和一次十分钟固定分段运行已有验收依据，可以结束本轮接入与基线建设。第七阶段整体仍保留未完成项，不能标记为完整临床能力或生产容量已验收。**

一句话概述：将真实流式模型接入既有 Go 网关，补齐模型资源与会话名额的所有权，并在同一 RPC 内按段释放识别流；两 Worker 错峰对照的新场完成数从 0/3 提升到 3/3，另完成一次 600 秒、20 段的完整链路验证。

## 背景、难点与目标

前六阶段已经在 Mock 与可控故障下验证转发、背压、调度和有限恢复，但 Mock 可以明确报告“处理到哪个字节”，也能配合取消及时退出。真实模型不一定提供这些能力：提交音频后，模型可能仍在内部计算；取消 RPC 后，正在执行的原生调用也可能尚未返回。若直接沿用 Mock 的假设，就可能提前归还计算名额，或把网络发送成功误当成模型处理完成。

真实后端还带来两类具体问题。多台 Worker 的问诊结束时间不同，普通轮询可能把新场分给仍忙的实例，而另一台已空闲。长问诊则不能只靠放大输入上限：首版整场共用一个可修订文本快照和识别流，需要明确何时定稿、释放当前流，以及如何继续下一段而不结束问诊。

本阶段的目标是让真实模型沿用已有流式协议，同时把不成立的假设显式拆开：输入期间能返回文字，正常结束能收取尾部；名额持续到各自负责的清理完成；固定分段保持原始输入和结果顺序；用有限实测检验分配收益、运行等待及资源表现。识别准确率作为模型背景保留，当前 Go 后端不承担模型调优目标。

## 行动与方案取舍

以下是基于实际实现的设计复盘；同期决定与实施顺序以各链接为准。

1. **将模型适配与会话控制分开。** 主模块的 [Engine/Worker](../../internal/realasr/engine.go)表达输入、解码、快照、尾部与释放；原生绑定放在[独立 Worker 模块](../../workers/sherpa/go.mod)。相比把 SDK 直接加入根模块，这保持了网关和普通测试的原生依赖隔离，代价是两套构建与测试入口。当前组装针对本机 macOS/cgo，未因此获得 Linux/GPU 部署能力。见[组装方案](2026-10-26-sherpa-engine-assembly.md)。

2. **由一个 RPC 执行流程串行拥有模型资源。** 调用返回后才能执行下一步或 Close，Worker 的实际名额覆盖创建、计算和释放全过程。与“收到 cancel 就马上归还名额”相比，这能避免旧计算未结束时再放入一场；代价是慢原生调用仍会占住名额。跨会话共享或常驻预加载模型可能减少加载成本，但还需要独立验证并发安全与资源所有权，本轮每场创建一个 recognizer。见[生命周期方案与验收](2026-10-26-real-asr-worker-lifecycle.md)。

3. **把检查空额、选择实例和占位合为一次原子操作。** [CapacityRoundRobin](../../internal/workerpool/capacity_round_robin.go)跳过本地已满条目，返回由会话持有的 Lease；v1/v2 在本地完整清理后归还，断开恢复与结果保留不重复申请。普通轮询保留作对照；先查询远端空闲再建流仍有竞争，预留协议则要增加过期与失效处理。本轮采用单 Gateway 的本地占用加 Worker 最终准入，不排队或透明重试。它不能提供跨 Gateway 全局容量，本地释放也不等于远端已释放。见[准入设计](2026-10-26-real-asr-admission-design.md)、[接入验收](2026-10-27-gateway-worker-lease-validation.md)。

4. **在同一 RPC 内分段，复用 recognizer、逐段重建 online stream。** 按原始样本数拆分跨界请求，满段依次刷新、解码尾部、发送 final、释放旧流；有下一段非空输入才创建新流。整场 Lease、模型名额和结果序号持续保留，段 final 不等于整场 completed。相比只提高上限，增加了明确的流释放边界；相比每段重载模型或换 RPC，避免重复整场初始化及重新分配。成本是固定边界可能截断词句并丢失跨段声学上下文，自然端点仍需另行设计。见[分段设计](2026-10-27-long-dialogue-segmentation-design.md)、[实现验收](2026-10-27-segmented-worker-validation.md)。

5. **按可证明的语义保留保护，显式关闭未知进度预算。** 真实适配器不发送 AudioProgress，实验中 `MaxPendingAudioBytes=0`。Send 返回、Accept 成功、暂时无可解码步骤和文本更新均不伪装为处理前缀。有界音频/结果存储、发送与收尾期限继续生效，但不声称它们限制了模型内部全部积压。额外加入“文本不更新超时”会误伤静音，本轮未采用。见[保护范围核对](2026-10-26-real-asr-admission-design.md)。

6. **用分层验证和冻结证据回答不同问题。** 可控 Engine 验证取消、换段失败与实际释放顺序；真实 TCP/WebSocket 验证组合路径；独立原生进程验证模型运行。实验预先固定条件与分母，交叉核对输入摘要、结果、完成确认、模型/流事件及采样质量；保留首轮工具失误，归档可独立复算。这样能区分代码机制、一次运行事实和对照收益，成本是维护专用驱动与复核器，而不是只读取一张成功率图。

## 量化结果与证据

各行是独立实验，不合并为总成功率。主要运行环境为 Apple M2 Pro、32GiB、CPU 两线程的固定 int8 模型；源码、具体参数与原始数据入口见报告。单场输入上限和每 Worker 一个名额是配置，不能冒充测得容量。

| 空闲 Worker 能否用于错峰新场 | [三批配对对照](2026-10-27-real-asr-admission-results.md)：新场 **0/3 → 3/3**，两组原场各 **6/6** 完成 | 旧策略选中仍忙的 A，新策略使用空闲 B；预设场景完成率 **+100 个百分点**，不是一般负载吞吐或稳定容量提升 |

## 反思与收获

1. **接入真实后端首先要核对契约。** Mock 可以配合进度和取消，真实 SDK 未必如此。先明确什么能被证明，再决定启用哪些保护，比补一个看似完整的进度字段更可靠。
2. **会话、模型和片段需要不同的生命周期。** 会话还在持续时，片段可以结束；客户端已退出时，模型可能还在释放。把三者合并成一个“结束”会同时破坏尾部完整性和资源准入。
3. **分配数量均匀不等于资源利用合理。** 长短场混合时，轮询次数不能代表当前占用。原子占位解决的是本地已知资源竞争，最终计算准入仍需要 Worker 自守。
4. **分段解决一部分状态寿命，不自动解决所有内存。** 本轮逐段流有明确释放点，但共享 recognizer、分配器和传输层仍可能保留状态。RSS 小幅增长应保留为限制，不能用 Close 日志直接消除疑问。
5. **指标必须服务项目目标。** 准确率诊断已作为模型背景收口，后端重点是传输、终态、资源和调度。预登记场景与独立复核使数字可以解释；更多试验时长、测试数量或低 CER 本身不代表后端收益。

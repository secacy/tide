# 第五阶段：调度与容量实验 · STAR + T

核对日期：2026-10-03。范围：Go Gateway、可控 Mock Worker、有限并发批次与逐实例观测。

**一句话概述：**为实时语音网关建立多 Worker 会话分配和可复核的负载实验体系，在固定异速 Mock、相同两个处理名额、每场 20 秒的三批对照中，采用静态 2:1 加权将 12 并发完成率从 83.3% 提高到 100%，并补充两分钟运行、过载清理及后续新会话可用性的验证。

本阶段完成了当前 Mock 实验范围的实现与验收。原计划中的“稳定容量”仍需更长观察、持续到达负载及资源测量支撑，不能因阶段总结完成而改记为已验证。下一步进入第六阶段设计；该证据缺口继续保留。

## Situation：背景、痛点与难点

前四阶段已经打通实时语音链路，并在会话异常、下游变慢或积压过多时执行清理和保护。但多个问诊同时接入后，仍缺少两个关键答案：现有处理资源能在哪些负载下完成全部会话，以及新增会话应该分给哪一个 Worker。连接建立成功并不意味着音频持续得到及时处理；一台 Worker 已经排队时，另一台仍可能有空闲。

难点同时存在于实现和判断结果上。一次识别流包含连续的上下文，选定 Worker 后需要维持整场绑定；处理能力不同时，平均分配连接可能使慢实例先积压。另一方面，过载时部分会话提前失败，剩余会话的延迟反而可能变好；客户端发送被拖慢，也会让服务端看起来更轻松。如果只看成功请求延迟或总连接数，就可能把少处理了音频误认为性能提升。

因此，需要让调度变化与真实完成情况建立可核对的联系：既确认输入按计划发出，也保留失败，并观察每个 Worker 的处理占用、等待及批次结束后的状态。比较时还要区分增加处理名额与改变分配策略各自带来的收益。

## Task：目标

在已有生命周期和保护机制上接入多个 Worker，让每场会话只选择一次后端，并能通过配置切换普通轮询与静态加权。建立固定输入、固定判据、保留原始记录的实验工具，找到当前 Mock 条件下可用于后续对照的达标与过载运行点，验证扩容、策略调整及延长运行后的表现。

实验前固定每批三个业务判据：全部会话完整完成、成功会话尾部 p95 ≤250ms、每次尝试最大发送排期落后 ≤100ms。采集质量另行检查，包括负载窗口内无查询失败、覆盖间隔 ≤500ms、前后空闲及进程正常退出。数据采集通过并不表示该批业务达标。这些阈值用于本轮工程筛查，尚未定义临床 SLA。

## Action + Trade-off：行动、方案与权衡

### 1. 将会话分配与音频转发分开

Gateway 依赖小接口 `WorkerSelector.Pick()`，在合法 start 后选择一次，后续音频、end、尾部结果和清理都沿用同一条识别流。每个后端复用一条 gRPC ClientConn，每场使用独立流及取消上下文；连接由启动层统一回收。

也可以直接在 Gateway 内按策略分支，初期更省代码，但会让转发路径了解不同算法的内部状态。当前接口将变化限制在选择器与启动组装中。按音频块重新选 Worker 则需要额外传递识别上下文和保证顺序，不符合现有流接口。建流失败目前消耗一次选择，不回退或自动换实例，避免在尚未定义重试语义时引入重复处理。实现与验收见[选择器设计](designs/2026-10-03-weighted-round-robin.md)。

### 2. 根据已观察的问题引入平滑加权轮询

先保留普通轮询作为基线。异速实验发现慢实例频繁繁忙并等待，而快实例仍有空闲快照，因此提出“调整新会话分配比例”的假设。对逐块耗时 10ms/20ms 的两个 Mock，先验证 2:1 静态权重。

| 可选方案 | 优点 | 代价与本阶段选择依据 |
| --- | --- | --- |
| 普通轮询 | 简单、无需运行时统计，适合能力相近的固定实例 | 不表达快慢差异；保留为对照策略 |
| 最少活跃会话 | 能反映会话结束时间不同造成的连接数差异 | 需要登记和归还；相同会话数在快慢实例上不代表相同压力 |
| 静态平滑加权轮询 | 按已知能力差异调整新会话比例，状态少、容易独立验证 | 不感知运行中变慢、健康和实际积压；本阶段采用 |
| 实时负载调度 | 有机会适应处理速度与负载变化 | 需要定义指标、采样过期及失败行为，并处理反复切换；当前证据尚不要求加入 |

平滑加权每次给各实例累加权重，选择分数最高者，再扣去权重总和；2:1 从初始位置产生 A/B/A。相较按权重展开列表，状态空间只随实例数增长。一把锁保护完整选择，锁内不执行 RPC；单次选择 O(N)，N 为 Worker 数。该实现适合当前少量固定后端，未测量大量 Worker 下的锁竞争，也未证明 2:1 是最优权重。权重约束的是新选择比例，不能保证任意时刻活动会话数同样为 2:1。

### 3. 让负载报告同时表达完成、失败和输入节奏

构建按需生成的有限静音 PCM 源、单场执行和固定并发批次，复用已有客户端协议与实时排期。逐场记录计划/实际写入字节、结果完整性、结束原因、尾部等待和发送排期落后，失败始终保留在分母中。成功尾部从原始样本合并后重算 nearest-rank p95，失败的缺失尾部不填零，也不平均各批 p95。

与不限速发送相比，按音频时长排期更适合检查实时输入下的持续处理行为；与持续补充会话相比，固定批次更容易核对整场完整性，但失败后活动量会下降。因此它能用于筛查和对照，不能当作持续维持 N 并发的压力模型。静音源避免预分配整段音频，适用于当前按字节和延迟工作的 Mock；真实 ASR 容量需使用有代表性的语音。详细口径见[负载工具设计](designs/2026-09-28-concurrent-load.md)。

### 4. 补齐逐实例观测与证据复核

独立采样 Gateway 活动会话和每个 Worker 的处理占用、等待数量，保存包含查询失败的 JSONL，并按五秒区间观察活动数变化。每路串行查询并设置期限，使查询不会无限叠加；代价是各实例采样不同步，不能把等待峰值相加当作系统同时峰值。

实验保存实际命令、启动配置日志、源码/二进制/工具哈希、原始报告和进程退出信息，分析可在临时副本重算。预先约定覆盖要求，保留休眠造成的无效采集和启动预检查中断，完整复测使用新目录，不拼接表现好的批次。Worker waiting 是等待名额的人数，busy 是繁忙快照占比；二者均不能直接替代排队时长、音频积压字节或 CPU 利用率。

### 5. 分别验证资源增加、策略变化和过载后的行为

扩容实验保持代码和轮询策略，比较一个与两个同配置 Worker。策略实验则保持两个实例、两个名额及相同二进制，重新运行普通轮询与加权，三轮相邻顺序为 RR/W、W/R、RR/W。直接比较旧报告成本更低，但难以排除版本变化；本轮选择完整重跑。交替顺序减少时间影响，但三轮顺序并不完全平衡，同机进程也没有隔离，因此不作统计显著性证明。

对短时达标档位再运行两分钟筛查，并单独验证加权过载：每批之后不重启后端，再用两场短会话探测服务可用性。这样分别回答“原会话是否成功”“失败后是否清理”“之后能否完成新会话”。短探测没有恢复原失败会话的音频，不能据此验收第六阶段的断线续传。

## Result：量化成果与证据

以下容量相关实验均在同一台 Apple M2 Pro（12 逻辑核、32GiB）、macOS 26.6.2、Go 1.26.5 上运行非 race 二进制。输入为每 100ms 排期发送 3200 字节的静音 PCM，32000 字节/秒；每 Worker 一个处理名额。Gateway 最大会话数 64、待处理音频预算 32000 字节。64 是配置保护上限，并非实测可承载会话数。完整配置和环境见各实验报告。

| 结果类别 | 实验及量化结果 | 可支持的结论 |
| --- | --- | --- |
| 增加处理资源 | [EXP-005-07](../experiments/worker-count-comparison.md)：10 并发、20 秒、各三批，单 Worker 26/30 → 双 Worker 30/30；完成率 86.7% → 100%，提高 13.3 个百分点；达标 0/3 → 3/3 | 同机增加一个 Mock 进程及处理名额后，该已测负载改善；收益不能归为调度算法优化 |
| 相同资源调整策略 | [EXP-005-12](../experiments/strategy-comparison.md)：10ms/20ms 两 Worker，12 并发、20 秒、各三批，轮询 30/36 → 加权 36/36；完成率 83.3% → 100%，提高 16.7 个百分点；达标 0/3 → 3/3 | 固定条件下调整分配比例有效；实例数和处理名额未增加 |
| 策略对照的完整范围 | 同一 EXP-005-12 的 8/10/12 三档：轮询 83/90 完成、3/9 批达标；加权 90/90 完成、9/9 批达标。轮询七次积压保护失败，加权零次 | 改善包含减少失败和保留完整输入；并非只比较幸存会话延迟 |
| 延长观察 | [EXP-005-13](../experiments/weighted-extended.md)：加权 12 并发，每场 120 秒、两批，24/24 完成、2/2 达标；合并成功尾部 p95 92.118ms，最大发送落后 43.811ms | 12 并发通过两分钟筛查；没有新增轮询长时组，不计算长时策略提升比例 |
| 过载保护与后续可用性 | [EXP-005-14](../experiments/weighted-overload.md)：加权 16 并发、20 秒、三批，41/48 完成、七次积压保护失败、0/3 达标，成功尾部 p95 1027.214ms；批次后活动/处理/等待归零，同一后端后续探测 6/6 完成 | 过载被明确暴露且服务能清理并完成之后的低负载新会话；失败会话的音频未恢复 |

上述尾部指标表示发送 end 后等待最终结果，当前 Mock 每场只产生四条 partial 和一条 final，不能解释为全程逐块转录延迟。成功样本群体不同，不能把成功尾部差值直接写成同一批会话的延迟降低百分比。过载后的探测每场两秒，在原批次退出约 19.13–19.20 秒后启动，未测量即时恢复原负载所需时间。

逐实例证据支持分配改善的解释：策略对照 10 并发时，快/慢 Worker 的 busy 快照占比由轮询的 52.2%/99.5% 变为加权的 64.6%/81.4%，慢实例 waiting 占比由 99.3% 降至 60.5%。结合完成与尾部达标，可以推断新分配更符合已知处理差异；由于未记录实验中逐会话 Worker 绑定，不能把某次失败归给具体实例，也未证明全局最优。

## Think：反思与收获

**先定义“完成得好”，再讨论能接多少连接。** 如果只展示成功尾部，轮询 12 并发约 91ms 的 p95 看起来很好，但仍有 6/36 失败。完成率、完整输入和延迟一起看，才解释了加权的实际价值。下一轮也应先定义判据，再选负载和指标。

**调度收益取决于工作负载。** 静态加权解决了本轮已知快慢差异，代价是不了解动态变化、会话时长及实际成本。后续若观测到运行中变慢或长短会话混合造成失衡，再比较加权最少活跃或负载反馈；不能因当前有效就宣称普遍优于轮询。

**保护系统与保住一次问诊是两个验收目标。** 过载失败能释放资源，也能让服务之后继续工作，但原来的音频与识别结果没有因此补回来。这使第六阶段的目标更具体：确定断开期间哪些音频仍可恢复，哪些会明确形成缺口。

**实验方法本身决定结论的可信范围。** 代码版本、负载节奏、失败分母和采样缺口都可能影响解释。现在已有可重复的比较方法和有限窗口下的运行点；要进一步回答长时稳定容量，需要补持续到达模型、符合问诊时长的观察窗口、资源趋势及真实音频。这些工作应由具体问题驱动，不将所有未测项目都临时追加到当前阶段。

## 下一步：第六阶段先确定恢复语义

首先明确要恢复的故障范围，再设计协议与生命周期，随后由开发者逐步实现。建议首个讨论场景为“客户端短暂断网，Gateway 与 Worker 仍存活”；Gateway 重启或 Worker 丢失识别状态需要另外的状态保存与重建方案，不能承诺相同恢复能力。

需要回答：逻辑问诊如何跨连接识别；断开后保留哪些状态及保留多久；客户端缓存哪段音频、用什么连续序号或位置重放；服务端的确认表示已接收、已处理还是已持久保存；重复音频和结果如何识别；缓存不足、超出窗口或 end 与断连交错时如何明确返回结果或缺口。

现有 `AudioProgress.processed_audio_bytes` 是“本次识别流连续完成处理的字节数”，用于积压保护，并不承诺可跨流恢复的检查点；当前 WebSocket start 也没有恢复标识或位置。第六阶段应先确定上述契约，不能直接把已有处理进度当作断点续传确认。到实现时，再为每一步设定重放范围、重复/缺口及恢复时间的验收指标。

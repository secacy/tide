# 单实例会话准入：设计与验收计划

Date: 2026-09-22
Status: 待开发者实现；尚无准入控制的实测结果。

## 问题与本步目标

发送期限保护只约束一次 Worker Send 的等待。现有 sessionTracker 虽然跟踪尚未完成清理的会话，但会在未停止接入时无限制地增加 active。因此，即使单个会话最终能够退出，同一时刻仍可能接纳过多会话。

本步为每个 Gateway 实例增加接入上限。保证已登记、尚未完成清理的会话数不超过配置；满载时立即拒绝新请求；清理完成后归还名额。

## 为什么调整推进顺序

原建议先确定应用层缓冲边界。暂停实验表明当前直接转发已经能够完成本次短暂抖动负载，但发送成功不能证明识别及时；尚无新增队列会降低延迟的证据。先保留直接转发与发送期限保护，完成可以独立验证的会话准入，再处理缓冲及其他等待边界。

这没有将应用层队列等同于所有缓冲有界，也没有将会话上限等同于已测稳定容量。

## 方案比较

| 方案 | 优点 | 代价与当前选择 |
| --- | --- | --- |
| 满载后等待空位 | 可以吸收短暂接入峰值 | 等待者仍占连接和处理资源；长时问诊释放慢，还需要等待队列上限、期限与取消机制，暂不采用 |
| 有界 channel 充当信号量 | 名额获取与归还直观 | 当前停止标记和 active 已由 tracker 管理，另加信号量会引入两套需要协调的状态，暂不采用 |
| 在 tracker 的同一把锁下判断并登记 | 复用 active/leave，停止与容量判定一致 | 需要保证临界区仅做检查和计数；本步采用 |
| 外部服务统一分配名额 | 可做多实例总量控制 | 增加跨实例协调和故障处理，本阶段先实现单实例上限 |

## 行为约定

- Config.MaxSessions：负值无效；0 使用开发默认值 64；正值为本实例上限。64 是初始资源保护策略，不是容量实验结论。
- tracker 保存不可变的 maxActive；内部构造函数要求正值，Gateway.New 在调用前完成校验和默认值处理。
- tryEnter 改为返回 error：nil 表示登记成功；errGatewayStopping 表示停止接入；errSessionLimit 表示名额已满。
- 在一把锁内依次执行：检查 stopping；检查 active >= maxActive；增加 active。两个拒绝分支不改变 active。
- 在 WebSocket 升级前尝试登记。满载或停止均返回 HTTP 503，通过不同错误文本区分原因；不升级连接，不创建 Worker stream，也不排队等待。
- 成功登记后立即 defer leave；先前的资源释放顺序继续保留。升级失败也归还名额。输入 end、RPC 取消或 Worker 退出本身都不是提前归还名额的理由。
- active 包括正在升级、等待 start、识别和收尾的请求。拒绝的 HTTP 请求仍有短暂处理开销；本机制不限制全部 HTTP 连接或操作系统资源。
- 单实例上限不保证多个实例共享的 Worker 不过载；不提供 Worker 调度或按用户限额。

## 实现范围

开发者修改 internal/gateway/tracker.go 和 handler.go。保持 session、upload、download 的职责不变，不增加按 ID 查询的会话注册表。本步只需计数和接入判定。

## 待执行的验证与量化口径

实现后由助手补测试并执行，不将下列预期写成已经发生的结果。

1. 配置默认值、正值及负值校验；并发 tryEnter 不突破上限；拒绝不改变计数；停止接入后不能因释放名额而重新接入。
2. 满载在升级前返回 503；升级失败归还名额；等待 start 也占名额；完整清理后可以再次接入。
3. 真实链路实验配置上限 4，每轮并发发起 20 个连接；已接纳者在所有尝试均得到结果之前保持占位，避免提前释放干扰统计。预期每轮接纳 4、容量拒绝 16、其他错误 0，峰值已登记数不超过 4。
4. 清理已接纳连接，确认计数归零，再验证重新接入；重复 5 轮，保留逐次结果与环境。初始突发共 100 次尝试，后续重新接入单独计数。
5. 运行既有生命周期和发送超时回归及 race 检查；保留失败和异常数据。拒绝等待时长可实测记录，但不预设未经验证的毫秒目标。

本实验验证资源保护规则，不测最大吞吐或推荐生产会话数。Worker 稳定容量仍属于第五阶段。

# 未确认音频预算与超限策略（链路验收与对照实验已完成）

## 问题与实验依据

[EXP-004-10](../../experiments/progress-backlog-baseline.md) 中，正常、暂停 500ms、持续降速三组的网关未确认音频观测峰值分别为 0.1、0.5、4.3 秒。降速组 Send 最大约 1.2 秒，未触发 2 秒发送期限，但客户端 end 后还需等待约 10.14 秒。这表明操作期限不能代替对处理积压的限制。

新增策略针对每个会话已完整读取、尚未获得 Worker 处理确认的原始音频字节数。目标是控制继续向慢 Worker 投入多少未确认音频，并让超限失败可区分、可验证；不宣称提高模型处理速度。

## 选择与代价

| 方案 | 收益 | 代价与当前选择 |
| --- | --- | --- |
| 仅依赖已有 Send/尾部期限 | 无新增控制逻辑 | 已有基线证明仍可能发生明显处理落后，不足以覆盖本问题 |
| 达到预算后暂停读取/发送，等待确认释放额度 | 短暂抖动恢复后可以继续原流 | 真实采集仍会继续，音频可能积在上游；还需等待预算、唤醒与取消规则，单独使用不能保证实时性，暂不采用 |
| 超过预算就结束当前会话 | 限制继续放行音频，失败语义和清理路径明确 | 无法继续完成本次流，已有文本只能作为部分结果；选择此策略作为第一版 |
| 丢弃部分音频后继续 | 可能追上输入时间轴 | 转录出现缺口，当前协议没有缺口表达与恢复能力，不采用 |
| 增加应用层队列 | 可以控制新增的本地排队 | 无法提高 Worker 处理速度，也不单独解决下游已接收音频的积压，不因本任务增加队列 |

超限终止不是透明恢复，不能将此前已返回的 partial/final 片段描述为完整问诊转录。后续需要继续问诊时，重连和有限重放属于第六阶段。

## 预算单位、开关与候选值

- 按原始音频字节计量，和已有 receivedBytes / processedBytes 对齐；不限消息数量。
- 后续配置名计划为 MaxPendingAudioBytes，0 表示关闭该限制，正值启用。不会仅因 Worker 没有汇报进度就自动关闭保护。
- 默认关闭用于保留当前链路及无进度 Worker 的兼容行为；实验显式启用。真实适配器需要提供可信进度，否则启用后累计输入会耗尽预算并失败。
- 第一组对照实验候选值为 32000 字节，按当前 16kHz/单声道/16-bit PCM 换算为 1 秒音频：高于已测短暂停顿的 0.5 秒峰值，又明显低于降速组的 4.3 秒峰值。这是实验候选，不是生产 SLA，亦不能保证所有 500ms 暂停都会成功。
- 1 秒音频量不是 1 秒实际等待时长；音频格式变化需要重新换算。单块本身超过预算也不能放行，客户端分块必须与预算相容。

## 判断位置与边界

后续接入顺序：完整读取一块 → addReceived → snapshot → 检查预算 → 合法才调用 Send。继续保留每会话单个上传 goroutine，判断后不会有另一个上传者增加计数；下载确认只会减少未确认量。锁仍不覆盖 I/O。

不得在检查失败后回滚 receivedBytes，因为触发失败的块已经被网关完整读取。超过预算的块不再发送，随后按独立失败原因结束当前会话。

因此不能宣称 receivedBytes - processedBytes 始终不超过预算：终止前的计数可以包含一块刚读取但不再放行的音频。在此前检查均通过、逐块串行输入的前提下，触发检查时的超出量至多是一块消息的大小；它受已有 MaxMessageBytes 约束，但不等于总内存边界。使用本次固定 3200 字节分块和 32000 字节预算时，触发失败的快照最多可为 35200 字节（1.1 秒音频）。精确行为以边界测试验证，不用周期采样证明硬上界。

这一控制不覆盖尚未读取的上游音频、所有网络缓冲或模型内部资源；不替代 Send、输入空闲、尾部和结果写回期限。

## 本次实现：纯判断函数

开发者只新增 internal/gateway/backlog.go，不修改现有计数方法、配置、构造函数或 upload/download：

```go
// ErrAudioBacklogExceeded 表示当前未确认处理音频量超过配置预算。
// 它是积压超限原因，不表示某次网络操作超时。
var ErrAudioBacklogExceeded = errors.New("audio backlog exceeded")

// checkPendingAudioLimit 检查一个有效计量快照是否超过未确认音频预算。
// maxBytes 的单位是原始音频字节，0 表示关闭限制。
// pendingBytes 等于预算时允许继续；严格大于预算时返回包装
// ErrAudioBacklogExceeded 的错误，并包含实际未确认量与预算值。
// 本函数不修改计量、不等待、不取消会话；调用方负责后续控制。
func checkPendingAudioLimit(p audioProgressSnapshot, maxBytes uint64) error
```

使用 p.pendingBytes，不另行计算或改变其口径。快照由 audioProgress.snapshot 产生，该函数依赖计量器已有的不变量，不重复实现确认合法性校验。错误需通过 `%w` 包装，以便调用方使用 errors.Is 识别。

纯函数与计量器的取舍：将策略放在计量器外，可保留 addReceived 在所有输入状态下的事实记录职责，避免“返回超限错误时究竟是否记账”的歧义；代价是接入时必须明确调用位置。该调用位置会有独立链路测试。

## 配置与链路接入方案（已实现）

1. Config 增加 `MaxPendingAudioBytes int64`，0 关闭、正值启用、负值在 New 拒绝。配置使用有符号类型以明确拒绝负数；内部仅在校验后转换为 uint64。0 不填默认 32000，候选预算仍由实验显式设置。
2. session 增加 `maxPendingAudioBytes uint64`；newSession 末尾增加同名参数并赋值，ServeHTTP 将已校验配置转换后传入。测试及实验夹具的构造调用由助手在接入检查时同步调整。
3. upload 在 addReceived 成功后、sendWithTimeout 之前调用 `checkPendingAudioLimit(s.progress.snapshot(), s.maxPendingAudioBytes)`。若返回错误，立即汇报新类别 resultAudioBacklogExceeded，保留原错误；不能继续 Send、回滚计数、另等一个超时或在这里关闭资源。
4. sessionResultKind 增加 resultAudioBacklogExceeded（注释说明是未确认音频超限，区别于操作超时）。finish 对应分支先 cancelRPC，再尝试 WebSocket 1011 / `audio backlog exceeded`，随后 cancelWS；关闭失败用 `%w` 包装，成功返回 nil。保持现有 run 等待两侧退出的流程。

收尾选择：上传直接取消/关闭较短，但会分散资源所有权；采用现有的汇报事件、协调者统一收尾方式，便于继续沿用生命周期测试。固定关闭原因不拼接原始错误或字节数，内部返回的错误仍保存实际预算信息。关闭握手失败或客户端不读时不能保证收到该关闭原因，不把握手等待误称为实时性保证。

此次不增加 `end` 检查、后台巡检或新的计时器。确认累计量等于输入量不代替 Worker EOF；已有 start/input/Send/tail/write 期限继续处理各自等待。启用预算但不汇报进度的 Worker 不获得静默豁免；默认关闭仍保持现有兼容行为。

接入验证将检查默认关闭、自定义值及负值拒绝、完整构造传参、等于预算放行、超限块不发送、失败账目保留、RPC/handler 清理及名额复用；接着再做改造后实验，不预先填写改善结果。

## 为什么暂不增加有界队列

本轮遇到的是下游持续处理落后。增加队列只能改变等待发生的位置，不能让 Worker 多处理音频。当前 upload 在 Send 返回前不读取下一块，本来没有无限增长的应用层音频队列；新增预算覆盖已读音频中尚未确认的部分，单消息大小则限制单次读取内容。

可选方案是现在加入队列并控制队列字节数，优点是短暂发送阻塞时读写可以独立推进；代价是增加排队、满载策略与退出协作，还需同时统计队列外已经发出的未确认音频。本阶段保留直接转发，原因是现有证据还没有指出必须通过读写拆分解决的具体问题。这是基于当前范围的设计选择，不是已完成的队列性能对比。

## 让启动命令显式启用预算（2026-09-26 已验收）

问题：保护已经可通过 Go Config 启用，但普通启动未传入该配置。默认关闭是兼容策略，本身没有错误；缺的是无需改源码的显式启用入口。

| 方案 | 优点 | 代价与选择 |
| --- | --- | --- |
| 在 main 中写死 32000 | 改动少 | 把实验候选值变成隐含默认，切换需改源码；不采用 |
| 环境变量 | 便于进程管理和部署注入 | 需要约定命名、解析及优先级；当前只有一个实验开关，暂不增加第二条配置来源 |
| 命令行参数 | 命令直接保留实验配置，标准库即可实现 | 参数增多后需统一整理；本步采用 |
| YAML/配置框架 | 适合大量配置 | 当前不足以抵偿文件和配置层复杂度；暂不采用 |

由开发者实现：

1. 新建 cmd/gateway/config.go，提供 `parseGatewayConfig(args []string) (gateway.Config, error)`。仅做命令行语法解析与映射，不启动服务或建立连接；使用独立 FlagSet，ContinueOnError，让调用方处理错误和帮助。
2. 注册 `-max-pending-audio-bytes`（int64，默认 0），说明单位为原始音频字节、0 关闭、正值启用、负值无效。保持原 MaxMessageBytes=1MiB。
3. Parse 失败原样返回错误；拒绝多余位置参数，避免拼错命令后静默启动。负数的语义校验沿用 Gateway.New，不复制默认值和整套校验逻辑；数字溢出由 int64 参数解析返回错误。
4. main 调用 parseGatewayConfig(os.Args[1:])；遇到 flag.ErrHelp 正常返回，其他错误按现有方式报告。成功后将 cfg 传给 `run(ctx, cfg)`。
5. run 将传入 cfg 直接交给 gateway.New，不重新创建只包含 MaxMessageBytes 的配置，也不把 0 改成 32000。

函数注释需解释 args 不包含程序名，返回值交给 Gateway.New 做语义校验；run 注释说明接收启动配置并组装依赖。

实现后助手补测试并检查实际传参：省略/显式 0、正值、负值最终被拒绝、非法数字、整数溢出、未知参数、位置参数、帮助。测试配置解析时不依赖网络，入口检查确保参数最终到达 Gateway。由于代码拆成同包多个文件，启动命令用 `go run ./cmd/gateway`，避免单文件运行漏编译 config.go。

已支持的命令：

```sh
go run ./cmd/gateway -max-pending-audio-bytes=32000
```

本步不扩展其他参数、不修改 Mock 启动配置、不引入线上指标系统。

## 随后的验收：反复故障与资源趋势

启动参数验收后，再由助手设计有界、可重复的实验，观察同一 Gateway 反复经历超限及超时退出时，会话/连接/Worker 是否逐轮清理，goroutine 和 GC 后存活堆是否持续累积。故障组需与正常组比较，预热与测量分开，不用单次 HeapAlloc 下跌证明泄漏不存在。

该项是原第四阶段资源验收的补证据，不是并发容量实验；结果只能描述已测条件下的趋势。严格总内存上界需分别分析应用缓冲、依赖传输和模型资源，不能用预算乘 MaxSessions 推导整个进程内存上限。更大规模、长时和多 Worker 稳定容量留给第五阶段。

# Tide 实时语音网关技术方案

本文是 Tide 的总体验证与演进方案。服务职责见[服务划分](./服务划分.md)，断线后的详细时序和可靠性边界见[断线重连](./断线重连.md)。本文只声明一次公共协议和核心技术决策，避免三份文档重复定义。

## 1. 目标与边界

Tide 面向浏览器实时语音转录，负责：

- 安全地创建逻辑音频流并接入 WebSocket；
- 将 PCM 音频低延迟转发到流式 ASR；
- 将 ACK、临时文本和最终文本返回客户端；
- 在网关多副本环境中支持短时断线续接和 owner 故障接管；
- 对过载、慢客户端、非法音频和重复连接给出明确结果。

本仓库不负责 ASR 模型实现、业务病历、完整录音归档和业务数据库。需要这些能力时，应通过独立服务接入，不能假定 Tide 已经提供。

## 2. 当前实现结论

原方案混合了设想与现状。以下结论以当前代码、Proto、测试及部署文件为准：

| 主题 | 当前实现 | 方案结论 |
|---|---|---|
| 音频格式 | 浏览器重采样为 16 kHz、单声道、PCM16LE | 保持 |
| 音频帧 | 640 samples，即 40 ms、1,280 字节 PCM | 使用 40 ms；删除 100 ms、256 ms 的冲突说法 |
| 音频位置 | 每帧携带大端 `uint64 sample_offset` | 使用采样点偏移，不再另设含义重叠的 `Sequence ID` |
| WebSocket 建连 | HTTP 创建 stream，WS 首帧发送 `hello + token` | 保持；不是 `session.start/session.attach` 协议 |
| 就绪时机 | WS `ready` 在 bridge 创建前发送，ASR `Ready` 未被消费 | 认证附着与 ASR 可写应分成两个阶段 |
| 暂停/继续 | 浏览器本地停止发送，服务端无暂停信令 | 不声明 `recording.pause/resume` 已实现 |
| 多节点路由 | edge 网关查询 Redis owner，经 peer gRPC 转到 owner 网关 | 保持；不是 Redis 直接保存 `stream -> ASR Pod IP` |
| ASR 上下文 | owner 网关内存中持有唯一 ASR gRPC stream | owner 存活时可连续；owner 变化时重建并提升 `epoch` |
| owner 身份 | 节点 ID 加进程启动时生成的 incarnation | 已避免同 Pod 容器重启后错误沿用 epoch |
| 去重与连续性 | owner runtime 按 `sample_offset` 校验、去重 | 不能再称网关“盲转发且不去重” |
| ACK | ASR 返回 `next_sample_offset`，网关透传 | ACK 语义需要与网关接收水位分离，见 5.2 |
| 文本恢复 | 无 `event_id` 和下行事件重放 | 当前不保证断线期间文本不丢 |
| 音频恢复 | 演示网页没有未 ACK Ring Buffer，断线时直接丢采样 | 当前不保证音频无损；客户端缓存是 P0 改造 |
| 归档 | 不保存 PCM 或转录正文 | Sidecar、`/dev/shm/*.wav` 和对象存储均未实现 |

因此，当前系统的准确能力描述是：**同一 owner 存活时保留 ASR 流并允许重新附着；owner 失效时优先恢复可用性，通过新 `epoch` 明示上下文断层，不承诺无损恢复。**

## 3. 总体架构

```text
Browser ─ WebSocket ─ Edge gateway ─ peer gRPC ─ Owner gateway ─ bidi gRPC ─ ASR
                              │              │
                              └──── Redis ───┘
                           会话、generation、owner lease、epoch、水位
                           不保存 PCM 和转录正文
```

任意网关都可以成为 edge；每条逻辑流同一时刻只有一个 owner。连接落到非 owner 节点时，edge 只做协议终结和跨节点转发；owner 维护 offset、背压队列和 ASR stream。这个设计避免要求负载均衡器提供粘性会话，同时承认 owner 是有租约的内存状态节点，并非“完全无状态”。

## 4. 对外协议

### 4.1 创建与结束

创建逻辑流：

```http
POST /v1/streams
Authorization: Bearer <access-jwt>
Content-Type: application/json

{"language_code":"zh-CN"}
```

返回 `stream_id`、`websocket_url`、一次性 `attach_token`、过期时间以及服务端接受的音频参数。客户端必须使用返回参数，不能假定请求参数一定被接受。

显式结束使用 WebSocket 文本帧 `{"type":"end"}`，或调用幂等的 `DELETE /v1/streams/{stream_id}`。删除接口必须校验租户归属。

### 4.2 WebSocket 握手

升级成功后，客户端须在 3 秒内发送：

```json
{"type":"hello","token":"<attach-or-resume-token>"}
```

服务端原子消费 token、增加 attachment `generation`，并返回：

```json
{
  "type": "ready",
  "stream_id": "...",
  "epoch": 1,
  "next_sample_offset": 0,
  "resume_token": "<rotated-one-time-token>",
  "expires_at": "..."
}
```

`generation` 只用于服务端排除旧连接，不需要暴露给浏览器。新附着成功后，旧 attachment 即使仍有 TCP 连接也不能继续写入。

当前 `ready` 实际只表示 token 已消费且会话元数据已附着：它在 peer/owner bridge 创建之前发送，ASR Proto 中的 `Ready` 也没有参与 WebSocket 就绪判断。目标协议应先返回一个只承载轮换 token 的 `attached` 事件，再在 bridge 建立且收到 ASR `Ready` 后返回 `ready`；客户端只能在后者之后发送或回放音频。这样既不会因后端初始化失败丢失新 token，也不会过早宣称 ASR 可写。

### 4.3 音频二进制帧

```text
0                   7 8
+--------------------+---------------------------+
| sample_offset (BE) | PCM16LE mono, 2..1280 B  |
+--------------------+---------------------------+
```

- `sample_offset` 是从逻辑流开始累计的采样点位置，不是字节偏移；
- 常规帧为 640 个采样点，即 40 ms；尾帧可以更短；
- offset 小于服务端接收水位的完整重复帧被幂等忽略；
- offset 大于期望值表示缺口，返回 `invalid_offset`，不得静默跳过；
- 单帧大小、偶数 PCM 长度和消息类型都在入口校验。

40 ms 在交互延迟和每秒 25 帧的协议开销之间更均衡。客户端 AudioWorklet 应使用带抗混叠滤波的高质量重采样器；当前最近邻重采样只适合作为演示实现。

### 4.4 服务端事件

当前事件类型为：

- `ack`：ASR 确认的 `next_sample_offset`；
- `transcript`：`epoch`、`segment_id`、`revision`、`text`、`is_final`、时间范围；
- `discontinuity`：owner 变化导致 ASR 上下文重建；
- `error`：稳定错误码、安全消息和 `retryable`；
- `ended`：逻辑流已结束。

临时文本以 `(epoch, segment_id)` 为键，只接受更大的 `revision` 并覆盖显示；final 也必须幂等处理。不能简单地把每次收到的 final 都追加，否则重放或重试会产生重复文本。

WebSocket 使用控制帧 Ping/Pong 做存活检测，不再定义一套重复的应用层 `ping/pong`。当前也没有 `flow.control`、`request_id`、`session.started` 等消息，后续只有在存在明确请求关联或客户端可执行的流控动作时才增加。

## 5. 可靠性设计

### 5.1 三个相互独立的版本号

- `sample_offset`：音频数据位置，用于查缺、去重和重放；
- `generation`：连接附着版本，用于 fencing，防止旧连接继续写；
- `epoch`：ASR 上下文版本，owner 改变时递增，提醒客户端不同 epoch 的 partial/final 不可直接覆盖。

三者不可合并。详细状态迁移见[断线重连](./断线重连.md)。

### 5.2 分离接收水位与提交水位

当前 runtime 在音频进入 owner 内存队列时就推进 `nextOffset`，并周期性写入 Redis；ASR ACK 又使用同名字段返回客户端。这会把“网关已接收”和“ASR 已确认”混为一谈，owner 故障时可能高估可恢复进度。

目标实现应拆成：

- `accepted_offset`：owner 已接收入内存队列，用于同一 owner 上的即时去重；
- `committed_offset`：满足既定可靠性条件后才能让客户端释放缓存。

在当前不持久化音频的架构中，`committed` 最多表示活动 ASR stream 已确认，不能跨 owner 保证恢复。如果产品要求 owner 故障后仍然无损，必须先把音频写入可重放的持久化日志或对象存储分片，再推进 durable `committed_offset`。不能仅靠 Redis 中的一个 offset 声称音频已安全保存。

### 5.3 下行文本一致性

当前 owner 在没有 attachment 时会丢弃下行事件，因此即使 ASR stream 保留，断线前在途的 final 也可能无法补发。目标方案至少应在 owner 内存中保存续接窗口内的 final 事件，并给事件增加单调 `event_id`；如果 final 文本是医疗记录的一部分，则应由业务归档链路持久化并支持按游标读取。Redis 会话注册表不应存储转录正文。

## 6. 背压与容量

- owner 音频队列当前为 50 帧，约 2 秒；队列满返回 `backpressure` 并要求重连；
- 浏览器必须监控 `WebSocket.bufferedAmount`，不能无限向浏览器网络缓冲区写入；
- ACK 和 partial 可以合并或丢弃旧版本，final 不得无声丢弃；final 队列无法消费时应关闭连接并返回 `slow_client`；
- 30 秒、16 kHz、PCM16 单声道音频约 960 KB，适合作为每条流的浏览器内存重传上限；超限必须明确停止采集或提示丢失，不能覆盖尚未提交的数据；
- 10,000 路单向原始 PCM 约 320 MB/s，部署时还要计算 peer 和 ASR 转发带来的额外带宽，优先减少跨节点转发比例。

## 7. 安全、隐私与可观测性

- access JWT 校验 `iss/aud/exp/sub/tenant_id`；生产环境使用 JWKS；
- attach/resume token 为短效、单次使用且每次附着轮换；WebSocket 校验 Origin；
- ASR 与 peer gRPC 使用 TLS/mTLS；入口 TLS 在 Ingress 或负载均衡终止；
- 日志、Trace、指标不得包含 token、PCM、转录正文、患者信息、租户 ID 或用户 ID；
- Redis 只保存路由和状态元数据，并设置会话上限、TTL 与租户配额；
- `/metrics` 仅暴露在管理网络，至少观测活跃连接、owner 数、音频/结果转发延迟、错误码、重连成功率、epoch 切换和 offset 差值。

## 8. 实施顺序

1. **P0：修正续接正确性。** 浏览器始终缓存未 committed 音频；区分 accepted/committed 水位；附着时原子校验 30 秒窗口；解决长会话中 2 分钟 resume token 过期问题。
2. **P0：修正 owner fencing。** owner ID 加入每次进程启动唯一的 incarnation；任何 runtime 丢失后的接管都必须产生新 epoch。
3. **P0：修正就绪语义。** 分离 `attached` 与 `ready`，等待 owner bridge 和 ASR Ready 后才允许音频发送。
4. **P0：补齐客户端幂等。** 重连循环保持 single-flight；按 `(epoch, segment_id, revision)` 更新文本，遇到 `discontinuity` 明示断层。
5. **P1：补 final 事件恢复。** 引入 `event_id` 和续接窗口内的 final 缓存；需要医疗级留存时接业务持久化服务。
6. **P1：提升音频质量和流控。** 使用高质量重采样、监控 `bufferedAmount`、明确缓存溢出策略。
7. **P2：按业务 SLA 选择持久化。** 只有明确要求 owner 故障后音频无损时，才引入可重放音频日志/分片对象存储和归档 Worker。

每项能力完成前，接口文档和产品 SLA 都应保留“当前保证”说明，避免以设计目标代替已经实现的事实。

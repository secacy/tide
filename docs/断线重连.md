# 断线重连与故障恢复

本文细化[技术方案](./技术方案.md)中的续接语义。WebSocket 重连是创建新连接并重新附着同一个逻辑 `stream_id`，不是恢复旧 TCP/WebSocket，也不等同于 ASR 上下文一定可恢复。

## 1. 保证等级

| 场景 | 当前服务端 | 当前演示网页 | 完成 P0 后的目标 |
|---|---|---|---|
| 短时断线、owner 存活 | 保留 ASR stream 30 秒，可重新附着 | 会重连，但断线期间采样被丢弃 | 浏览器缓存并重放，音频连续 |
| 新连接落到其他 edge | peer 转发回原 owner | 支持 | 保持 |
| 同 token 重放/双连接竞争 | token 单次消费，generation 排除旧连接 | 支持保存轮换 token | 保持 |
| owner 故障或滚动交接 | 租约接管、epoch 递增、重建 ASR | 显示 discontinuity | 可用性恢复，但仍不承诺上下文无损 |
| 断线期间下行 final | 无事件缓存，可能丢失 | 无法补偿 | 增加 event_id 和 final 重放 |
| owner 故障后音频无损 | 无持久音频，不能保证 | 无法补偿 | 只有引入 durable audio ingest 后才能保证 |

禁止使用“零丢帧”“完美拼接”“无感恢复”等绝对表述，除非相应故障注入测试覆盖了浏览器、edge、owner、Redis、ASR 和归档链路。

## 2. 关键状态

- `stream_id`：逻辑流身份，在多个 WebSocket 和 epoch 之间保持不变；
- `generation`：每次成功附着原子递增；只有最新 generation 可以发送音频；
- `epoch`：owner 首次获取时为 1，换 owner 时递增；标识 ASR 上下文边界；
- `accepted_offset`：当前 owner 已接收的下一个采样点；
- `committed_offset`：客户端可以安全释放的下一个采样点；
- `resume_token`：单次使用的附着凭证，成功附着后立即轮换；
- `owner_lease`：当前 owner 的短租约，默认 10 秒、每 3 秒续租；
- `detach_window`：连接断开后保留 runtime 的窗口，默认 30 秒。

当前代码只有一个持久字段 `next_offset`，实际更接近 `accepted_offset`；客户端收到的 ASR `ack.next_sample_offset` 更接近 `committed_offset`。P0 改造应在命名和存储上将两者分开。

## 3. 稳态发送

目标客户端对每个 40 ms 帧执行以下顺序：

1. AudioWorklet 生成 640 个 16 kHz 采样点；
2. 使用本地连续采样位置作为 `sample_offset`；
3. **先写入内存 Ring Buffer，再尝试发送**；
4. 连接可写且未触发背压时发送二进制帧；
5. 收到 committed ACK 后，删除 `frame_end <= committed_offset` 的缓存；
6. 即使 WebSocket 暂时不可写，也继续在容量上限内采集和排队，offset 不回退。

30 秒缓存约 960 KB/stream。Ring Buffer 满且最旧数据尚未 committed 时，客户端必须停止采集并明确提示，或按产品策略结束会话；不得静默覆盖。刷新页面或浏览器进程崩溃不属于纯内存 Ring Buffer 的保证范围。医疗音频是否落 IndexedDB 必须经过隐私、安全和清理策略评审。

当前 `app.js` 只在 `WebSocket.OPEN` 时发送数据，断线或重连中直接丢弃 Worklet 输出，也会在收到 `ready` 时直接把本地 offset 改为服务端 offset。因此当前页面只能演示重建连接，不能作为无损续接实现。

## 4. 正常断线续接时序

### 4.1 断线与挂起

1. edge 通过 EOF、读错误或 WebSocket Ping/Pong 失败发现连接断开；
2. 当前 attachment 关闭，Session Registry 以当前 generation 原子标记 `detached` 并写入 `detached_until`；
3. owner 关闭该 attachment 的事件通道，但保留 ASR gRPC stream、offset 和短期 runtime；
4. owner 启动 30 秒 timer；ASR 无需切换到虚构的 `Suspended` 协议状态，当前实现只是暂时没有新音频输入；
5. 浏览器继续把音频写入本地 Ring Buffer，并以退避和抖动重试，避免所有客户端每秒同步重连。

### 4.2 重新附着

1. 浏览器建立新的 WebSocket，可以落到任意 edge；
2. 在 3 秒内发送当前 `resume_token`；
3. Session Registry 原子校验 stream、tenant、token hash、token 过期时间和 `detached_until`，消费 token 并增加 generation；
4. 服务端返回 `attached` 和轮换后的 token，浏览器更新凭证但还不能发送音频；
5. edge 获取 owner 信息：owner lease 有效则通过 peer 回到原 owner；租约已过期则尝试接管并增加 epoch；
6. owner 取消 detach timer，用新 generation 替换旧 attachment，并确认 ASR stream Ready；
7. 服务端返回 `ready`、恢复 offset 和 epoch；
8. 浏览器从服务端要求的 offset 开始按原速或受控倍速回放缓存；完成追赶后恢复实时发送。

当前 Attach 实现尚未检查 `detached_until`，导致“30 秒窗口”主要由存活 owner 的本地 timer 执行，owner 已丢失时语义不一致。应把窗口校验加入 Redis Lua 和 MemoryStore 的原子 Attach 操作，并为 `resume_window_expired` 返回稳定错误码。

当前 WebSocket 实现也在 bridge 创建前就发送 `ready`，且忽略 ASR Proto 的 `Ready`。上述 `attached -> ready` 两阶段是目标时序，用于区分“凭证已轮换”和“音频链路已可写”。

浏览器只能运行一个 reconnect loop 和一个在途 connect。当前示例的 `onclose` 与 Promise `catch` 都可能调用 `scheduleReconnect`，但没有 timer/inflight fencing，失败路径可能安排多个并发重连并争用同一个一次性 token；P0 客户端改造应统一由一个带取消能力的状态机调度。

### 4.3 重放校验

- 服务端 offset 等于某个缓存帧起点：从该帧开始重放；
- 服务端 offset 大于缓存最早位置：删除更早的完整帧后重放；
- 服务端 offset 小于客户端最早缓存位置：客户端已缺数据，必须报告 `audio_gap`，不能伪造静音或跳到本地 offset；
- 服务端 offset 落在某帧内部：协议实现应支持裁剪该帧后重放，或保证所有持久水位始终按采样边界对齐；
- 重复完整帧：owner 返回当前 ACK，不再次送入 ASR；
- 出现向前缺口：返回 `invalid_offset` 并关闭本次 attachment。

追赶期间应限制发送速率并观察 `bufferedAmount`。一次性“倾泻”30 秒音频会放大 edge、peer 和 ASR 队列压力，不是合适的恢复策略。

## 5. Token 生命周期

当前 attach/resume token 固定有效 2 分钟，并且只在附着成功时轮换。一个持续超过 2 分钟且从未重连的正常会话，手中的 resume token 会过期，之后即使只断线 1 秒也无法附着。这与最长 4 小时 stream 和 30 秒续接承诺冲突。

推荐增加经 access JWT 鉴权的接口：

```http
POST /v1/streams/{stream_id}/resume-token
Authorization: Bearer <access-jwt>
```

接口校验租户归属、stream 状态和续接窗口，原子轮换 token hash，再签发短效一次性 token。浏览器优先使用已有 token；遇到 `token_expired` 且 access JWT 仍有效时调用此接口。这样不必把可抢占连接的 resume token 延长到整个问诊时长。

如果产品不允许断线后再次调用 HTTP，也可以在活动 WS 上周期性下发新 token，但必须处理消息丢失、并发轮换和旧 token 宽限期，复杂度更高。

## 6. owner 故障与 epoch

owner 进程崩溃时，本地 runtime、ASR gRPC stream、未持久化水位和下行事件一起丢失。恢复流程为：

1. 客户端连接任意 edge 并附着；
2. 若原 owner lease 尚有效，返回可重试的 `owner_unavailable`，客户端退避；
3. 租约过期后，新节点获取 owner，`epoch += 1`；
4. 新 owner 从 Session Registry 的恢复水位创建新的 ASR stream；
5. `ready` 后发送 `discontinuity(previous_epoch, epoch, owner_changed)`；
6. 客户端结束旧 epoch 的 partial 展示，不允许新 epoch 的同名 segment 覆盖旧 epoch；
7. 浏览器按服务器指定位置继续发送。

这里恢复的是服务可用性，不是旧模型上下文。当前 Redis `next_offset` 来自 owner 接收队列并每 10 帧更新一次，既可能落后于内存水位，也可能领先于 ASR 真正确认。改造后应明确使用哪个水位：

- 只要求尽快继续实时识别：从最后已知边界开启新 epoch，并明确可能存在缺口；
- 要求完整音频：从 durable audio store 的 committed offset 重放；
- 要求模型上下文连续：ASR 本身还必须支持可迁移 checkpoint 或基于已持久音频重建上下文。

单靠客户端重传“未 ACK 数据”无法重建已经 ACK、但随 owner 一起丢失的模型上下文。

owner lease 的持有者必须包含进程 incarnation。当前 Kubernetes 配置只使用 Pod 名；同一 Pod 内的容器重启会复用该 ID，Session Registry 可能判定 owner 未变化，从而在 runtime 已丢失时不增加 epoch。新进程必须使用新的 owner identity，使客户端必然收到 discontinuity。

## 7. 下行文本恢复

`segment_id + revision` 只能去重，不能找回从未到达客户端的事件。目标协议增加：

- 每个 stream/epoch 单调递增的 `event_id`；
- 客户端在附着时提交 `last_event_id`；
- owner 缓存 30 秒内的 final 和必要状态快照，续接后先重放再恢复实时事件；
- partial 只需重放每个 segment 最新 revision，无需保存所有版本；
- 缓存缺口返回 `event_gap`，客户端从业务转录查询接口获取最终状态。

医疗级 final 文本不应只保存在 owner 内存。业务归档服务应以 `(stream_id, epoch, segment_id, revision)` 为幂等键持久化，Tide Redis 仍不保存正文。

## 8. 生命周期与竞态

- 新 generation 成功后，旧连接的发送必须返回 `connection_replaced`；旧连接的 detach 不能覆盖新连接状态；
- 30 秒到期与新 Attach 必须通过原子状态操作决出唯一结果，避免一边成功 ready、一边结束 runtime；
- 客户端显式 `end`、DELETE、最大会话时长到期都会进入终态，之后不得恢复；
- owner 优雅下线时先停止接收新连接，通知 attachment 重连，释放租约并保留逻辑 stream；新 owner 接管后提升 epoch；
- Redis 不可用时不要猜测 owner 或放行 token；已有连接可按明确的短期降级策略继续，但新的 attach 应失败；
- 退避建议从 200 ms 起，指数增长到 2 秒并加入随机抖动，总时长不得超过服务端返回的续接截止时间。

## 9. 验收测试

至少覆盖：

- 在每个帧边界断开并恢复，验证 PCM 哈希、offset 连续且无重复；
- ACK 已发/未发、Redis 水位已刷/未刷的组合；
- 两个浏览器同时消费同一 token，以及新旧 generation 并发写；
- edge 重启、owner 强杀、owner 优雅滚动、owner lease 到期接管；
- 断线恰好发生在 detach window 和 token 过期边界；
- 30 秒缓存回放时的限速、背压和 Ring Buffer 溢出；
- partial revision 覆盖、final 重放幂等、事件缓存缺口；
- Redis 短暂不可用、ASR 返回错误和慢客户端；
- 2 分钟以上以及接近最大时长的真实长会话续接。

测试应区分“连接恢复成功”“音频无损”“文本无损”“ASR 上下文连续”四个指标，不能用 WebSocket 再次连上代替全部可靠性验收。

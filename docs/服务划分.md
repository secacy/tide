# 服务划分

本文只定义组件职责和数据所有权。公共协议、可靠性语义与实施优先级统一见[技术方案](./技术方案.md)，不在这里重复。

## 1. 划分原则

- 控制面与实时数据面分离，但不要为了概念完整而过早拆服务；
- 谁持有可变状态，谁负责该状态的并发控制和 fencing；
- Redis 是会话注册表，不是音频、转录或业务记录数据库；
- “可恢复”必须指出故障范围，不能把 owner 内存保活描述成跨节点持久化；
- 慢 I/O 不进入实时音频转发关键路径。

## 2. 当前仓库中的组件

### 2.1 Tide Gateway

当前一个 Go 进程同时承担 HTTP 控制接口、WebSocket edge 和 stream owner 三种角色。这是有意的部署单元合并，不代表职责没有边界。

**HTTP 控制接口**

- 校验 access JWT、租户配额和创建/连接速率；
- 创建 `stream_id`，签发一次性 attach token；
- 幂等结束 stream；
- 不查询业务病历库，不处理归档。

**Edge 角色**

- 终结 WebSocket、校验 Origin 和 hello token；
- 原子增加 attachment `generation`，使旧连接失效；
- 校验音频帧格式；
- 本机是 owner 时直连 runtime，否则通过内部 peer gRPC 转发。

**Owner 角色**

- 获取并续租 Redis owner lease；
- 使用“节点标识 + 进程启动 incarnation”作为租约持有者身份；
- 为逻辑流持有唯一 ASR gRPC stream；
- 校验 `sample_offset` 连续性、去重并实施背压；
- 转发 ACK 和 transcript；
- 连接暂离时保留 runtime，窗口到期后结束；
- owner 交接时释放租约；其他节点取得租约后使 `epoch` 递增。

因此，“网关只做盲转发、绝不去重”和“网关完全无状态”都不符合当前设计。准确说法是：edge 近似无状态，owner 有受租约保护的短期内存状态。

### 2.2 Session Registry（Redis / 单机内存实现）

保存：

- stream 状态、租户、语言、创建和过期时间；
- token hash、attachment generation；
- owner ID、内部地址、租约截止时间、epoch；
- 音频水位和断线窗口截止时间；
- 租户活跃流配额索引。

不保存：

- PCM/WAV；
- partial/final 转录正文；
- 病历或患者资料；
- ASR 模型上下文。

无 Redis 时使用内存 Store，只支持单节点语义；生产和跨节点续接必须使用 Redis。所有 attach、token 消费、generation 递增和 owner 获取都应保持原子操作。

### 2.3 ASR Service

ASR 是本仓库之外的服务，按照 `proto/tide/asr/v1/asr.proto` 提供双向 gRPC：

- 接收 `Start/Audio/End`；
- 返回 `Ready/Ack/Transcript/Error`；
- 校验约定的 PCM 参数和连续 offset；
- 定义 ACK 到底代表“进入 ASR 队列”还是“已被可靠处理”。

Tide 当前通过一个配置地址连接 ASR，没有在 Redis 中锁定具体 GPU Pod，也没有实现 ASR session 的跨流重附着。当前 owner 发送 Start 后并不等待 ASR `Ready`，这是需要按总方案 P0 修正的就绪语义。ASR 的负载均衡、模型调度和容量保护应由 ASR 平台或独立调度层负责，不应让普通业务 API 写 Pod IP 路由。

### 2.4 Gateway Peer

peer gRPC 是 Gateway 内部接口，不是独立部署服务。它让任意 edge 把连接转发到当前 owner，并携带 stream、tenant、generation 和 epoch 进行校验。该端口只应在集群管理网络开放并使用 mTLS。

## 3. 仓库外的可选组件

### 3.1 Business API

当产品已有挂号、问诊、医生权限和病历系统时，独立 Business API 负责：

- 业务级权限与问诊生命周期；
- 调用 Tide 创建/结束 stream；
- 关联业务 encounter ID 与 Tide stream ID；
- 消费最终转录、病历生成结果和录音 URL；
- 审计、数据保留和删除策略。

它不应代理 WebSocket 或音频流，也不应直接操作 Tide 的 Redis 内部结构。当前 Tide 自带的 `POST /v1/streams` 仍是数据面准入接口，不必为了拆分而再复制一套会话创建逻辑。

### 3.2 Archive Pipeline

只有业务要求保存完整录音或跨 owner 无损恢复时才引入归档链路。推荐设计为独立的流式 Ingest/Worker：

1. 按 stream 和 offset 接收不可变音频分片；
2. 分片持久化成功后推进 durable committed offset；
3. 异步合并或封装 WAV，并上传对象存储；
4. 通过幂等事件通知 Business API；
5. 根据保留策略清理临时分片。

不推荐让 ASR 把完整长录音写到 `/dev/shm` 再由 Sidecar 监听：内存盘容量受限，Pod 故障会同时丢失 ASR 和文件，文件完成事件也难以表达幂等、校验与业务确认。若 ASR 厂商只能输出本地文件，Sidecar 可作为兼容适配，但不应成为主可靠性方案。

## 4. 数据所有权与调用关系

| 数据 | 唯一权威方 | Tide Redis 是否保存 |
|---|---|---:|
| 业务问诊、医生/患者权限 | Business API / 业务数据库 | 否 |
| stream 准入、generation、owner lease、epoch | Tide Gateway + Session Registry | 是 |
| 活动 ASR 上下文 | 当前 owner 对应的 ASR stream | 否 |
| 未确认音频（P0 目标） | 浏览器短期 Ring Buffer | 否 |
| 持久音频（可选增强） | Archive Pipeline / 对象存储 | 否 |
| partial 文本 | ASR；客户端按 revision 展示 | 否 |
| final 文本/病历记录 | Business API 或专用转录存储 | 否 |

正常调用方向为：Business API 调 Tide HTTP；Browser 直连 Tide WebSocket；edge 调 owner peer；owner 调 ASR；归档组件通过明确的内部接口或事件总线与业务系统交互。ASR 和归档组件不直接回调浏览器。

## 5. 故障边界

- **edge 故障：** 浏览器重新连接任意 Gateway；owner 未变时 ASR 上下文可继续；
- **owner 故障：** 等租约过期后新 Gateway 接管并增加 epoch；当前实现重建 ASR，上下文有断层；
- **Redis 故障：** 禁止新建、附着和 owner 变更；已有内存流可短暂运行，但不能宣称可恢复；
- **ASR 故障：** 返回可重试错误并结束当前 runtime；是否重建由客户端续接和新 epoch 策略决定；
- **归档故障：** 不应阻塞实时转录；通过持久任务和幂等重试恢复；若其 ACK 是 durable committed 的依据，则失败时不得让客户端释放对应音频。

当前部署把 `TIDE_NODE_ID` 设为 Pod 名。容器在同一个 Pod 内重启时该值不变，新进程可能被 Redis 误认为原 owner，导致 ASR runtime 已丢失但 epoch 没有递增。启动时应生成不可复用的 incarnation（也可使用 Pod UID 加启动 UUID），并将它用于 owner acquire/renew/release。

## 6. 何时再拆分 Gateway 控制接口

只有出现独立扩缩容、安全域、发布节奏或团队所有权需求时，才把 Tide HTTP 控制接口拆成单独 Control Service。拆分后它仍只管理 Tide stream 元数据；实时 owner 状态、offset 校验和 ASR gRPC stream 必须留在数据面。以“API 服务是大脑”为理由提前拆分，会增加一次网络调用和分布式事务，却没有改善当前可靠性问题。
